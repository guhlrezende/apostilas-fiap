1O que é vibe coding, e o que não é

Se a IA escreve o código, o que sobra para mim?

"Vibe coding" é o nome que pegou, a partir de 2025, para programar descrevendo o que você quer em linguagem natural e deixando a IA escrever o código. O termo nasceu meio de brincadeira, para protótipos descartáveis em que você aceita o que vier.

Para trabalho de verdade, o seu papel muda de digitar para especificar e verificar: dizer exatamente o que quer, ler o que mudou, rodar os testes e decidir. A vaga de AI Builder descreve isso: não precisa saber como o modelo funciona por dentro, precisa saber o que pedir e transformar em algo que funciona.

O limiteCódigo que você não entende e não testou não vai para algo que outras pessoas usam. Protótipo pode ser no impulso; ferramenta interna, não.

2O Cursor

Por que um editor próprio, e não só o chat no navegador?

O Cursor é um editor de código baseado no VS Code com IA integrada. Ele enxerga o projeto inteiro, então a IA trabalha em cima dos seus arquivos, e não de trechos colados. As peças principais:

PeçaPara que serve
Tabautocompletar enquanto você digita
Chat e agentepedir mudanças em vários arquivos; o agente lê, edita e roda comandos
@ (menções)apontar arquivos, pastas ou documentação como contexto
Rulesinstruções permanentes do projeto

Rules, conferido na documentação: as regras do projeto ficam em .cursor/rules, em arquivos .mdc. Há quatro tipos: Always (sempre no contexto), Auto Attached (quando arquivos que batem com um padrão aparecem), Agent Requested (a IA decide pela descrição) e Manual (só quando você chama com @nome). Um AGENTS.md simples na raiz também é aceito. O antigo .cursorrules ainda funciona, mas está depreciado.

E o Claude Code?A extensão do Claude Code instala também no Cursor. Os dois convivem: a apostila do Claude cobre o Claude Code em detalhe.
PlanosO Cursor tem uma entrada gratuita com uso de IA limitado e planos pagos. Os nomes e limites dos planos mudaram mais de uma vez em 2026: confira a página de preços antes de assinar.

3O laço seguro

Como evitar a pilha de mudanças que ninguém entende?

1. Commit limpo

Antes de pedir, git status sem pendências. Se a IA estragar, git restore . volta tudo.

2. Peça um plano

"Antes de editar, liste os arquivos que vai mudar e por quê." Corrija o plano, não o código.

3. Um passo pequeno

Uma funcionalidade por vez. Diff grande é diff que você não lê.

4. Leia o diff

Procure segredo no código, arquivo que não devia mudar e teste apagado para "passar".

5. Rode a verificação

Testes, o app abrindo, o fluxo rodando. Peça para a IA mostrar a saída do teste, não dizer que passou.

6. Commit

Mensagem curta do que mudou. Volte ao passo 2.

A IA "resolveu" o teste que falhava apagando o teste.

Clássico: o objetivo virou fazer o teste passar, não fazer o código funcionar. Rejeite.

Renomear uma variável em um arquivo, com os testes passando.

Mudança pequena, verificável e reversível.

O diff tem uma linha API_KEY = "sk-...".

Segredo no código. Volte para variável de ambiente antes de qualquer commit.

Você pediu uma tela e o agente também mexeu em 14 arquivos de configuração.

Escopo maior do que o pedido: entenda cada mudança ou desfaça.

Cola da prova

  • Vibe coding: programar descrevendo. O seu trabalho vira especificar e verificar.
  • Cursor: Tab, chat/agente, @ para contexto e rules do projeto.

Teste rápido

Pergunta 1

Onde ficam as regras de projeto do Cursor, pela documentação atual?

.cursorrules ainda funciona, mas está depreciado. O formato atual são arquivos .mdc em .cursor/rules.
Pergunta 2

Qual tipo de regra entra só quando você escreve @nome?

Manual depende de você chamar. Always entra sempre; Auto Attached por padrão de arquivo; Agent Requested pela decisão da IA.
Pergunta 3

O agente disse “todos os testes passam”. O que fazer?

Evidência vale mais que afirmação. A saída do teste mostra o que rodou e o que passou.
