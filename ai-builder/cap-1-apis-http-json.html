1O que é uma API

Todo sistema que você vai ligar nesta trilha conversa por API. Então, o que é isso?

Intuição. Pense no balcão de um cartório. Você não entra no arquivo e procura a certidão: você preenche um pedido no formato que o cartório aceita, entrega no balcão e recebe a certidão (ou um "faltou documento"). A API é esse balcão: um conjunto de pedidos que um sistema aceita, com regras sobre o formato.

Definição. API é a interface que um programa oferece para outros programas. Quase todas as APIs web usam HTTP (o mesmo protocolo do navegador) e trocam dados em JSON. Quando o n8n "busca as linhas da planilha" ou o Claude "chama uma ferramenta", por baixo está um pedido HTTP.

2A requisição e a resposta

Um pedido HTTP tem sempre as mesmas peças. Quais são, e o que cada uma diz?

PeçaO que dizExemplo
Métodoa intençãoGET ler, POST enviar dados, PUT/PATCH alterar, DELETE apagar

Cabeçalhosinformações sobre o pedidocontent-type: application/json, a chave de acesso

Os códigos que você mais vai ver: 200 ok, 201 criado, 400 pedido mal formado, 401 sem autorização (chave errada ou ausente), 403 proibido, 404 não existe, 405 método não permitido, 422 dados inválidos, 429 excesso de pedidos, 500 o servidor quebrou.

O n8n mostra 401 Unauthorized. O 4 diz que o problema é do seu lado, não do servidor.
401 especificamente é autorização: a credencial do nó está vazia, vencida ou no cabeçalho errado.

3JSON em dez minutos

Todo dado que passa entre as ferramentas é JSON. O que preciso saber para ler e montar um?

JSON tem só três ideias: objeto (chaves e valores entre { }), lista (valores em ordem entre [ ]) e valores simples (texto entre aspas, número, true/false, null). Elas se encaixam umas nas outras:

{
  "cliente": { "nome": "Ana Souza", "email": "ana@exemplo.com" },
  "pedido":  { "valor": 1500, "itens": ["teclado", "mouse"] },
  "urgente": false
}

Para chegar a um valor, você segue o caminho: cliente.nome dá "Ana Souza"; pedido.itens[0] dá "teclado" (listas contam a partir de zero). É exatamente o que você vai escrever nas expressões do n8n no próximo capítulo.

Erro comumVírgula sobrando no último item, aspas simples no lugar de duplas ou comentário dentro do JSON. Qualquer um desses torna o JSON inválido, e a API devolve 400 ou 422.

Webhook: o sistema liga para você.

4Webhook x polling

Como uma automação fica sabendo que chegou um pedido novo?

Há dois jeitos. No polling, a sua automação pergunta de tempos em tempos: "tem pedido novo?". Funciona, mas gasta execuções à toa e tem atraso. No webhook, você entrega uma URL ao outro sistema e ele faz um POST nela quando o evento acontece. É imediato e só roda quando há o que fazer. Por isso os gatilhos das ferramentas de automação preferem webhook quando o serviço oferece.

O formulário do site precisa disparar o fluxo no segundo em que o cliente clica em enviar.

Evento pontual e urgente: o formulário avisa por webhook.

Um site do governo publica uma tabela, sem nenhuma forma de aviso, e você quer saber se mudou.

Quem não oferece webhook só pode ser consultado de tempos em tempos.

O gateway de pagamento informa quando um Pix foi confirmado.

Pagamentos são o caso clássico de webhook: o gateway chama a sua URL a cada confirmação.

Uma planilha antiga, num serviço que só tem leitura pela API, recebe linhas durante o dia.

Sem evento disponível, o jeito é ler periodicamente e comparar.

Tanto o pedido quanto o webhook exigem uma chave. Onde ela mora?

Segredos: a regra que não tem exceção.

5Chaves de API e segredos

A chave de API é a sua senha para aquele serviço. Quem a vê pode gastar no seu nome.

A regra: chave nunca fica no código nem no repositório. Ela vai em uma variável de ambiente (no seu PC, num arquivo .env listado no .gitignore) ou no cofre de credenciais da ferramenta (o n8n, o Make e o Zapier têm um). O código só lê o nome da variável, como em os.environ.get("API_KEY") no exemplo do capítulo 7.

Se vazouApagar o commit não basta, porque o histórico do Git guarda a chave. O certo é revogar a chave no painel do serviço e gerar outra.

6Fechamento do capítulo

Cola da prova

  • API: o balcão de pedidos de um sistema. Quase sempre HTTP com JSON.
  • Requisição: método, URL, cabeçalhos e corpo. Resposta: status e corpo.
  • 2xx ok, 4xx erro de quem pediu (401 chave, 404 não existe, 422 dados inválidos), 5xx erro do servidor.
  • JSON: objeto {}, lista [] e valores simples. Caminho: pedido.itens[0].
  • Webhook: o sistema avisa você. Polling: você pergunta de tempos em tempos.
  • Chave em variável de ambiente ou no cofre da ferramenta. Vazou, revoga.

Teste rápido

Pergunta 1

A API respondeu 422 a um POST. O que é mais provável?

422 quer dizer que o pedido chegou e foi entendido, mas os dados não passaram na validação. Rota inexistente seria 404; servidor caído, 5xx; excesso, 429.
Pergunta 2

No JSON do capítulo, qual caminho leva a "mouse"?

A lista começa no índice 0: itens[0] é teclado e itens[1] é mouse.
Pergunta 3

Por que webhook costuma ser melhor que polling?

O webhook é disparado pelo próprio evento, sem consultas à toa. Ele ainda exige cuidado com autenticação e só existe se o serviço oferecer.
Pergunta 4

Você subiu uma chave no GitHub por engano e apagou o commit. E agora?

O histórico e as cópias já podem ter a chave. Só a revogação a torna inútil.
