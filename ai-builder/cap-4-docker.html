1O problema que o Docker resolve

"Na minha máquina funciona." Por que essa frase existe?

Um programa depende de muita coisa além dele: a versão do Python ou do Node, bibliotecas, variáveis, pastas. Na máquina de outra pessoa, qualquer diferença quebra. O Docker empacota o programa junto com tudo de que ele precisa num formato que roda igual em qualquer computador com Docker. E isola: o que roda lá dentro não bagunça o seu sistema.

2Imagem, container e volume

Qual a diferença entre o pacote e o programa rodando?

Imagem

A receita congelada: sistema mínimo, dependências e o programa. Só leitura. Ex.: n8nio/n8n, python:3.12-slim.

Container

Uma imagem rodando. Dá para ter vários containers da mesma imagem. Apagar o container apaga o que foi escrito dentro dele.

Volume

Uma pasta guardada fora do container, montada dentro dele. Sobrevive quando o container é apagado. É onde ficam dados que importam.

O que você baixa com docker pull n8nio/n8n.

Pull baixa a imagem; nada roda ainda.

Onde os seus workflows e credenciais do n8n precisam ficar para não sumirem.

Só o volume sobrevive ao container ser recriado.

O que aparece em docker ps.

docker ps lista containers em execução.

O resultado de docker build em cima de um Dockerfile.

Build produz uma imagem nova a partir da receita.

3Dockerfile e o cache de camadas

Como transformar a API do capítulo 7 numa imagem?

O Dockerfile é a receita, lida de cima para baixo. Cada instrução gera uma camada, e o Docker reaproveita as camadas que não mudaram. Por isso a ordem importa: dependências (mudam pouco) antes do código (muda sempre).

# Imagem da API de triagem (apostila de AI Builder, cap. 4).
# Construir:  docker build -t triagem .
# Rodar:      docker run --rm -p 8000:8000 -e API_KEY=minha-chave triagem
FROM python:3.12-slim

WORKDIR /app

# Primeiro só as dependências: se o código mudar e elas não, o Docker reaproveita esta camada.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Depois o código.
COPY api.py .

EXPOSE 8000
CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]

Este Dockerfile está em exemplos/. Ele não foi construído aqui (a máquina onde a apostila foi feita não tinha o serviço do Docker rodando); a API que ele empacota foi testada com pytest.

Erro comumColocar COPY . . antes do pip install. Qualquer vírgula mudada no código invalida a camada e o Docker reinstala todas as dependências a cada build.

5Docker Compose: o n8n no seu PC

Como descrever o container uma vez e subir com um comando?

O Docker Compose lê um arquivo YAML com os serviços, portas, variáveis e volumes. A documentação do n8n marca o docker run como forma antiga e recomenda o Compose. O arquivo abaixo é a tradução do comando oficial; ele foi validado com docker compose config:

# n8n local com Docker Compose (apostila de AI Builder, cap. 4).
# É a tradução para Compose do comando "docker run" da documentação oficial do n8n.
# Subir:   docker compose up -d      Abrir: http://localhost:5678
# Parar:   docker compose down       (os fluxos ficam guardados no volume n8n_data)
services:
  n8n:
    image: n8nio/n8n
    ports:
      - "5678:5678"
    environment:
      - GENERIC_TIMEZONE=America/Sao_Paulo
      - TZ=America/Sao_Paulo
      - N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true
    volumes:
      - n8n_data:/home/node/.n8n
    restart: unless-stopped

volumes:
  n8n_data:

6Fechamento do capítulo

Cola da prova

  • Imagem é a receita congelada; container é a imagem rodando; volume guarda dados fora do container.
  • Dockerfile: dependências antes do código, para aproveitar o cache de camadas.
  • -p 5678:5678: porta do PC, dois-pontos, porta do container.
  • Sem volume, docker compose down leva os dados junto.
  • Compose: um YAML, up -d para subir, down para parar.

Pergunta 1

Com -p 8080:5678, qual endereço abre o n8n?

A primeira porta é a do seu PC (8080); a segunda, a do container (5678), onde o n8n já escuta.
Pergunta 2

Você roda docker compose down e depois up. Os workflows continuam lá se:

Down apaga os containers. Só o que estava no volume sobrevive.
Pergunta 3

Por que o Dockerfile copia o requirements.txt antes do código?

Camadas que não mudam vêm do cache. Separar as dependências evita reinstalar tudo a cada mudança no código.
