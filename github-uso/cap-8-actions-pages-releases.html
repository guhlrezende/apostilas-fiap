1Actions: um workflow em YAML

Todo PR eu rodo os testes à mão. Dá para o GitHub fazer isso sozinho, sempre igual?

Intuição. É um robô de plantão. Você escreve uma receita (“quando alguém fizer push, rode isto numa máquina limpa”) e o GitHub executa toda vez, igual, e mostra se passou.

Definição. Um workflow é um arquivo YAML em .github/workflows/ (extensão .yml ou .yaml). Ele diz quando rodar (on), em qual máquina (runs-on) e quais passos (steps). Roda na infraestrutura do GitHub. Gatilhos comuns: push (commits enviados, com filtro por branch, tag ou caminho), pull_request (atividade em PR, com filtros) e workflow_dispatch (disparo manual). O schedule (cron) aparece na minha referência geral, mas eu não li a página dele: confira. (GitHub Docs, lidos em 10/11/2026.)

Um workflow mínimo, com permissão mínima. Conferi com um parser que o YAML é válido (1 job, 3 passos); não rodei no GitHub:

name: ci
on:
  push:
    branches: [main]
  pull_request:
permissions:
  contents: read          # o GITHUB_TOKEN so le o repositorio; eleve so o job que precisar
jobs:
  testar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6        # tag so por ser didatico; confira a versao atual
      - name: Ver os arquivos
        run: ls
      - name: Teste de exemplo
        run: echo "tudo certo"           # troque por npm test, pytest etc.
Não testado aquiNão rodei nenhum workflow. Só validei que o YAML é um YAML válido. A versão @v6 do checkout vem do exemplo oficial que li e eu não conferi se é a atual. O exemplo usa tag por ser didático, mas a lista da seção seguinte recomenda o SHA completo para actions de terceiros: confira a versão e fixe o SHA no uso real.

Para ver o resultado depois, o gh run (flags lidas na ajuda real, não rodei contra o GitHub): gh run list --branch main, gh run view ID --log-failed, gh run watch ID e gh run rerun ID. Para ver a falha, faça um passo falhar de propósito, por exemplo run: exit 1, e leia o log.

Erro comumColar um workflow da internet sem ler o que ele faz, ou subir a indentação errada do YAML. Valide sempre (o editor ajuda). E esquecer o permissions: aí o acesso do token depende do padrão do repositório ou da organização, que varia conforme a configuração (confira; a página de GITHUB_TOKEN que li não informa o padrão). Declare permissions para não depender dele.

Em secrets, nunca no YAML.

2Secrets, GITHUB_TOKEN e o que não fazer

O deploy precisa de uma chave. Coloco no YAML, só para testar?

Intuição. O YAML vai para o repositório, e o repositório pode ser público. A chave fica no cofre do GitHub, e o workflow a pede por nome na hora de rodar, sem nunca aparecer no arquivo.

Definição. Secrets são cadastrados nas configurações do repositório, em “Secrets and variables” e depois “Actions”, e nunca no YAML. Quem tem escrita no repositório consegue usá-los: use credencial de menor privilégio. Não use JSON, XML ou YAML como valor de um secret (a ocultação nos logs depende de texto exato): um secret por valor. Se um secret aparecer sem ocultação num log, apague o log e rotacione o secret. Environments com revisores obrigatórios protegem secrets de produção. O GITHUB_TOKEN é um token temporário do próprio workflow: dê só o que o job precisa com permissions, no workflow ou no job. E um ponto importante da página de gatilhos: eventos criados com o GITHUB_TOKEN geralmente não iniciam novos workflows (para evitar laços infinitos), com exceção de workflow_dispatch e repository_dispatch. (GitHub Docs, lidos em 10/11/2026.)

jobs:
  publicar:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Usar o segredo sem imprimir
        env:
          CHAVE_DE_DEPLOY: ${{ secrets.CHAVE_DE_DEPLOY }}   # vem do cofre; nunca do repositorio
        run: ./publicar.sh                                    # o script le a variavel; ninguem faz echo dela

O que a página de segurança manda evitar

  • pull_request_target ou workflow_run com checkout de código de fork não confiável: esses gatilhos rodam com privilégios e acesso a secrets, e a página diz que isso pode levar à tomada do repositório.
  • Usar ${{ github.event.pull_request.title }} direto dentro de um run:: o texto vem de fora e pode ser um comando. Passe por variável de ambiente e use aspas.
  • Runner self-hosted em repositório público: qualquer pessoa pode abrir um PR.
  • issue_comment: um workflow nesse gatilho também processa texto escrito por gente de fora (o comentário). Isso é uma ressalva minha, não lida na página de segurança: confira antes de usar texto do comentário num run: ou de dar permissão ao token.
  • Fixar uma action só pela tag, se você não confia no autor: prefira o SHA completo de 40 caracteres.

Erro comumImprimir o secret num echo para “conferir”. Pode vazar no log. E dar a um token mais permissão do que o job usa: se a ação for comprometida, o estrago cresce.

Pages, tags e releases.

3Pages, tags, releases e versionamento

Quero colocar um site no ar de graça e marcar a versão 1.0 do meu projeto. Como?

Intuição. Pages é uma vitrine automática: o GitHub pega os arquivos do site do seu repositório e os serve. A tag é uma etiqueta em um commit (“esta é a versão 1.0”). A release embrulha essa etiqueta com notas e arquivos para baixar.

Definição. Pages hospeda site estático (HTML, CSS, JS) a partir de um repositório, podendo passar por um build. Há site de usuário ou organização (repositório <usuario>.github.io, um por conta) e site de projeto (um por repositório); o endereço padrão é https://<usuario>.github.io ou https://<usuario>.github.io/<repositorio>. A fonte de publicação pode ser “Deploy from a branch” (uma branch que você escolhe, publicando a raiz / ou a pasta /docs) ou GitHub Actions com um workflow seu. A página diz que o IP do visitante é registrado por segurança. Tag é um ponteiro com nome para um commit; release é o pacote que usa uma tag, com notas, arquivos e os zips automáticos. Toda release se baseia numa tag; a página cita até 1000 arquivos por release, cada um com menos de 2 GiB. (GitHub Docs, lidos em 10/11/2026.)

Versionamento semântico (SemVer 2.0.0)

ParteQuando sobeExemplo de commit (Conventional Commits)
MAJORmuda a API de forma incompatívelfeat!: remove o parametro antigo ou rodapé BREAKING CHANGE:
MINORadiciona função compatívelfeat: adiciona exportar em CSV
PATCHcorrige bug de forma compatívelfix: corrige a media com nota zero

Versões 0.y.z são a fase inicial (qualquer coisa pode mudar); 1.0.0 declara a API pública. Tipos como docs, chore, refactor e test são aceitos sem efeito na versão. O Keep a Changelog sugere um CHANGELOG.md com seções por versão (a mais recente primeiro) e as categorias Added, Changed, Deprecated, Removed, Fixed e Security, com uma seção “Não publicado” no topo.

Exemplo resolvido: uma tag anotada, rodada de verdade
Num repositório de teste criei a tag anotada v0.1.0 e fiz push dela para o remoto bare. O git tag -n1 mostrou a mensagem e o git ls-remote --tags origin listou a tag no remoto.
Depois de um commit novo, o git describe --tags respondeu v0.1.0-1-gda5b4a8: “1 commit depois da tag v0.1.0”. É uma forma de saber em que versão você está.
A release pelo gh release create eu não criei: li só a ajuda (--title, --notes, --notes-file, --generate-notes, --draft, --prerelease, --target).
$ git tag -a v0.1.0 -m "Primeira versao demo"
$ git push -q origin v0.1.0
$ git tag -n1
v0.1.0          Primeira versao demo
$ git ls-remote --tags origin | cut -c42-
refs/tags/v0.1.0
refs/tags/v0.1.0^{}
$ git commit -qam "fix: corrige texto" ; git describe --tags
v0.1.0-1-gda5b4a8
$ gh release create v0.1.0 --title "v0.1.0" --notes-file CHANGELOG-trecho.md   # NAO rodei: criaria uma release

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Um repositório bare local recebeu a tag (o remoto foi só um caminho de pasta). Hashes, datas e caminhos mudam em cada máquina.

Laboratório: tag, release e Actions com permissão mínima

Exercícios 6 e 7 da lista. Nada aqui pede segredo real.

Tag e release. Crie a tag anotada v0.1.0 (git tag -a v0.1.0 -m "primeira versao") e envie (git push origin v0.1.0). Escreva um trecho de notas no formato Keep a Changelog (## [0.1.0], ### Added).
Publique a release com gh release create v0.1.0 --title "v0.1.0" --notes-file notas.md. Prova: a release aparece na lista de releases do repositório com as suas notas.
Faça um commit fix: pequeno, crie a tag v0.1.1 (um PATCH) e publique a release. Prova: git tag -l "v*" lista as duas.
Actions. Crie .github/workflows/ci.yml com permissions: contents: read e um job com um run: echo (ou npm test, se tiver projeto). Valide o YAML no editor antes de enviar.
Faça push e veja a execução: gh run list e gh run view --log. Prova: o job aparece como passou.
Troque um passo por run: exit 1, envie de novo e leia o erro com gh run view --log-failed. Depois volte ao passo certo. Prova: você achou a linha do log em que o passo falhou.

4Fechamento do capítulo

Cola da prova

  • Workflow = YAML em .github/workflows/: on (quando), runs-on (onde), steps (o quê). Gatilhos: push, pull_request, workflow_dispatch.
  • permissions: contents: read como padrão; eleve só o job que precisa. Secrets nunca no YAML, nunca no echo.
  • Eventos criados com o GITHUB_TOKEN geralmente não disparam novos workflows (exceto workflow_dispatch e repository_dispatch).
  • Evite pull_request_target com código de fork, título de PR direto num run: e runner self-hosted em repositório público. Prefira SHA completo para actions de terceiros.
  • Pages: site estático; fonte pode ser uma branch (raiz ou /docs) ou Actions. Release usa uma tag.
  • SemVer: MAJOR (incompatível), MINOR (nova função compatível), PATCH (correção). feat ~ MINOR, fix ~ PATCH, ! ou BREAKING CHANGE ~ MAJOR.

Teste rápido

Pergunta 1

Um workflow, usando o GITHUB_TOKEN, faz um push. Esse push dispara outro workflow?

É o que a página de gatilhos descreve.
Pergunta 2

Qual a versão seguinte a 1.4.2 se você só corrigiu um bug compatível?

Correção compatível é PATCH. Função nova compatível seria 1.5.0; mudança incompatível, 2.0.0.
Pergunta 3

Onde o valor de um secret deve ficar?

O YAML vai para o repositório. O valor fica fora dele.
Pergunta 4

Por que não usar ${{ github.event.pull_request.title }} direto dentro de um run:?

É um dos itens da página de segurança de Actions.
