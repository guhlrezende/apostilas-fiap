1Público, privado e o que “público” significa

Vou criar o repositório. Marco público ou privado, e dá para voltar atrás?

Intuição. Público é um mural na praça: qualquer um lê e copia. Privado é um armário trancado: só entra quem você der a chave. A diferença que pega: o que foi para o mural não volta, mesmo que você apague depois.

Definição. Público: qualquer pessoa na internet acessa e lê. Privado: só você, quem recebeu acesso e membros da organização com permissão. Interno existe só em organização no GitHub Enterprise Cloud, e não importa numa conta pessoal. Quem tem permissão de administrador pode mudar a visibilidade. (GitHub Docs, lido em 10/11/2026.) A regra prática é minha: tudo que vai para um repositório público já deve ser tratado como copiado por alguém (cópias, forks e caches), então senhas, tokens, .env, CPF, dados de cliente, finanças e saúde não entram.

2README e LICENSE

Um estranho abre o meu repositório. O que ele precisa ver para entender o projeto em um minuto?

Intuição. O README é a recepção: o que é isto, para que serve, como eu começo. A licença é o aviso na porta que diz o que os outros podem fazer com o seu código. Sem ela, a porta diz “não pode nada”.

Definição. O README deve trazer o essencial: o que o projeto faz, como instalar, como rodar, onde pedir ajuda e quem mantém. Documentação longa vai para uma wiki ou para docs/. O GitHub procura o README em .github/, na raiz e em docs/, nessa ordem, e mostra o primeiro que achar; conteúdo acima de 500 KiB é truncado na tela. A licença diz o que os outros podem fazer. Sem licença, o código continua protegido por direito autoral e ninguém tem permissão explícita de usar, copiar ou alterar. O guia de open source cita três licenças populares: MIT (permissiva e curta, exige manter o aviso de copyright e a licença), Apache 2.0 (permissiva, com cláusula de patentes) e GPLv3 (copyleft: quem distribui versão modificada precisa liberá-la sob a mesma licença). Compare opções em choosealicense.com. O arquivo se chama LICENSE ou LICENSE.md, e o GitHub mostra o nome da licença no topo quando a reconhece. Isto não é aconselhamento jurídico: para um caso específico, procure quem entende do assunto. (GitHub Docs e Open Source Guides, lidos em 10/11/2026.)

O .gitignore e os arquivos que organizam a comunidade.

3.gitignore, arquivos de saúde e templates

Quero que as pessoas saibam como contribuir, como reportar um problema de segurança e o que não é para subir. Onde isso fica escrito?

Intuição. É o regulamento do prédio: o que pode entrar (.gitignore diz o que não entra), como se comportar (código de conduta), como pedir mudança (CONTRIBUTING) e a quem avisar de uma falha grave (SECURITY).

Definição. O “perfil da comunidade” do GitHub confere se um repositório público tem README, CODE_OF_CONDUCT, CONTRIBUTING, LICENSE, uma política de segurança e templates de issue. Segundo a página sobre arquivos de saúde padrão, CONTRIBUTING.md, CODE_OF_CONDUCT.md e SECURITY.md podem ficar na raiz, em .github/ ou em docs/, e o GitHub procura em .github primeiro, depois na raiz, depois em docs. Os templates de issue ficam em .github/ISSUE_TEMPLATE/, em Markdown (cabeçalho com name: e about:) ou em formulário .yml (name: e description:). O template de PR é pull_request_template.md, na raiz, em docs/ ou em .github/, e só vale depois de ir para o branch padrão. (GitHub Docs, lido em 10/11/2026.) O .gitignore só vale para arquivo que o Git ainda não rastreia.

Exemplo resolvido: montando tudo isso num repositório local e conferindo
Numa pasta nova criei README.md, .gitignore (com node_modules/ e segredo.txt), um LICENSE de mentira, um template de issue em Markdown e um pull_request_template.md. Também criei um segredo.txt com um valor falso.
O git status -s listou as pastas e arquivos novos, mas não o segredo.txt: o .gitignore o escondeu. O git check-ignore -v disse qual linha da regra decidiu.
Depois do git add . e do commit, o git ls-files mostrou só os arquivos de saúde. O segredo falso ficou de fora, como queríamos.
$ mkdir -p .github/ISSUE_TEMPLATE
$ git status -s
?? .github/
?? .gitignore
?? LICENSE
?? README.md                         # segredo.txt NAO aparece: foi ignorado
$ git check-ignore -v segredo.txt
.gitignore:2:segredo.txt	segredo.txt   # arquivo:linha:padrao e o arquivo
$ git add . ; git commit -qm "docs: README, LICENSE, gitignore e templates"
$ git ls-files
.github/ISSUE_TEMPLATE/bug.md
.github/pull_request_template.md
.gitignore
LICENSE
README.md

## Como reproduzir

Armadilha no PowerShell 5.1. O operador > pode gravar o .gitignore em UTF-16 e o Git deixa de entender a regra. O teste completo está no capítulo 5 de Terminal e Git (seção do .gitignore). Aqui basta: grave com Set-Content -Encoding ascii (ou use o Git Bash) e confirme com git status.

Laboratório: criar o repositório de treino

Este é o exercício 1 da lista: um repositório de treino com README e licença. Nas telas do GitHub, siga o assistente deles (eu não descrevo botões).

Crie, na sua conta, um repositório público chamado treino-github, com README e a licença que você escolher depois de comparar opções (por exemplo MIT). Anote por que escolheu essa.
No seu computador, crie as pastas .github/ISSUE_TEMPLATE/ e os arquivos do exemplo acima: um template de issue e um pull_request_template.md. Crie um .gitignore com segredo.txt e confirme com git check-ignore -v segredo.txt.
Crie um segredo.txt com o texto valor falso (nunca uma credencial verdadeira) e confirme que ele não aparece no git status -s.

Prova de que deu certo: o git ls-files lista os arquivos de saúde e não lista o segredo.txt. Quando você enviar (capítulo 3), a página do repositório mostra o nome da licença no topo.

4Fechamento do capítulo

Cola da prova

  • Público: qualquer um lê, e o que foi publicado não volta. Privado: só quem recebeu acesso.
  • README: o que é, como instalar, como rodar. Sem licença, ninguém tem permissão explícita de usar o código. MIT e Apache 2.0 são permissivas; GPLv3 é copyleft. Isto não é aconselhamento jurídico.
  • CONTRIBUTING, CODE_OF_CONDUCT e SECURITY ficam na raiz, em .github/ ou em docs/ (a busca começa por .github). Templates de issue: .github/ISSUE_TEMPLATE/.
  • .gitignore só vale para arquivo ainda não rastreado. No PowerShell 5.1 limpo, > pode gravar UTF-16 e quebrar a regra: use Set-Content -Encoding ascii.
  • git check-ignore -v arquivo diz qual regra decidiu.

Teste rápido

Pergunta 1

Um repositório público não tem arquivo LICENSE. O que isso significa para quem quer usar o código?

Sem licença, ninguém recebeu permissão. A licença é o que diz o que os outros podem fazer.
Pergunta 2

Você já fez commit de um segredo.txt e agora o põe no .gitignore. O que acontece?

O .gitignore só vale para arquivos ainda não rastreados. Para o histórico, veja o capítulo 9.
Pergunta 3

Onde o GitHub procura o CONTRIBUTING.md, segundo a página de arquivos de saúde?

As três pastas valem, com essa ordem de busca.
Pergunta 4

Qual comando mostra qual linha do .gitignore decidiu ignorar um arquivo?

O -v mostra o arquivo, o número da linha e o padrão que casou. O git ls-files só lista o que já é rastreado.
