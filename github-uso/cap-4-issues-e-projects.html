1Issue, label, milestone e assignee

Tenho dez coisas para fazer no projeto, anotadas em cinco lugares. Como junto tudo e ainda deixo claro quem faz o quê?

Intuição. A issue é uma ficha de tarefa afixada no mural do projeto: tem número, título, conversa e responsável. Cada ficha é uma coisa só (um bug, uma ideia, uma tarefa), e dá para pesquisar e fechar.

Definição. Issue: item para registrar e discutir trabalho, com número (#123). Label: etiqueta colorida (bug, documentação). Milestone: marco com prazo que agrupa issues e PRs. Assignee: quem está responsável. A página oficial também cita sub-issues (hierarquia de tarefas dentro de uma issue maior). Discussions é outra coisa: conversa aberta, sem item de trabalho; serve para perguntas, anúncios e enquetes, e pode virar issue quando vira trabalho. O administrador precisa habilitar. (GitHub Docs, lido em 10/11/2026.)

2#123, Closes #123 e a regra do branch padrão

Escrevi “Closes #7” no PR e a issue não fechou. O que faltou?

Intuição. É uma etiqueta que o GitHub lê: “quando esta mudança entrar na pista principal, dê a ficha por resolvida”. Se a mudança entrar numa pista lateral, a etiqueta não dispara.

Definição. Escrever #123 em outra issue ou PR cria um link entre eles. As palavras que fecham a issue quando o PR entra são close, closes, closed, fix, fixes, fixed, resolve, resolves e resolved, como em Closes #123 ou Fixes dono/repo#100. A palavra só vale quando o PR tem como destino o branch padrão. Em outro destino, nada acontece. Para desfazer o vínculo automático, edite a descrição do PR e tire a palavra. (GitHub Docs, lido em 10/11/2026.)

Exemplo resolvido: o Git guarda a frase, mas quem interpreta é o GitHub
Fiz um commit com a mensagem docs: README, LICENSE, gitignore e templates (Closes #7) num repositório local.
O git log mostrou a frase inteira, como qualquer texto. Localmente nada fecha nem liga: não existe issue 7 no meu computador.
No GitHub, a palavra-chave é lida na descrição do PR e (segundo a documentação) também nos commits, quando o PR vai para o branch padrão. Eu não testei isso no site.
$ git commit -qm "docs: README, LICENSE, gitignore e templates (Closes #7)"
$ git log -1 --format='%s'
docs: README, LICENSE, gitignore e templates (Closes #7)    # so texto: quem le e o GitHub

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Foi um repositório local, sem remoto. Hashes, datas e caminhos mudam em cada máquina.

Não testado aquiO fechamento automático da issue só acontece no GitHub. Para confirmar, no seu repositório de treino abra uma issue de teste, escreva Closes #1 num PR para a main e veja a issue fechar quando o PR entrar (laboratório abaixo).
Erro comumAbrir o PR para uma branch que não é a padrão (por exemplo develop) com Closes #123 e esperar que a issue feche. Nesse destino, nada acontece. Outro: confundir #123 de issue com #123 de PR: os dois usam a mesma numeração no repositório.

3Projects: tabela, quadro e roadmap

Tenho vinte issues abertas. Quais atacar primeiro, e quem está parado onde?

Intuição. Se a issue é a ficha, o Project é o quadro na parede onde você pendura as fichas em colunas (a fazer, fazendo, feito) ou as lista numa tabela com prazo e prioridade.

Definição. Projects oferece visões de tabela, quadro (kanban) e roadmap sobre issues e PRs, com campos personalizados (a página lida cita até 50 por projeto). O quadro lê as issues; mover o cartão atualiza o campo de status. (GitHub Docs, lido em 10/11/2026.)

Erro comumMontar um quadro bonito e nunca olhar. Quadro que ninguém atualiza é pior que nenhum: dá falsa sensação de organização. Comece com três colunas e só acrescente quando precisar.

Laboratório: uma issue de ponta a ponta

Prepara o exercício 3 do capítulo 5: você precisa de uma issue de teste.

No treino-github, crie duas labels (por exemplo bug e documentação) e um milestone com uma data próxima. Anote o nome de cada.
Abra uma issue de teste com título claro e uma frase de descrição, com a label e o milestone. Ela deve ter o número #1 (se não tiver, anote o número que apareceu e use ele no capítulo 5).
Atribua a issue a você mesmo (no terminal, --assignee @me na criação; no site, o campo de responsável).
Crie um Project (tabela ou quadro) e adicione a issue. Mova o cartão de coluna e observe o campo de status.
Prova de que deu certo: gh issue list mostra a issue com label e responsável, e o Project mostra o mesmo cartão. Se você usou o gh, nenhum token apareceu na tela.

4Fechamento do capítulo

Cola da prova

  • Issue = ficha de trabalho com número. Label classifica, milestone agrupa com prazo, assignee é o responsável. Discussion é para conversa sem tarefa.
  • #123 cria link. Closes #123 (ou fix, resolve) fecha a issue, mas só quando o PR vai para o branch padrão.
  • O Git guarda a frase como texto; quem interpreta é o GitHub.
  • Projects: tabela, quadro e roadmap sobre issues e PRs, com campos personalizados.
  • Poucas labels, claras. Quadro só vale se alguém atualiza.
