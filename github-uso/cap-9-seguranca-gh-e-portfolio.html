1Secret scanning, push protection e Dependabot

O GitHub avisa sozinho quando eu subo uma chave por engano?

Intuição. É um vigia com lista de padrões: ele conhece o jeito de uma chave de API ou de um token e grita quando vê um igual num commit. O Dependabot é outro vigia, que olha as bibliotecas que o seu projeto usa e avisa quando alguma tem falha conhecida.

Definição. Secret scanning procura credenciais (chaves de API, tokens, senhas) no histórico completo de todas as branches e também em issues, PRs, discussões, wikis e gists secretos. Em repositório público, roda automaticamente e de graça; em privado exige o GitHub Secret Protection (planos Team ou Enterprise Cloud, segundo a página). Push protection bloqueia o push de uma credencial detectada, vem ativado por padrão em repositório público, e se alguém contorna o bloqueio, gera um alerta. Credenciais de provedores parceiros são avisadas ao provedor quando o vazamento é público. Dependabot: alertas de vulnerabilidade em dependências, security updates (PR com a correção) e version updates (PR para manter dependências atualizadas, com um .github/dependabot.yml criado ao ativar). A página de segurança que li diz que esses três estão em todos os planos. (GitHub Docs, lido em 10/11/2026.) A página do guia rápido do Dependabot não traz o exemplo mínimo do arquivo (ela só diz que o GitHub cria um dependabot.yml em /.github), então o exemplo abaixo é ilustrativo: confira as opções na página de referência do Dependabot.

# .github/dependabot.yml  (exemplo ILUSTRATIVO; confira a pagina de opcoes do Dependabot)
version: 2
updates:
  - package-ecosystem: "github-actions"   # mantem as actions do workflow atualizadas
    directory: "/"
    schedule:
      interval: "weekly"
Não testado aquiSecret scanning, push protection e Dependabot não foram testados: dependem do site e de um repositório real. Não tente disparar um alerta com uma credencial verdadeira nem com o token de teste de um serviço: o sistema reconhece padrões reais.
Erro comumConfiar só no scanner. Ele pega padrões conhecidos, e pega depois que o dado já foi enviado. A defesa é não pôr segredo no repositório em primeiro lugar.

2Vazou um segredo: a ordem certa

Commitei uma chave. Apago o commit e acabou?

Intuição. É uma carta com a senha que você já postou. Rasgar o rascunho em casa não a tira da caixa do correio, e quem pegou a carta continua com a senha. O que fecha a porta é trocar a fechadura (revogar a chave), não esconder a carta.

Definição. A ordem, segundo a página oficial de remoção de dados sensíveis e a de expiração de tokens (lidas em 10/11/2026): 1. revogar ou rotacionar a credencial agora (é a única ação que impede o uso do segredo); 2. verificar se alguém usou, nos logs do serviço; 3. avisar quem tem clone antigo, antes de reescrever nada, porque um git pull seguido de git push pode reintroduzir o dado; 4. só depois, se preciso, limpar o histórico com git filter-repo (a página cita versão mínima 2.47; exemplo da página: git filter-repo --invert-paths --path ARQUIVO e depois git push --force --mirror origin). Pré-condições (são minhas e de bom senso, não testei esses comandos): faça num clone novo, com um backup antes, e avise o time antes, porque o --mirror reescreve todas as refs (branches e tags) e muda os hashes de todo mundo; 5. saber que limpar o histórico não basta: clones, forks, caches e PRs que citam o commit continuam com o dado, e remover de vez exige acionar o GitHub Support. Se o que vazou é dado pessoal em repositório público, a limpeza deixa de ser opcional (o dado não se revoga): a ordem é remover as cópias que você controla, avisar, limpar e acionar o suporte. A página de expiração diz que um token enviado a repositório público é revogado automaticamente, e mesmo assim você troca a credencial.

Exemplo resolvido: o segredo continua no histórico (rodado, com valor falso)
Criei um arquivo com o valor falso CHAVE_FALSA_123, fiz o commit “sem querer”, depois pus o arquivo no .gitignore, rodei git rm --cached e fiz um segundo commit. O git status ficou limpo e o git ls-files só lista o .gitignore: parece resolvido.
O git log --all --oneline -S CHAVE_FALSA_123 listou 2 commits que mexeram nessa string, e o git show HEAD~1:segredo.txt imprimiu a chave. O valor segue legível no commit anterior.
Moral: git rm --cached e .gitignore impedem o próximo vazamento. Só revogar impede o uso do que já vazou.
$ echo "CHAVE_FALSA_123" > segredo.txt ; git add . ; git commit -qm "sem querer"
$ printf 'segredo.txt
' > .gitignore ; git rm -q --cached segredo.txt     # Git Bash
$ git add .gitignore ; git commit -qm "tira do rastreio"
$ git status --short                       # vazio: parece que acabou
$ git ls-files
.gitignore
$ git log --all --oneline -S CHAVE_FALSA_123
386bd13 tira do rastreio
7433788 sem querer
$ git show HEAD~1:segredo.txt
CHAVE_FALSA_123                            # continua ali, no commit anterior

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Foi um repositório local, sem remoto. Hashes, datas e caminhos mudam em cada máquina.

Os comandos acima são de Git Bash. No PowerShell 5.1, o > pode gravar o .gitignore em UTF-16 e o segredo continuaria aparecendo no git status (vi isso numa rodada e o capítulo 5 de Terminal e Git (seção do .gitignore) mostra): lá, use Set-Content -Encoding ascii.

Não testado aquiNão rodei git filter-repo, nem git push --force, nem pedi nada ao GitHub Support. O que digo sobre limpar o histórico vem da página oficial; o que eu rodei foi a prova de que o histórico guarda o valor.
Erro comumRodar git rm --cached, ou apagar o commit, e considerar resolvido sem revogar. Quem clonou antes, um robô que varre repositórios públicos ou um fork continuam com a chave. Sem o passo 1, a chave segue valendo. E reescrever o histórico sem avisar o time pode atrapalhar todo mundo.

3O gh no terminal

Abrir o navegador para cada PR e cada issue cansa. Dá para fazer pelo terminal?

Intuição. O gh é o controle remoto do GitHub no seu terminal. Você faz ali o que faria nos botões do site.

Definição. O gh é o GitHub CLI (gh --version na minha máquina: 2.101.0). Grupos principais do manual: gh auth, gh repo, gh pr, gh issue, gh run, gh release e gh api. A ajuda abaixo é real, rodada nesta máquina, sem chamar a API. O gh auth status mostra a conta e os escopos: não cole a saída em chat. E o gh api com -X POST, PUT ou DELETE altera o GitHub: não use sem saber o que vai mudar.

4Erros comuns e como se recuperar

Fiz besteira no Git. Perdi trabalho?

Intuição. O Git quase nunca perde nada de verdade: guarda um diário (o reflog) de onde a sua branch esteve. O que dá medo é a rapidez com que dá para errar; a recuperação costuma ser curta.

Definição. Os erros abaixo eu reproduzi num repositório de teste, com saída real. As correções que reescrevem histórico ou descartam trabalho (reset --hard) só use quando tiver certeza de que nada se perde.

5Portfólio: perfil, README e o que mostrar

Quero que o meu perfil mostre o que sei fazer. O que vale pôr ali?

Intuição. O perfil é a sua vitrine, e o que está nela é público. Uma vitrine com poucas peças bem cuidadas diz mais que uma cheia de caixas vazias.

Definição. O README de perfil é um repositório público com o mesmo nome do seu usuário, com um README.md na raiz: o GitHub o mostra no seu perfil. Repositórios criados antes de julho de 2020 não aparecem sozinhos (use “Share to profile”, segundo a página). A página não diz quantos repositórios podem ser fixados (pins): confira. Não há fonte oficial lida que diga o que recrutadores olham, e nada garante vaga por causa de commits ou PRs. O que dá para afirmar é que o perfil mostra repositórios públicos, o README de perfil e a atividade pública. Minhas sugestões (não são de fonte oficial): projetos reais com README que ensina a rodar, commits com mensagem clara, PRs em projetos de terceiros com a resposta às revisões, licença e .gitignore corretos, e nada de segredo, dado pessoal ou cópia de projeto de outra pessoa sem autorização.

Só no seu repositório de treinoFaça tudo num repositório seu (por exemplo treino-github), na sua conta. Não use credencial real como exemplo, não suba dado pessoal e não faça push para repositório de outras pessoas. Laboratório: secret scanning, vazamento simulado e gh

Segunda metade do exercício 8, mais um treino de vazamento local. Em nenhum passo use credencial real ou de teste de um serviço.

No treino-github, confira nas configurações de segurança o que está ligado (secret scanning, push protection, Dependabot alerts). Anote o que viu e o que depende do plano (confira, sem supor).
Crie um arquivo teste-segredo.txt com o texto valor falso, nao e credencial (algo que não imite nenhum formato de token) e dê push. Prova: o push não é bloqueado, porque não casa com nenhum padrão de credencial. Não tente simular um token.
Vazamento local. Numa pasta temporária, repita o experimento do capítulo: commit de um arquivo com CHAVE_FALSA_123, depois git rm --cached e novo commit. Prova: git log --all --oneline -S CHAVE_FALSA_123 lista dois commits.
Abra a demo “vazou um segredo” e percorra os cinco tipos de segredo. Anote, para cada um, qual é o passo 1.
gh. Rode gh pr create --help e gh run list --help e liste, no seu caderno, três flags que você usaria. Não rode gh api com POST, PUT ou DELETE.
Monte o README de perfil (repositório com o seu usuário) com só o que é verdade. Prova: aberto numa janela anônima, o perfil mostra o README e nenhum dado pessoal que você não quis publicar.

6Fechamento do capítulo

Cola da prova

  • Secret scanning (de graça em repositório público) e push protection (bloqueia push de credencial detectada) ajudam, mas agem depois ou só em padrões conhecidos. Dependabot: alertas, security updates e version updates.
  • Vazou? 1. revogar ou rotacionar; 2. ver se foi usada; 3. avisar o time; 4. limpar o histórico com git filter-repo (opcional, exceto dado pessoal em repositório público), num clone novo e com backup; 5. limpar não basta (clones, forks, caches). Apagar o commit não é o passo 1.
  • git rm --cached e .gitignore não removem o segredo do histórico: o git log -S o acha.
  • gh: pr, issue, repo, run, release, auth, api. gh api com POST, PUT ou DELETE altera o GitHub de verdade. --admin no merge é bypass.
  • Recuperação: git reflog acha o commit; git branch nome hash o devolve; git revert -m 1 desfaz um merge; pull --ff-only falha com divergência.
  • Perfil: README com o mesmo nome do usuário; nenhuma promessa de emprego; nada de segredo nem dado pessoal.
