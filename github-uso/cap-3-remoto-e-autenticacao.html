1Remoto, origin, main, clone e fork

Quando eu digito git push sem dizer para onde, para onde vai?

Intuição. O remoto é um contato salvo no celular: um apelido para o endereço de outro repositório. O apelido padrão é origin (de “origem”, o lugar de onde você clonou). Clonar é fotocopiar o caderno do outro. Fazer fork é fotocopiar o caderno dentro do prédio, na sua estante, para você poder mexer sem pedir licença.

Definição. Remoto: apelido para outro repositório; git remote -v mostra as URLs. Clone: cópia para o seu PC; você só consegue dar push se tiver permissão de escrita nele. Fork: cópia do repositório na sua conta do GitHub; você dá push no seu fork e abre um PR para o original, que se chama upstream. É assim que se contribui com projeto de terceiros (capítulo 6). main é o nome da branch padrão de projetos novos: o GitHub passou a criar repositórios com main a partir de 1º de outubro de 2020 (isso eu li em fonte secundária, não no blog oficial, então trate como informação a confirmar). Repositórios antigos não mudam sozinhos. Para o seu Git local criar main em repositórios novos, use git config --global init.defaultBranch main. (GitHub Docs e Pro Git, lidos em 10/11/2026.)

$ git clone https://github.com/seu-usuario/seu-repo.git        # NAO testado aqui (depende do GitHub)
$ git remote -v
$ git remote add upstream https://github.com/dono-original/repo.git
Exemplo resolvido: conectar um repositório novo a um remoto e enviar
Criei um repositório bare (nuvem.git, o papel do GitHub), um projeto com git init -b main e adicionei o remoto: git remote add origin ../nuvem.git.
git push -u origin main enviou e guardou o vínculo (o -u): depois disso, git push e git pull sem argumentos sabem para onde ir.
git branch -vv mostrou [origin/main] ao lado da main: é o vínculo registrado.
$ git init -q -b main projeto ; cd projeto
$ git remote add origin ../nuvem.git
$ git remote -v
origin	../nuvem.git (fetch)
origin	../nuvem.git (push)
$ git push -u origin main
To ../nuvem.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git branch -vv
* main f76f8cc [origin/main] docs: cria README e .gitignore

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Um repositório bare local (../nuvem.git) fez o papel do GitHub; o colega foi um segundo clone dele. Hashes, datas e caminhos mudam em cada máquina.

Erro comumClonar o repositório de outra pessoa e tentar dar push nele. Sem permissão de escrita, o push falha. O caminho é fork + PR. Outro erro: origin apontando para o lugar errado (o original em vez do seu fork); confira com git remote -v e corrija com git remote set-url origin URL.

2fetch, pull, push e a divergência

Um colega enviou um commit enquanto eu fazia o meu. O que acontece quando eu tento sincronizar?

Intuição. fetch é olhar a caixa de correio sem abrir as cartas dentro de casa: você vê o que chegou, e seus arquivos não mudam. pull é buscar e já misturar na sua branch. push é entregar o que você fez.

Definição. git fetch baixa o que mudou no remoto e atualiza origin/main, sem tocar nos seus arquivos. git pull faz fetch e depois merge (ou rebase, se configurado) na sua branch. git push envia seus commits. Quando os dois lados andaram, a história diverge: o push é recusado (non-fast-forward) e o pull --ff-only falha, porque não dá para só avançar. Aí você escolhe, de propósito, merge ou rebase.

Exemplo resolvido: a divergência, rodada de verdade
Tenho 1 commit local que ainda não enviei. O colega (um segundo clone) envia 1 commit. O git fetch trouxe origin/main novo e o git status -sb mostrou [ahead 1, behind 1]: um à frente, um atrás.
O git pull --ff-only falhou com fatal: Not possible to fast-forward, aborting.: o histórico divergiu, então só avançar é impossível.
O git pull --no-rebase --no-edit funcionou: criou um commit de merge. Em outra rodada, meu git push foi recusado com ! [rejected] ... (fetch first) porque o colega tinha enviado antes. A saída é sempre buscar, integrar e enviar de novo.

$ git status -sb | head -1
## main...origin/main [ahead 1, behind 1]
$ git pull --ff-only

hint:
hint: 	git merge --no-ff
hint:
hint: or:
hint:
hint: 	git rebase

$ git pull --no-rebase --no-edit

$ git push origin main                          # numa segunda rodada em que o colega enviou antes

Erro comumTratar --force como a saída do push recusado. Forçar sobrescreve o histórico dos outros. A saída certa é git fetch, integrar (merge ou rebase) e fazer push de novo. E confundir fetch com pull: fetch é seguro para só olhar; o pull altera a sua branch.

3Autenticação: token, SSH, gh e o que nunca colar

Digitei a senha da minha conta no git push e deu erro. Por quê?

Intuição. Senha de conta é uma chave-mestra: se ela vazasse num comando, abriria tudo. Então o GitHub passou a pedir chaves específicas para o Git: um token (que você pode limitar e revogar), um par de chaves SSH ou o login do gh.

Definição. Desde 13 de agosto de 2021 o GitHub.com não aceita a senha da conta para operações Git: é preciso token de acesso (por exemplo, um token pessoal), chave SSH ou token de instalação de app. (Changelog do GitHub, lido em 10/11/2026.) Os tokens têm prefixos: ghp_ (pessoal clássico) e github_pat_ (fine-grained). A página de expiração recomenda definir validade; token sem uso por um ano é revogado; dá para revogar a qualquer hora; token enviado por push a repositório público é revogado automaticamente. No SSH, a chave privada fica no seu PC (use senha de chave) e a pública vai para a conta; chave sem uso por um ano é removida. A página não diz qual tipo de chave o GitHub recomenda: Ed25519 é prática comum, mas confira. O Git Credential Manager (credential.helper manager) guarda as credenciais no cofre do Windows.

FormaComo funcionaQuando usar
HTTPS com tokeno Git pede usuário e um token no lugar da senha; o gerenciador guarda no cofreo caminho mais simples no Windows
SSHpar de chaves: privada no seu PC, pública cadastrada na contaquem já usa SSH e não quer digitar token
gh auth logino gh faz o login e configura o Git para usar o mesmoquem usa o gh: o caminho menos manual
Exemplo resolvido: gerar um par de chaves descartável, sem cadastrar em lugar nenhum
No Git Bash: ssh-keygen -t ed25519 -f chave-descartavel -N "" -C teste criou o par. O arquivo .pub é a chave pública (começa com ssh-ed25519) e é a única que sai do PC.
No PowerShell 5.1 uma string vazia some ao chegar no programa nativo: o -N "" precisa virar -N '""'. Com isso funcionou também.
Eu não cadastrei a chave e não rodei ssh -T contra o GitHub.
$ ssh-keygen -t ed25519 -f chave-descartavel -N "" -C teste

Your public key has been saved in chave-descartavel.pub
$ cut -c1-12 chave-descartavel.pub

PS> ssh-keygen -t ed25519 -f chave-ps -N '""' -C teste      # no PS 5.1, a string vazia precisa dessas aspas

O que o Git grava quando você põe o token dentro da URL do remoto (com um valor falso, claro):

$ git remote add origin https://usuario:TOKEN_FALSO_AQUI@github.com/seu-usuario/repo.git
$ grep url .git/config
	url = https://usuario:TOKEN_FALSO_AQUI@github.com/seu-usuario/repo.git    # em texto puro, no disco
$ git remote set-url origin https://github.com/seu-usuario/repo.git         # a correcao
$ grep url .git/config
	url = https://github.com/seu-usuario/repo.git

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. A chave SSH foi descartável e não foi cadastrada em lugar nenhum; o token da URL era falso e o repositório não tinha remoto real. Hashes, datas e caminhos mudam em cada máquina.

O que NUNCA colar, em chat, repositório ou URL
  • A senha da conta.
  • Um token (ghp_, github_pat_, gho_...). Se colou, revogue antes de qualquer coisa.
  • A chave privada SSH (o arquivo sem .pub).
  • Um código de recuperação do 2FA.
  • O token dentro da URL do remoto: ele fica em .git/config e no histórico do shell.
  • Variável de ambiente com segredo em arquivo do repositório.
Se um token apareceu em conversa ou em arquivo commitado, a ordem é: revogar, gerar outro, guardar no gerenciador. Só depois, se for o caso, limpar histórico (capítulo 9).

Erro comumColar o token no lugar da senha “para ver se vai” e depois deixá-lo no histórico do terminal. Ou receber Permission denied (publickey) e achar que o GitHub caiu: normalmente a chave pública não foi cadastrada, ou a chave certa não está carregada no ssh-agent.

4Fechamento do capítulo

Cola da prova

  • origin é o apelido do remoto de onde você clonou. git remote -v mostra; git push -u grava o vínculo.
  • Clone: cópia no PC. Fork: cópia na sua conta do GitHub, para contribuir com o que não é seu. O original é o upstream.
  • fetch só olha; pull = fetch + merge; push envia. Histórico divergente: pull --ff-only falha, e o push é recusado. Resolva com merge ou rebase, não com --force.
  • Desde 13/08/2021 senha de conta não vale para o Git: token, SSH ou gh. No PowerShell 5.1, -N '""' para senha de chave vazia.
  • Nunca colar token, chave privada, senha ou código de recuperação em chat, repositório ou na URL do remoto. Vazou: revogar primeiro.

Pergunta 1

Você tem commits locais e o colega enviou outro. O que o git pull --ff-only faz?

O --ff-only só aceita avançar. Com divergência, ele recusa e você escolhe merge ou rebase.

Qual comando atualiza origin/main sem mexer nos seus arquivos?

O fetch só baixa. O pull baixa e integra.
