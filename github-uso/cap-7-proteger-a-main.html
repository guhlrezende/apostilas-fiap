1Por que não commitar direto na main em equipe

Se eu confio nas pessoas do time, por que trancar a main?

Intuição. A main é o que todo mundo usa e o que vai para o ar. Um erro nela vira problema de todos na hora, sem ninguém ter olhado. Trancar a porta não é desconfiar de ninguém: é garantir que uma segunda pessoa e os testes passem antes.

Definição. Com proteção, a main só recebe mudança por PR aprovado e com checks passando. A página de branches protegidas diz que as regras podem bloquear o merge quando os requisitos não são atendidos. (GitHub Docs, lida em 10/11/2026.)

Exemplo resolvido: uma analogia local: um remoto que recusa push direto na main
Como eu não podia ligar a proteção do GitHub, montei uma analogia: um repositório bare com um hook pre-receive que recusa pushes na main depois do primeiro. Não é a mesma coisa que a proteção do GitHub, mas mostra a ideia de um servidor que diz não.
O primeiro push da main passou (era a criação). O segundo, direto na main, foi recusado com pre-receive hook declined.
O push de uma branch feature/ok passou normalmente: o caminho do trabalho é a branch, e a main só muda depois (pelo PR).
$ git push origin main                       # segundo push direto na main
remote: main protegida: abra um pull request
To ../prot.git
 ! [remote rejected] main -> main (pre-receive hook declined)
error: failed to push some refs to '../prot.git'
$ git switch -c feature/ok ; git push -u origin feature/ok     # a branch passa
 * [new branch]      feature/ok -> feature/ok
$ git branch -vv
* feature/ok 5eea15b [origin/feature/ok] c2
  main       5eea15b [origin/main: ahead 1] c2

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Um repositório bare local (../prot.git) com um hook pre-receive fez o papel do servidor. Hashes, datas e caminhos mudam em cada máquina.

Não testado aquiA proteção de verdade do GitHub eu não testei. O hook acima é só uma analogia de um servidor que recusa o push, e a mensagem do GitHub é diferente.
Erro comumAchar que proteção resolve tudo. Ela só obriga o processo: quem aprova ainda precisa olhar o código. E liberar sempre o bypass para administradores: anula a regra.

Proteção de branch clássica e rulesets.

2Proteção de branch e rulesets

Quais as travas que posso ligar na main, e quais valem em qualquer plano?

Intuição. Cada regra é uma tranca separada: exigir PR, exigir uma aprovação, exigir testes verdes, exigir conversas resolvidas, impedir force push. Você liga as que fazem sentido para o time.

Definição. A página de branches protegidas (lida em 10/11/2026) lista: exigir PR antes do merge, com número mínimo de aprovações (revisores com permissão de escrita ou code owners); Request changes bloqueia o merge até ser resolvido; descartar aprovações antigas quando novos commits mudam o diff; status checks obrigatórios (modo strict exige a branch atualizada com a base, o loose não exige); exigir aprovação de code owners; exigir conversas resolvidas; force push e exclusão da branch bloqueados por padrão. Por padrão, as regras não valem para administradores; existe a opção “Do not allow bypassing the above settings”. Rulesets são listas nomeadas de regras para branches e tags: vários podem valer ao mesmo tempo, dá para desativar sem apagar, quem tem leitura vê os ativos e, em conflito, vale a mais restritiva; também controlam mensagem de commit e e-mail do autor, e o limite citado é 75 rulesets por repositório e por organização.

Disponibilidade por plano: confiraA página de rulesets diz que estão nos planos Team e Enterprise. A página de planos não os lista para conta pessoal Free ou Pro. A página de proteção que reli em 10/11/2026 só menciona plano para duas funções: restringir quem pode dar push (em repositórios públicos de uma organização Free e em todos os de organizações Team ou Enterprise Cloud) e listas de bypass (só em repositórios de organização). Ela não diz se a proteção clássica ou os rulesets funcionam num repositório pessoal gratuito, e eu não testei. Antes de contar com uma regra, olhe a tela de configuração do seu repositório e a página de planos.
Exemplo resolvido: lendo a demo
Com as regras iniciais (1 aprovação, checks obrigatórios, conversas resolvidas) e o PR sem aprovação, o veredito é bloqueado, com a lista do que falta.
Aprove, faça os checks passarem e resolva as conversas: o veredito vira liberado.
Ligue “aprovação antiga é descartada com novo commit”, marque que houve um novo commit e a aprovação some: bloqueado de novo.
Marque “sou administrador” com a regra “não permitir bypass” desligada: o merge é liberado mesmo sem cumprir as regras (a página diz que, por padrão, a regra não vale para admin). Ligue o “não permitir bypass” e ele volta a bloquear.
Não testado aquiA demo aplica as regras como a documentação as descreve. Eu não ativei proteção nem ruleset em nenhum repositório real, e o comportamento exato (por exemplo, se o autor pode aprovar o próprio PR) depende da configuração: confira.
Erro comumExigir um check com nome que não existe mais: o PR fica esperando para sempre. E exigir aprovação de uma só pessoa no time de uma pessoa: ninguém consegue fazer merge.

Com o CODEOWNERS.

3CODEOWNERS: quem é dono de cada pedaço

O time tem uma pessoa que cuida do front e outra do banco. Como o GitHub pede revisão a quem entende?

Intuição. É uma tabela “pasta, dono” na porta do arquivo. Quando um PR mexe numa pasta, o GitHub chama quem aparece como dono dela.

Definição. O arquivo CODEOWNERS fica em .github/, na raiz ou em docs/ (usa o primeiro que achar) e precisa estar na branch base do PR para pedir revisão. Até 3 MB. A sintaxe parece a do .gitignore, mas sem !, sem intervalo [ ] e sem escapar #. Vários donos na mesma linha; vence a última regra que casa com o caminho, então as gerais (*) vão no começo e as específicas embaixo. Os donos precisam ter permissão de escrita explícita no repositório. Um PR em draft não pede revisão automática a code owners. (GitHub Docs, lido em 10/11/2026.)

# .github/CODEOWNERS  (exemplo ilustrativo, NAO testado aqui)
*           @seu-usuario              # regra geral, no comeco
/docs/      @seu-usuario
*.yml       @seu-usuario              # a ultima regra que casa vence
Não testado aquiO CODEOWNERS não foi testado: ele depende do site para pedir a revisão. O exemplo usa um nome de usuário de mentira.
Erro comumColocar no CODEOWNERS um usuário sem permissão de escrita: a regra não pega e ninguém é avisado. Ou pôr uma regra geral no fim do arquivo, que passa por cima de todas as específicas (a última que casa vence).

4Fechamento do capítulo

Cola da prova

  • Proteger a main = obrigar PR, revisão e checks antes do merge. É processo, não confiança.
  • Regras clássicas: PR obrigatório, número de aprovações, descartar aprovação antiga, checks obrigatórios (strict ou loose), code owners, conversas resolvidas, sem force push, sem apagar a branch. Admin escapa por padrão.
  • Rulesets: vários ao mesmo tempo, dá para desativar, vale a mais restritiva. Disponibilidade por plano: confira (a página lida não fecha o caso do repositório pessoal gratuito).
  • CODEOWNERS: .github/, raiz ou docs/; na branch base; última regra que casa vence; donos com permissão de escrita.
  • Hook pre-receive local: analogia de servidor que recusa push, não é o GitHub.
