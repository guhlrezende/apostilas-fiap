1GitHub Flow: branch curta, PR, revisão, merge

Num projeto com mais de uma pessoa, qual é o caminho de uma mudança até a main?

Intuição. A main é a versão “oficial” do livro. Você não rabisca nela: tira uma cópia (branch), escreve na cópia, mostra o rascunho para alguém ler (pull request) e só quando aprovado a mudança entra no original.

Definição. A página oficial do GitHub Flow lista seis passos: (1) criar uma branch com nome curto e descritivo; (2) fazer a alteração, em commits com mensagem descritiva e, de preferência, uma mudança isolada e completa, e dar push; (3) abrir o PR com resumo, problema resolvido e issues ligadas (pode ser draft se você quer feedback antes); (4) responder aos comentários com novos commits (o PR se atualiza sozinho); (5) fazer o merge depois da aprovação, sem conflitos e respeitando as regras de proteção; (6) apagar a branch depois do merge. A página não diz qual é o nome do branch padrão; aqui assumo main. (GitHub Docs, lido em 10/11/2026.)

$ git switch main
$ git pull --ff-only                       # so avanca; falha se divergiu
$ git switch -c feature/titulo-curto
# ... edita, testa ...
$ git add arquivo.ext
$ git commit -m "feat: descreve a mudanca"
$ git push -u origin feature/titulo-curto
$ gh pr create --draft --fill              # NAO rodei contra o GitHub: abriria um PR
# quando estiver pronto:
$ gh pr ready
$ gh pr checks
$ gh pr merge --squash --delete-branch
Não testado aquiOs comandos gh pr acima não foram rodados contra o GitHub. As flags eu li na ajuda real: gh pr create aceita --draft, --fill, --base, --title, --body, --reviewer, --label, --milestone, --template e --dry-run. O gh pr merge aceita --merge, --squash, --rebase, --delete-branch, --auto e --admin.

Um bom PR

Título: o que muda, em uma frase, no imperativo (Corrige o cálculo da média com nota zero). Descrição (esta lista é sugestão minha, não está em página oficial): o que mudou e por quê, como testar, a issue com Closes #123, capturas de tela se houver mudança visual e o que ficou de fora de propósito. O guia de open source recomenda PRs pequenos e focados, que expliquem o motivo e não só o que foi feito.

Erro comumTrabalhar direto na main local e depois não conseguir separar o que é seu. Crie a branch antes de editar (veja o capítulo 9 para recuperar). E abrir PR de branch antiga, desatualizada: traga a base antes com merge ou rebase.

2A vida de um PR: revisão, checks e conflito

Pedi revisão e o colega pediu mudanças. Eu já posso fazer o merge? E o que muda quando o PR é draft?

Intuição. O PR é um processo com portões: cada portão só abre depois do anterior. Um rascunho não pede revisão nem entra. Uma revisão que pede mudanças tranca o merge até você responder. Os checks são a catraca automática: se falham, não passa.

Definição. Segundo a página de revisões (lida em 10/11/2026): Comment comenta sem aprovar nem reprovar; Approve aprova; Request changes pede ajuste e bloqueia o merge enquanto não for resolvido, se a regra exigir; Suggested changes propõe um trecho exato que o autor aceita com um clique. Cada comentário em linha pode ser marcado como resolvido. A aba “Files changed” mostra o diff e “Conversation” a discussão. Um PR em draft não pode ser mesclado e não dispara pedido automático de revisão a CODEOWNERS. Um PR com conflito não pode ser mesclado até o conflito ser resolvido. A página não diz se o autor pode aprovar o próprio PR: isso depende da regra de proteção (confira).

Exemplo resolvido: lendo a demo
Comece clicando em Abrir como draft. Em seguida tente Fazer merge: a demo recusa, porque um rascunho não pode ser mesclado.
Marcar como pronto, Pedir revisão e Pedir mudanças. Com mudanças pedidas e a regra de aprovação ligada, o merge é recusado (a página diz que bloqueia “se a regra exigir”: desligue a regra e a demo deixa passar). Um novo commit devolve o PR para a revisão e os checks recomeçam.
Com as regras da demo ligadas (aprovação e checks obrigatórios), o merge só é aceito depois de Aprovar e de os checks passarem. Depois do merge, Apagar a branch só funciona uma vez.
Desligue a regra de aprovação: num repositório seu, sem proteção, o merge é permitido sem aprovação. Se isso vale ou não no seu repositório depende da configuração: confira na tela.

Revisar pelo terminal (flags confirmadas na ajuda de gh pr review: --approve, --comment, --request-changes, --body):

$ gh pr review 123 --approve                                             # NAO testado aqui
$ gh pr review 123 --request-changes --body "Falta teste para o caso X"  # NAO testado aqui
$ gh pr review 123 --comment --body "Duvida sobre Y"                     # NAO testado aqui

Conflito

Dois lados mexeram na mesma linha. O Git não decide por você. Resolva atualizando a sua branch com a base (git merge main ou git rebase main), editando o arquivo, git add e git commit, e enviando de novo. O GitHub também tem um editor para conflitos simples (não testado aqui). Saída real de um conflito de conteúdo:

$ git merge feature/conflito
Auto-merging titulo.txt
CONFLICT (content): Merge conflict in titulo.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status -s
UU titulo.txt
$ cat titulo.txt
<<<<<<< HEAD
titulo: C
=======
titulo: B
>>>>>>> feature/conflito
# resolver: deixe so o texto final no arquivo, depois: git add titulo.txt ; git commit

Erro comumDeixar os marcadores <<<<<<< no arquivo e dar commit. O texto com os marcadores vira parte do código. Abra o arquivo, escolha o texto final, apague as três linhas de marcação e só então git add.

Merge commit, squash ou rebase: cada um deixa a história de um jeito.

3Merge commit, squash e rebase: o que cada um faz na main

O PR tem três commits de ajuste. Como eles vão aparecer na main depois do merge?

Intuição. Três jeitos de colar as páginas do rascunho no livro. Merge commit: cola as três páginas e põe um marcador no ponto de junção. Squash: resume as três numa só página. Rebase: recopia as três páginas, uma depois da outra, sem marcador.

Definição. Segundo a página oficial de merges (lida em 10/11/2026): merge commit mantém todos os commits do PR e cria um commit de merge na base, indicado quando o histórico completo importa; squash and merge junta todos os commits do PR em um só, indicado quando o PR é uma única mudança lógica com muitos commits de ajuste; rebase and merge adiciona cada commit à base sem commit de merge e o GitHub recria os commits com novos SHAs, indicado quando o time quer histórico linear e os commits já estão bem organizados.

Exemplo resolvido: o mesmo PR, três resultados (rodado de verdade, e igual ao da demo)
Cenário: a main tinha 2 commits (c1, c2), eu abri uma branch com 3 commits (p1, p2, p3) e, enquanto isso, a main ganhou 1 commit (m1).
Merge commit: a main fica com 7 commits (2 + m1 + 3 do PR + o commit de merge). O grafo tem dois ramos e um commit de dois pais.
Squash: a main fica com 4 commits (2 + m1 + 1 commit só com tudo). Os commits p1 a p3 não estão na main: o git branch --contains do p3 listou só a branch do PR.
Rebase: a main fica com 6 commits (2 + m1 + 3 copiados), em linha reta, sem commit de merge, e os três ganharam hashes novos (por exemplo, p3 era cdb9065 e virou d6ba3ab).

Como reproduzi no terminal (o botão do GitHub faz o equivalente):

$ git merge --no-ff --no-edit feature/x        # merge commit
$ git merge --squash feature/x                 # squash: prepara tudo, e voce faz o commit
$ git commit -qm "feat: ajustes (squash)"
$ git switch feature/x ; git rebase main       # rebase: recopia os commits sobre a main
Successfully rebased and updated refs/heads/feature/x.
$ git switch main ; git merge --ff-only feature/x

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Foi um repositório local, sem remoto. Hashes, datas e caminhos mudam em cada máquina.

Um detalhe que testei: com a main parada (sem commit novo desde que a branch nasceu), o git rebase main local respondeu Current branch f is up to date. e o hash não mudou. A página do GitHub diz que o “rebase and merge” recria os commits com novos SHAs; a demo mostra o resultado como a página descreve e eu não testei o botão.

Desfazer um merge

$ git revert --no-edit HEAD                    # HEAD e um commit de merge

$ git revert --no-edit -m 1 HEAD               # -m 1 = manter o primeiro pai (a main)

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Foi um repositório local, sem remoto. Hashes, datas e caminhos mudam em cada máquina.

Erro comumDar git revert num commit de merge sem -m 1. O Git não sabe qual dos dois pais é a “linha principal” e recusa. O -m 1 diz: mantenha o primeiro pai (a main). Outro erro: usar rebase em branch que outras pessoas já baixaram, e dar --force.

4Fechamento do capítulo

Cola da prova

  • GitHub Flow: branch curta, commits descritivos, PR (draft se quer feedback), responder com novos commits, merge depois da aprovação, apagar a branch.
  • Draft não faz merge. Request changes bloqueia (se a regra exigir). Conflito bloqueia. Checks falhando bloqueiam se forem obrigatórios.
  • Merge commit: mantém tudo e cria commit de merge. Squash: um commit só. Rebase: commits copiados (hashes novos), história linear, sem merge commit.
  • No cenário de 3 commits e main que andou 1: merge commit adiciona 4 (3 + merge), squash 1, rebase 3.
  • git revert de merge exige -m 1. git pull --ff-only falha com histórico divergente.
  • Sem forçar push em branch que outras pessoas usam.

Teste rápido

Pergunta 1

Um PR tem 3 commits de ajuste e o time quer a main com um commit por mudança. Qual tipo de merge?

O squash junta todos os commits do PR em um só na base.
Pergunta 2

Você tenta git revert num commit de merge e recebe “is a merge but no -m option was given”. O que fazer?

O -m 1 diz ao Git para manter o primeiro pai, a linha da main.
Pergunta 3

Um PR em draft, com checks passando e aprovado. Dá para fazer o merge?

A página de revisões diz que o draft não pode ser mesclado.
Pergunta 4

O que acontece, segundo a página oficial, com os commits quando você usa “rebase and merge”?

É o que a página de merges descreve. Por isso o histórico fica linear, mas os hashes mudam.
