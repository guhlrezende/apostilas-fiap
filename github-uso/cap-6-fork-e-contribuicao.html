1Fork ou branch: quando usar cada um

Quero corrigir um erro de digitação no repositório de outra pessoa. Faço uma branch nele?

Intuição. Se a casa é sua ou você tem a chave, você trabalha dentro dela (branch). Se a casa é de outra pessoa, você tira uma cópia da planta para a sua casa (fork), mexe lá e manda a proposta de volta por correio (PR).

Definição. Sem permissão de escrita no repositório: fork. Com permissão de escrita no repositório do time: branch no próprio repositório, sem fork, que é o padrão de equipe. O fluxo de fork da página oficial (lida em 10/11/2026): fazer o fork, clonar o seu fork, criar uma branch, commitar, enviar para o seu fork e abrir o PR para o original. A página de visibilidade diz que o fork compartilha o código e as configurações de visibilidade com o original. A regra fina de fork de repositório privado não está na página que li (confira).

SituaçãoO que fazer
O repositório é seubranch + PR para a sua main
É do seu time e você tem permissão de escritabranch no repositório original + PR (sem fork)
É de outra pessoa ou projeto aberto, sem permissão de escritafork, branch no fork, PR para o original
Erro comumClonar o original, fazer commits e só então descobrir que o push é recusado. O clone aponta para o original: faltou o fork. Confira git remote -v antes de investir tempo.

2origin, upstream e manter o fork em dia

Meu fork é de semana passada e o original já recebeu dez commits. Como alcanço?

Intuição. Seu fork é uma foto do original no dia em que você tirou. O upstream é um segundo contato na sua agenda, o do original. Você busca as novidades por ele, mistura na sua cópia e devolve ao seu fork.

Definição. Num fork há dois remotos: origin (o seu fork, onde você tem permissão) e upstream (o original, que você só lê). A sequência da página oficial de sincronização: git remote add upstream URL, git fetch upstream, git switch main, git merge upstream/main e git push origin main. O gh repo sync também faz isso, com --branch, --source e --force; a página avisa que o --force apaga a branch do fork para igualar ao original, descartando commits locais dela.

Exemplo resolvido: um fork simulado, rodado de verdade
Criei original.git (o dono) com um commit, e um fork.git como cópia dele (um git clone --bare, só para simular, porque eu não criei fork no GitHub). Clonei o fork em meu e adicionei o upstream.
O dono enviou um commit novo. Rodei git fetch upstream. O git rev-list --left-right --count main...upstream/main deu 0 1: zero commits meus à frente, um atrás do original.
O git merge --ff-only upstream/main avançou a main e o git push origin main levou isso para o meu fork (f629c8c..64436cb). Só então criei a branch fix/typo a partir da main atualizada e a enviei com -u para o meu fork.
$ git remote -v                          # logo depois de clonar o meu fork
origin	.../fork.git (fetch)
origin	.../fork.git (push)
$ git remote add upstream ../original.git
$ git fetch upstream
 * [new branch]      main       -> upstream/main
$ git rev-list --left-right --count main...upstream/main
0	1                                    # 0 a frente, 1 atras do original
$ git switch main ; git merge --ff-only upstream/main
Updating f629c8c..64436cb
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
$ git push origin main
   f629c8c..64436cb  main -> main        # agora o meu fork esta em dia
$ git switch -c fix/typo ; git push -u origin fix/typo
$ git branch -vv
* fix/typo e3cd4cd [origin/fix/typo] docs: corrige typo
  main     64436cb [origin/main] feat: novidade do dono
$ git rev-list --left-right --count main...upstream/main
0	0                                    # em dia: nenhum commit de diferenca

Rodado de verdade em 10/11/2026 (Git 2.56 no Windows 11, Git Bash), em pasta temporária nova, fora do repositório. Dois repositórios bare locais (original.git e fork.git) simularam o original e o fork; o git clone grava o caminho completo, que aqui aparece abreviado como .... Hashes, datas e caminhos mudam em cada máquina.

Não testado aquiFork, gh repo fork, gh repo sync e o botão “Contribute”/“Open a pull request” não foram testados: usei dois repositórios bare locais para simular o fork. A simulação mostra os remotos e os commits, não o comportamento do site.
Erro comumFazer as suas alterações direto na main do fork e depois não conseguir sincronizar sem conflito. Deixe a main do fork espelhando o upstream e trabalhe em branches. Outro erro: usar gh repo sync --force sem saber que ele descarta commits locais da branch.

3O desenho completo: upstream, origin e a sua máquina

Em que ordem acontecem as coisas, e o que está impedido enquanto outra etapa não for feita?

Intuição. Três caixas: o original (upstream), o seu fork no GitHub (origin) e o seu computador (local). As setas entre elas são os comandos. O PR é a seta que sai do seu fork e chega no original.

Definição. O diagrama abaixo simula: fazer o fork, clonar, adicionar o remoto upstream, fetch upstream, merge upstream/main, push origin main, criar a branch, enviar a branch e abrir o PR. Quando o dono do original publica algo, o seu fork fica atrás até você sincronizar. A simulação recusa passos fora de ordem e explica por quê.

Exemplo resolvido: um caminho completo na demo
Fazer o fork, clonar o fork e git remote add upstream.
Clique em O dono publica uma novidade: o contador “atrás do original” sobe para 1.
git fetch upstream, git merge upstream/main e git push origin main: o contador volta para 0 e o fork fica em dia.
Criar branch, Commit na branch, Enviar a branch e Abrir PR. Tente abrir o PR sem enviar a branch: a demo recusa.

Etiqueta de quem contribui

Do guia de open source e da página de contribuição (lidos em 10/11/2026), resumidos com as minhas palavras:

  • Antes de qualquer coisa, leia o README, o CONTRIBUTING e o código de conduta, e veja se o projeto tem commits e respostas recentes.
  • Procure uma issue existente antes de abrir outra. Se for trabalhar nela, avise.
  • Mudança grande: combine na issue antes de escrever o código.
  • PR pequeno e focado, com teste, e no estilo do projeto.
  • Responda à revisão com rapidez. Sem resposta por mais de uma semana, faça um lembrete educado no próprio tópico, não em mensagem privada.
  • Se recusarem a contribuição, agradeça e respeite. Você sempre pode manter o seu fork.
  • Se usou ferramentas de IA, revise o que for enviar: você continua responsável pelo conteúdo.
Erro comumAbrir um PR enorme, sem avisar, num projeto que você acabou de conhecer. O mantenedor não tem como revisar e não sabe se a mudança cabe no projeto. Combine na issue e mande pedaços pequenos.

Laboratório: fork simulado no seu computador

Fazer fork do seu próprio repositório na mesma conta não é o caso de uso (confira na tela: não li essa regra na documentação), e contribuir com um projeto de terceiros exige respeitar as regras dele. Por isso este laboratório é local: ele reproduz a mecânica com repositórios bare, e eu rodei exatamente estes comandos.

Numa pasta nova, crie o “original” e o “fork”: git init -q --bare -b main original.git. Clone-o para dono, faça um commit com README e git push origin main. Depois git clone -q --bare original.git fork.git.
Clone o fork: git clone -q fork.git meu. Em meu, rode git remote -v e anote para onde o origin aponta. Configure nome e e-mail de teste só nesse clone (git config user.name e user.email).
Adicione o upstream (git remote add upstream ../original.git). Em dono, faça outro commit e envie. Em meu, rode git fetch upstream e git rev-list --left-right --count main...upstream/main.
Sincronize: git merge --ff-only upstream/main e git push origin main. Crie fix/typo, faça um commit e envie com -u para o fork.
Prova de que deu certo: git branch -vv mostra [origin/fix/typo] e o contador do passo 3 vira 0 0 depois do sincronismo. Opcional, no site: veja como fica a tela “Contribute” do seu próprio fork (não testado aqui).

0 de 5 passos feitos.

4Fechamento do capítulo

Cola da prova

  • Sem permissão de escrita: fork. Com permissão no repositório do time: branch nele, sem fork.
  • Num fork: origin = o seu fork; upstream = o original. git fetch upstream, git merge upstream/main, git push origin main.
  • git rev-list --left-right --count main...upstream/main diz quantos commits você tem à frente e atrás.
  • gh repo sync --force descarta commits locais da branch do fork.
  • Etiqueta: ler CONTRIBUTING, procurar issue existente, combinar mudança grande, PR pequeno com teste, lembrete educado no próprio tópico.

Teste rápido

Pergunta 1

Você não tem permissão de escrita num projeto e quer propor uma correção. Qual o caminho?

Sem permissão de escrita, a contribuição passa pelo seu fork.
Pergunta 2

O que o resultado 0 3 de git rev-list --left-right --count main...upstream/main diz?

O primeiro número conta o que só a sua main tem; o segundo, o que só a upstream/main tem.
Pergunta 3

Na demo, você tenta abrir o PR sem ter enviado a branch para o fork. O que acontece?

O PR compara uma branch do seu fork com a do original; sem push, a branch só existe no seu computador.
