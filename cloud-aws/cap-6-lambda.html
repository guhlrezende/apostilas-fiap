Onde paramosAté aqui cada serviço apareceu sozinho: EC2 (máquina), S3 (arquivos), RDS (banco). A startup agora quer somar as horas de cada funcionário em cada projeto, e todo mês chega um arquivo atualizado para ser processado e inserido no banco. Dois problemas: como processar arquivos, e como executar código na nuvem sem manter um servidor ligado esperando.

1Lambda: código que só existe quando roda

Para um arquivo que chega uma vez por mês, ter uma máquina ligada é desperdício.

A AWS Lambda executa código sob demanda, sem gerenciar servidor (serverless). Você sobe só o código, a AWS o roda quando algo o aciona e cobra por execução, considerando duração e memória usada. Linguagens: Python, Node.js, Java, Go, .NET, Ruby. Usos citados: ETL (extrair, transformar, carregar), integração com APIs e com mensageria.

Complemento: limites mudamOs números do slide são de uma época anterior. Hoje a documentação da AWS permite memórias maiores (até cerca de 10 GB), por exemplo. O tempo limite de 15 minutos segue válido e é o que define o tipo de trabalho adequado: tarefas curtas e pontuais, e não processos longos. Confira sempre a documentação atual.

Compare com a EC2: ela cobra enquanto está ligada, mesmo esperando. A Lambda cobra só quando roda. Para um arquivo mensal, a diferença é enorme.

2O fluxo completo: S3, gatilho, Lambda, RDS

Quatro serviços, um fluxo.

CSV  →  S3  --(gatilho)-->  Lambda  --(INSERT INTO)-->  RDS

O laboratório, em ordem: (1) criar o bucket; (2) criar o MySQL no RDS e anotar o endpoint; (3) criar a tabela; (4) criar a função Lambda (runtime Python) com um perfil de execução (a role do laboratório); (5) subir o código empacotado; (6) criar o gatilho do S3; (7) subir o CSV no bucket; (8) ver o log no CloudWatch; (9) consultar o RDS. Faça você o passo 7: o banco abaixo é de verdade, e a tabela tem a mesma chave primária composta do laboratório.

O que você acabou de ver
A chave primária é (idProjeto, idFuncionario): o funcionário 1 pode estar em dois projetos, mas o mesmo par não pode aparecer duas vezes.
Na segunda subida do mesmo CSV, todas as linhas violam a chave primária. O código faz rollback: ou entram todas, ou nenhuma.
O erro apareceria no CloudWatch, onde tudo o que a função imprime (print) vira log.

3O código, por dentro

Ler o arquivo, quebrar em linhas, inserir, confirmar.

import boto3, pymysql
# versão resumida: troque pelos valores do seu laboratório
bucket, arquivo = "meu-bucket", "horasalocadas.csv"
endpoint, usuario, senha, banco = "...", "...", "...", "..."   # na prática: variáveis de ambiente
s3 = boto3.client('s3')

def lambda_handler(event, context):      # o ponto de entrada que a AWS chama
    inserir_dados_mysql()
    return {'statusCode': 200, 'body': 'Processamento realizado com sucesso!'}

def ler_arquivo_csv_s3():
    response = s3.get_object(Bucket=bucket, Key=arquivo)
    dados = response['Body'].read().decode('utf-8')
    return dados.splitlines()               # lista de linhas do CSV

def inserir_dados_mysql():
    linhas = ler_arquivo_csv_s3()
    conexao = pymysql.connect(host=endpoint, user=usuario, passwd=senha, db=banco)
    try:
        with conexao.cursor() as cursor:
            for linha in linhas[1:]:               # [1:] pula o cabeçalho
                if not linha.strip(): continue
                p = linha.split(";")               # este CSV usa ponto e vírgula
                cursor.execute("INSERT INTO projetoFuncionario (idProjeto, idFuncionario, horas) VALUES (%s, %s, %s)", (p[0], p[1], p[2]))
        conexao.commit()                     # grava tudo de uma vez
    except Exception:
        conexao.rollback()                   # desfaz a execução inteira
        raise
    finally:
        conexao.close()
  • lambda_handler(event, context) é a função que a AWS chama. O nome precisa bater com o handler configurado.
  • O código ignora o event: o bucket e o arquivo estão fixos no código. Para o seu laboratório, troque pelo seu bucket e pelo seu endpoint. (Melhor: usar o event, que traz o nome do bucket e do arquivo que dispararam a função.)
  • %s com tupla em vez de montar o SQL concatenando texto: o driver escapa os valores e evita SQL injection.
  • commit() só no fim, rollback() no erro: transação de verdade (Bancos de Dados, Capítulo 8).
  • O pacote (.zip) leva a pasta do pymysql junto: a Lambda já traz o boto3, mas não traz o driver do MySQL. (Alternativa mais limpa: layers.)
Cuidado: senha no códigoO arquivo do exemplo traz endpoint, usuário e senha escritos no próprio .py. Funciona no laboratório, mas em produção a senha vai para variáveis de ambiente da Lambda ou, melhor, para o Secrets Manager. Nunca no repositório.
Por que a role (LabRole)A Lambda precisa ler o S3, o que exige permissão. Em vez de uma chave de acesso no código, a função assume uma role. É o Capítulo 2 na prática: a role não tem senha e serve para um serviço ganhar permissão.

Cola da prova

  • Lambda: código sob demanda, sem servidor; cobra por execução. Limite de 15 min por execução.
  • Fluxo do laboratório: CSV → S3 → gatilho → Lambda → RDS, com log no CloudWatch.
  • lambda_handler(event, context) é o ponto de entrada. O event traz quem disparou.
  • Role de execução no lugar de chave de acesso. Senha em variável de ambiente ou Secrets Manager, nunca no código.
  • Mesmo CSV duas vezes: erro de chave primária e rollback.

Teste rápido

Pergunta 1

O que dispara a função no laboratório?

O gatilho do S3 avisa a Lambda quando o objeto é criado. Isso é o 'event-driven'.
Pergunta 2

Por que a função precisa de uma role?

A role entrega credenciais temporárias ao serviço. Isso evita segredo fixo.
Pergunta 3

Qual o tempo máximo de uma execução da Lambda?

Por isso a Lambda serve para tarefas curtas. Processos longos pedem outra solução.
