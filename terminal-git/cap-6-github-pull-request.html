1Remotos: push, pull e clone

Meu histórico está só no meu computador. Como levo isso para o GitHub, e como outra pessoa pega?

Intuição. Pense numa pasta compartilhada na nuvem que entende de histórico. O GitHub guarda uma cópia do seu repositório. Cada pessoa trabalha na sua cópia local e eles se sincronizam: você envia (push) o que fez e traz (pull) o que os outros fizeram.

Definição. Um remoto é um repositório em outro lugar, com um apelido; o padrão é origin. git remote add origin URL registra o apelido. git push -u origin main envia a branch (o -u lembra o destino para os próximos). git clone URL baixa uma cópia completa. git fetch só atualiza o que você sabe do remoto; git pull faz isso e traz as mudanças para a sua branch.

Exemplo resolvido: duas pessoas, um remoto
Para testar sem GitHub, criei uma pasta que faz o papel de remoto (git init --bare -b main; sem o -b main, dependendo da sua configuração o remoto nasce apontando para master e o primeiro git clone avisa remote HEAD refers to nonexistent ref, como aconteceu comigo) e dois repositórios que conversam com ela. É o mesmo mecanismo do GitHub; muda a URL.
No meu repositório: 1 commit, git remote add origin ../nuvem/projeto.git e git push -u origin main. A resposta: [new branch] main -> main.
A colega faz git clone, cria a branch ajuste-titulo, faz 1 commit e envia. No meu repositório, o git fetch só traz o aviso: aparece origin/ajuste-titulo em git branch -r, sem mexer nos meus arquivos.
Depois que a mudança dela entra na main e vai para o remoto, o git pull responde Fast-forward e o log passa a ter 2 commits.

2Pull request: pedir para juntar, com revisão

Posso fazer merge direto na main. Por que times usam pull request?

Intuição. É um pedido formal: 'terminei esta branch, alguém pode olhar antes de entrar?'. Os colegas veem exatamente o que mudou, comentam, pedem ajustes, e só depois a mudança entra. É o controle de qualidade do time.

Definição. Um pull request (PR) é um pedido para integrar uma branch ao projeto principal. Em geral: a pessoa abre o PR, a equipe compara as mudanças e comenta, quem abriu faz novos commits se for preciso, e um mantenedor aprova e faz o merge. Em outras plataformas, como o GitLab, o nome é merge request. (IBM Think, página sobre pull request.) A IBM descreve três fluxos: feature branch (uma branch por mudança), fork (uma cópia sua do repositório alheio, comum em projetos abertos) e git-flow (um conjunto mais rígido de branches).

1. Branch

git switch -c ajuste-titulo. Nunca trabalhe direto na main.

2. Commits

Faça commits pequenos, cada um com mensagem que explica o quê e por quê.

3. Push da branch

git push -u origin ajuste-titulo. Este passo eu testei com o remoto local.

4. Abrir o PR

No site do GitHub: escolher a branch de origem e a de destino, escrever o que mudou e por quê. não testado aqui

5. Revisão

Os colegas leem o diff e comentam. Se pedirem ajuste, você faz novos commits na mesma branch e o PR se atualiza. não testado aqui

6. Merge

Alguém com permissão aprova e junta na main. Depois, git pull na main local e apague a branch já usada. não testado aqui

Exemplo resolvido: o que o PR muda em relação ao merge direto
Merge direto na main: 1 pessoa decide sozinha. Erro entra e só aparece depois.
Com PR: se o time exigir revisão, outra pessoa olha a mesma mudança antes de ela entrar (quem escreveu e quem revisa). O PR em si não garante isso: é uma regra do time ou do repositório. O PR registra a discussão junto do código, e fica fácil voltar depois e entender por que algo foi mudado.
Na minha simulação, o equivalente do botão de merge foi rodar git merge origin/ajuste-titulo na main (respondeu Fast-forward) e git push. No GitHub quem faz isso é o servidor. o PR em si, não testado aqui

Erro comumAbrir um PR enorme, com dezenas de arquivos e várias ideias misturadas. É ruim de revisar e a revisão vira só um 'ok'. Prefira um PR por assunto, pequeno, com título e descrição que expliquem o que mudou. (Boa prática geral, não é medição minha.)

3Fluxo de trabalho e erros comuns

Conheço os comandos. Na hora de trabalhar de verdade, qual é a sequência certa, e onde as pessoas escorregam?

Intuição. É um hábito, como olhar os dois lados antes de atravessar a rua: olhar o estado, trabalhar numa branch, registrar em pequenos pedaços, mostrar para alguém, só então juntar.

Definição. O fluxo básico, em ordem: (1) git status para saber onde está; (2) git switch -c nome; (3) editar e testar; (4) git add e git commit, várias vezes; (5) git push -u origin nome; (6) abrir o PR; (7) depois do merge, git switch main, git pull e apagar a branch usada com git branch -d nome.

Exemplo resolvido: o ciclo com os números do que rodei
git branch -d feature depois de um fast-forward: Deleted branch feature (was 2efef5d). A branch some; os 3 commits continuam na main.
No remoto local, depois do fetch: 2 branches remotas de verdade (origin/main e origin/ajuste-titulo); a linha origin/HEAD -> origin/main é só um atalho para a principal. Depois do pull, o log tem 2 commits.

Treine a decisão. Para cada situação, qual é a ação certa?

Quero testar uma ideia sem mexer na main.

Crie uma branch: git switch -c nome. É uma etiqueta nova, barata, e a main fica intacta.

Meu arquivo de senhas foi commitado ontem e quero parar de acompanhá-lo.

Troque a senha primeiro, porque ela ficou no histórico. Só o .gitignore não basta para arquivo já acompanhado: use git rm --cached para parar de acompanhá-lo daqui para a frente.

Terminei a minha branch e quero que alguém revise antes de ela entrar na main.

É exatamente o pull request: pedido formal de integração, com revisão.

Alterei dois arquivos e quero registrar essa versão com uma mensagem.

git add nos arquivos e git commit -m "mensagem". Com git status antes, para conferir o que entra.

Fiz commits na minha branch e quero que meus colegas a vejam no GitHub.

git push -u origin nome envia a branch para o remoto. Sem o push, ela só existe no seu computador.

Os erros mais comuns de quem está começando

Resumo do que apareceu na apostila inteira, em ordem de quanto custa errar:

  1. Subir segredo (.env, chave privada) para o repositório. Coloque no .gitignore antes do primeiro commit; se já foi, troque a credencial primeiro (o git rm --cached só tira dos commits futuros).
  2. Commitar direto na main em vez de criar uma branch e abrir PR.
  3. git push --force em branch compartilhada (não testado aqui) e rebase em commits já enviados (alerta da IBM): reescrevem o histórico dos outros.
  4. Não olhar o git status antes e depois de cada passo.
  5. Resolver conflito sem ler o arquivo e os marcadores.
  6. Estranhar o aviso de CRLF do Windows (visto de verdade, não é erro fatal) ou, ao contrário, ignorá-lo sem saber se o time usa a mesma regra.
  7. Misturar o terminal: comando de bash no PowerShell e vice-versa; curl que é alias; aspas erradas.
  8. Apagar a chave privada de SSH sem backup, ou compartilhá-la.

4Fechamento do capítulo

Cola da prova

  • Remoto = repositório em outro lugar, com apelido (origin). push envia, fetch só atualiza o que você sabe, pull traz para a branch, clone baixa tudo.
  • Pull request = pedido formal de juntar uma branch, com revisão. Em outras plataformas: merge request. Fluxos: feature branch, fork, git-flow.
  • Fluxo: status → branch → commits pequenos → push → PR → revisão → merge → pull na main.
  • Segredo: .gitignore antes do primeiro commit; se vazou, revogue ou troque a credencial (o git rm --cached só vale daqui para a frente; o histórico guarda o segredo).
  • Evite push --force em branch compartilhada e rebase de commits já enviados.
  • Nunca coloque token ou senha em URL, em chat ou no repositório. Chave privada não se compartilha.

Teste rápido

Pergunta 1

Qual a diferença entre git fetch e git pull?

Na simulação, o fetch só criou origin/ajuste-titulo na lista de branches remotas. O pull foi o que fez a minha branch andar (Fast-forward).
Pergunta 2

Para que serve um pull request, em vez de um merge direto na main?

O PR é o ponto de conversa: as pessoas veem o que mudou, comentam e pedem ajustes antes de juntar.
Pergunta 3

Você descobre que subiu uma chave de API no último commit, já enviado. Qual a reação certa?

O arquivo continua no histórico e em quem já baixou. A chave tem de ser trocada; tirar do repositório é o segundo passo. O git rm --cached só vale para os próximos commits, e limpar o histórico (filter-repo, BFG) exige force push e não substitui a troca (não testado aqui).
