1Os três lugares e o commit

Por que o Git pede add e commit separados? Não bastava salvar?

Intuição. Pense numa foto de grupo. Primeiro você arruma quem vai aparecer (o add), depois aperta o botão (o commit). O resultado é uma foto do projeto naquele momento, que fica guardada e dá para rever depois. Se você mudou 5 arquivos mas só 2 contam a mesma história, tira uma foto com 2 e outra com 3.

Definição. Um repositório Git tem três lugares: a pasta de trabalho (os arquivos que você edita), a área de preparação (staging: o que vai entrar na próxima foto) e o repositório (a pasta escondida .git, onde as fotos ficam). Um commit é um registro de um estado do projeto, com identificador (hash), autor, mensagem e um ponteiro para o commit anterior (IBM Developer, tutorial de 2021).

Exemplo resolvido: do arquivo novo ao primeiro commit
Crio notas.txt. O git status o lista em Untracked files: o Git vê, mas ainda não acompanha.
git add notas.txt põe o arquivo na área de preparação. O git status -s (versão curta) mostra A notas.txt: A de added.
git commit -m "primeiro commit" responde 1 file changed, 1 insertion(+): 1 arquivo, 1 linha nova. O git log --oneline mostra 1 commit, com hash curto de 7 caracteres.
$ git init -b main                  # cria o repositório (a pasta .git); main é o nome da branch
Initialized empty Git repository in C:/Users/voce/estudo/projeto-git/.git/
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notas.txt

nothing added to commit but untracked files present (use "git add" to track)
$ git add notas.txt                 # arruma a foto
warning: in the working copy of 'notas.txt', LF will be replaced by CRLF the next time Git touches it
$ git status -s
A  notas.txt
$ git commit -m "primeiro commit"   # aperta o botão
[main (root-commit) 8727806] primeiro commit
 1 file changed, 1 insertion(+)
 create mode 100644 notas.txt
$ git log --oneline
8727806 primeiro commit

Nos exemplos, o Git sabia quem era o autor porque passei a identidade por variáveis de ambiente (nome fictício, e-mail de exemplo). No seu computador isso se configura uma vez com git config --global user.name e git config --global user.email; não rodei esses dois no seu computador. No PowerShell os comandos git são exatamente os mesmos, porque o git é um programa e não um comando de shell.

Exemplo resolvido: ver a diferença antes de registrar
Acrescento a linha nova a um arquivo de 3 linhas. O git diff mostra a mudança: linhas com + entraram, com - saíram. Aqui apareceu 1 linha com +nova.
git restore notas.txt desfaz a edição e volta ao último commit. O git status -s fica vazio.
$ git diff
diff --git a/notas.txt b/notas.txt
index e2e365a..a7ce375 100644
--- a/notas.txt
+++ b/notas.txt
@@ -1,3 +1,4 @@
 a
 l2
 l3
+nova
$ git restore notas.txt     # CUIDADO: descarta a edição que não foi commitada
Erro comumDois tropeços. (1) Ver warning: LF will be replaced by CRLF e achar que quebrou tudo. Não é erro fatal: é o Git do Windows avisando que vai converter o fim de linha (configuração core.autocrlf). Não ignore sem entender se o seu time usa a mesma regra. (2) Rodar git restore sem pensar: ele descarta mudanças que não foram commitadas, e não há como recuperar.

2Branches, HEAD e merge

Quero testar uma ideia sem arriscar a versão que funciona. Preciso copiar a pasta inteira?

Intuição. Não precisa copiar nada. Uma branch é só uma etiqueta colada num commit. Criar outra etiqueta é instantâneo. Quando você faz um commit novo, a etiqueta em que você está anda para a frente; as outras ficam onde estavam. O HEAD é o 'você está aqui': aponta para a branch atual.

Definição. git branch nome cria a etiqueta; git switch nome muda para ela (git switch -c nome cria e muda). git merge nome junta o trabalho de nome na branch em que você está. Há dois resultados: fast-forward (a branch atual não andou, então o merge só move a etiqueta e não cria commit) ou merge commit (as duas andaram, então nasce um commit novo com dois pais). (IBM Developer, tutorial de 2021.)

Exemplo resolvido: os dois tipos de merge, com número
Cenário A, fast-forward. Parto de 1 commit (c1). Crio feature e faço 2 commits nela (c2, c3). Volto para a main, que não andou, e faço git merge feature: a resposta é Fast-forward. Total: 3 commits, em linha reta, e nenhum commit de merge.
Cenário B, dois pais. Mesmo começo, mas depois de voltar para a main eu faço o commit c4 nela. Agora as duas branches andaram. O git merge feature cria o commit c5 com 2 pais (c4 e c3). Total: 5 commits.
Na saída real do cenário B, o git log --graph desenha o losango: a linha da feature sai de c1 e volta no commit de merge.
# Cenário A: fast-forward
$ git merge feature
Updating f4a794f..00d811c
Fast-forward
 notas.txt | 2 ++
 1 file changed, 2 insertions(+)
$ git log --oneline --graph --all
* 00d811c (HEAD -> main, feature) c3: exercicio
* bfc05a0 c2
* f4a794f primeiro commit

# Cenário B: as duas andaram, então nasce um commit de merge
$ git merge feature -m "c5: junta feature"
Merge made by the 'ort' strategy.
 notas.txt | 2 ++
 1 file changed, 2 insertions(+)
$ git log --oneline --graph --all
*   2e19467 (HEAD -> main) c5: junta feature
|\
| * 84a1923 (feature) c3: exercicio
| * cb32ac7 c2
* | 93b03f0 c4: so na main
|/
* bd48c22 primeiro commit

Nas saídas reais acima, os hashes (como 2e19467) vêm da minha execução e seriam outros no seu computador. Os nomes entre parênteses (HEAD -> main, feature) o Git mostra quando a saída vai para um terminal; para reproduzir isso eu rodei com --decorate. Também encurtei as saídas: tirei os avisos de CRLF do Windows e as linhas de progresso que o Git imprime no terminal. Na demo, para ficar legível, os commits se chamam c1, c2 e assim por diante. A mensagem do merge também é diferente: na demo, o Git de mentira escreve Merge branch 'feature'. Use um cenário pronto ou digite os seus comandos.

Quando o merge não consegue sozinho: conflito

Se as duas branches mudaram a mesma linha do mesmo arquivo, o Git não sabe qual vale, e para. Ele escreve os dois lados no arquivo, entre marcadores, e espera você decidir. Rodei isso de verdade:

$ git merge ajuste
Auto-merging leia.txt
CONFLICT (content): Merge conflict in leia.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status -s
UU leia.txt                          # UU: os dois lados mudaram
$ cat leia.txt
<<<<<<< HEAD
titulo: Guia de Git                  # o que está na sua branch (main)
=======
titulo: Git na pratica               # o que veio da outra branch (ajuste)
>>>>>>> ajuste
# edite o arquivo, deixe a versão final sem os marcadores, e então:
$ git add leia.txt
$ git commit -m "resolve conflito"   # fecha o merge, com 2 pais como o cenário B
Erro comumResolver o conflito às cegas com git checkout --theirs ou --ours, ou apagar os marcadores sem ler. Abra o arquivo, ache os <<<<<<<, decida o texto final com a cabeça e só então faça o git add e o commit. Esquecer um marcador dentro do arquivo é um erro que costuma ir parar no repositório.
Complemento do complemento: rebase e revert (rodei um caso simples)

O rebase reaplica os commits de uma branch em cima da ponta de outra, criando commits novos e deixando o histórico em linha reta. Num teste simples (a main com m1 e m2, e uma branch rb que saiu de m1 com o commit r1), o git rebase main respondeu Successfully rebased and updated refs/heads/rb. O r1 trocou de hash (era cee1e6c e virou f90b08b, ou seja, é um commit novo) e o git log --graph ficou reto, com 3 commits e sem losango. A IBM alerta: não reescreva commits que já foram enviados a outras pessoas, porque o rebase troca os hashes. O git revert --no-edit HEAD faz o contrário de apagar: cria um commit novo que desfaz o anterior (rodei: saiu [main bb731b5] Revert "r1", com 1 file changed, 1 deletion(-), e o commit original continua no log, logo abaixo). Não testei cherry-pick.

Com o .gitignore.

3.gitignore: o que nunca entra

Quase todo projeto tem um arquivo com senha ou chave, tipo um .env. Como garantir que ele nunca vá parar no GitHub?

Intuição. O .gitignore é uma lista de 'não quero que você nem olhe para isso'. O Git passa a fingir que esses arquivos não existem: eles não aparecem no git status e não entram no git add comum.

Definição. É um arquivo de texto na raiz do repositório com um padrão por linha (.env, logs/, *.log). Vale só para arquivos que ainda não estão sendo acompanhados. Um arquivo já commitado continua acompanhado até você mandar o Git parar de acompanhá-lo. (Documentação oficial do Git.)

Exemplo resolvido: ignorar antes, e o que fazer se for tarde
Com .env e logs/a.log na pasta e um .gitignore com as linhas .env e logs/, o git status -s lista só .gitignore e app.txt: 2 arquivos. Os outros 2 ficaram invisíveis.
git check-ignore -v .env mostra a regra responsável (.gitignore:1:.env). É a forma de tirar a dúvida 'por que o Git está ignorando isto?'.
O caso difícil: um arquivo .env2 já foi commitado. Adiciono .env2 ao .gitignore e edito o arquivo. O git status -s ainda mostra M .env2 (modificado): continua acompanhado. Só git rm --cached .env2 faz o Git parar de acompanhá-lo: ele imprime rm '.env2', o status passa a D .env2 e o arquivo continua na sua pasta. Mas isso vale daqui para a frente: o conteúdo antigo continua nos commits que já existem (o git show HEAD~1:.env2 do bloco abaixo mostra isso).
$ cat .gitignore
.env
logs/
$ git status -s
?? .gitignore
?? app.txt
$ git check-ignore -v .env logs/a.log
.gitignore:1:.env	.env
.gitignore:2:logs/	logs/a.log

# o caso difícil: o arquivo já foi commitado
$ echo ".env2" >> .gitignore
$ echo mudou >> .env2
$ git status -s
 M .env2                  # ainda acompanhado, apesar do .gitignore
?? .gitignore
?? app.txt
$ git rm --cached .env2   # --cached
rm '.env2'
$ git status -s
D  .env2
?? .gitignore
?? app.txt
$ git commit -m "para de acompanhar o .env2"    # saída do commit omitida
$ git show HEAD~1:.env2   # HEAD~1: o conteúdo antigo continua no histórico
env2
Erro comumAchar que o .gitignore resolve um segredo que já foi commitado. Não resolve: o arquivo continua no histórico e em quem já baixou o repositório. Se uma senha ou chave de API foi parar num commit, trate como vazada: o passo obrigatório é revogar ou trocar a credencial (gerar outra e invalidar a antiga no serviço). O git rm --cached só tira o arquivo dos commits futuros: a chave continua no histórico e, se você já fez push, no remoto e em quem clonou (rodei: depois do rm --cached e do commit, o git show do commit anterior ainda mostrou o conteúdo). Apagar do histórico exige reescrevê-lo com git filter-repo ou com o BFG Repo-Cleaner e dar um push --force, o que reescreve o histórico de todo mundo que usa o repositório: não testado aqui. Mesmo assim, troque a credencial, porque cópias antigas podem existir. (A parte de orientação é boa prática geral; o que eu medi foi o git show.)

Cuidado ao criar o .gitignore pelo PowerShell 5.1. Rodei (com um arquivo de teste no lugar do .env): ".env" > .gitignore grava o arquivo em UTF-16 LE (bytes 255 254 46 0 101 0 ...) e o Git não o lê: o .env continuou aparecendo como ?? e o git check-ignore -v .env não imprimiu nada. O Out-File sem opção faz o mesmo. É um risco real de commitar um segredo achando que ele estava ignorado. O que funcionou nos meus testes: Set-Content .gitignore -Value ".env" -Encoding ascii (também o -Encoding utf8, que no 5.1 grava com BOM e o Git aceitou), ou criar o arquivo pelo Git Bash com echo .env > .gitignore. Depois de criar, sempre rode git check-ignore -v .env para confirmar. Fonte do .gitignore: documentação oficial do Git (não é da IBM; a IBM não tem tutorial de .gitignore nas páginas que li).

4Fechamento do capítulo

Cola da prova

  • Três lugares: pasta de trabalho → (git add) → staging → (git commit) → repositório. Use git status antes e depois de cada passo.
  • Commit = registro com hash, autor, mensagem e ponteiro para o anterior. git log --oneline lista; git diff mostra o que mudou.
  • Branch é uma etiqueta num commit, não uma cópia. HEAD é onde você está. git switch -c nome cria e entra.
  • Merge: fast-forward (sem commit novo, a atual não andou) ou merge commit (dois pais, as duas andaram). Cenário A = 3 commits; cenário B = 5 commits.
  • Conflito: os dois lados mudaram a mesma linha. Edite, git add, git commit.
  • .gitignore só vale para o que ainda não é acompanhado. Se já foi commitado: git rm --cached tira só dos commits futuros; se era segredo, revogue ou troque a credencial, porque ele continua no histórico.

Teste rápido

Pergunta 1

A main não recebeu nenhum commit desde que a feature saiu dela. O que faz git merge feature na main?

Se a atual não andou, o histórico da feature é continuação direta dela. O Git só avança a etiqueta (fast-forward). O commit de merge com dois pais só nasce quando as duas andaram.
Pergunta 2

Você adicionou .env ao .gitignore, mas ele já tinha sido commitado e continua aparecendo como modificado. O que resolve?

O .gitignore só vale para arquivos que ainda não são acompanhados. O --cached tira o arquivo do Git sem apagá-lo da pasta, mas o conteúdo antigo continua no histórico.
Pergunta 3

Criar uma branch copia todos os arquivos do projeto?

A branch é um ponteiro. Os arquivos só mudam de verdade quando você troca de branch e os commits são diferentes.
