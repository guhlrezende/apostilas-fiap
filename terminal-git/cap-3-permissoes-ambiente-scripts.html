1Permissões: quem pode ler, escrever e executar

Um arquivo que 'não abre' e um script que 'não roda' costumam ser a mesma coisa. O que o sistema olha antes de deixar você usar um arquivo?

Intuição. Cada arquivo tem três crachás de acesso: um para o dono, um para o grupo dele e um para todo o resto (outros). Em cada crachá o sistema marca três permissões separadas: ler, escrever e executar.

Definição. O ls -l mostra isso em 10 caracteres: o primeiro é o tipo (- arquivo, d pasta) e os outros nove são três trios rwx (dono, grupo, outros), com - onde falta a permissão. Em octal, cada letra vale um número: r = 4, w = 2, x = 1, e você soma por trio. O chmod muda isso; o umask define o padrão de arquivos novos.

Exemplo resolvido: do número para as letras, e de volta
755 são três dígitos: dono 7 = 4+2+1 = rwx; grupo 5 = 4+0+1 = r-x; outros 5 = r-x. Fica rwxr-xr-x: o dono faz tudo, os outros leem e executam. É o normal de script e de pasta.
644: dono 6 = 4+2 = rw-; grupo e outros 4 = r--. Fica rw-r--r--: o normal de um arquivo de texto.
600 = rw-------: só o dono lê e escreve. É o que se espera de um arquivo privado.
O umask do meu Git Bash mostrou 0022. Como regra de bolso, um arquivo novo começa em 666 e o umask tira 022: 666 − 022 = 644. Conferi: todo arquivo que criei saiu como -rw-r--r--.

Brinque com a calculadora. Marque as caixas e veja o número; digite um número e veja as caixas:

$ ls -l log.txt
-rw-r--r-- 1 voce 197609 125 Nov  6 14:00 log.txt      # tipo(-) dono(rw-) grupo(r--) outros(r--)
$ umask
0022
$ chmod 755 script.sh     # dono rwx, grupo e outros r-x   (não testado aqui, num Linux de verdade)
$ chmod +x script.sh      # liga o x para todos
$ chmod u+x script.sh     # liga o x só para o dono (u = user)
PS> icacls log.txt        # no Windows as permissões são ACLs, outro modelo
Não testado aquiO chmod e as permissões rwx são conceito de Linux (as páginas da IBM tratam de Linux). Eu só tinha o Git Bash no Windows, e lá o resultado engana: rodei chmod 600 seg.txt e a listagem continuou -rw-r--r-- (644). Um arquivo que começa com #! (um script) já aparece como -rwxr-xr-x sem eu ter dado chmod +x. Ou seja, o bit x no Windows não funciona como no Linux. No PowerShell o equivalente de verdade seria icacls, que usa ACLs; eu só rodei icacls log.txt para ver que existe, não mexi em permissão.
Erro comumDar chmod 777 para 'resolver' um erro de permissão. Isso libera escrita para qualquer usuário. O certo é descobrir quem precisa de qual permissão e dar só isso (a calculadora acima avisa quando você marca tudo).

2Variáveis de ambiente e PATH

Digito git em qualquer pasta e funciona. Digito o nome do meu script e dá erro. Como o shell decide onde procurar?

Intuição. O shell tem uma memória de post-its: nomes com valores. São as variáveis. Uma delas, o PATH, é uma lista de pastas. Quando você digita só um nome, o shell abre cada pasta da lista, na ordem, procurando um programa com esse nome. Se não achar, desiste.

Definição. Uma variável de ambiente é um nome com valor que o shell guarda. Só os programas que ele inicia (os 'filhos') enxergam a variável se ela for exportada. O PATH é a variável com as pastas de busca, separadas por : no bash e por ; no Windows. No PowerShell lê-se e escreve-se com $env:NOME.

Exemplo resolvido: o filho só enxerga o que foi exportado
X=um cria a variável no shell. Quando um programa filho tenta lê-la (bash -c 'echo "filho:[$X]"'), vê filho:[]: vazio.
Depois de export X, o mesmo comando mostra filho:[um]. O export é o que repassa a variável aos filhos.
which git mostrou /ucrt64/bin/git no Git Bash, e (Get-Command git).Source mostrou C:\Program Files\Git\cmd\git.exe no PowerShell. Cada shell tem a sua lista de pastas e achou o git em um lugar diferente. Conferi abrindo o bash.exe da pasta do Git for Windows: esse /ucrt64 existe dentro da instalação (ucrt64\bin\git.exe) e não há pasta mingw64. O prefixo depende da versão do Git for Windows (versões mais antigas costumam mostrar /mingw64/bin/git; isso eu não testei), então o caminho no seu computador pode ser outro.
$ X=um
$ bash -c 'echo "filho:[$X]"'    # o programa filho não vê a variável
filho:[]
$ export X
$ bash -c 'echo "filho:[$X]"'
filho:[um]
$ which git                       # onde o shell achou o programa (o caminho varia com a versão do Git)
/ucrt64/bin/git
$ type cd                         # nem todo comando é programa: o cd é do próprio shell
cd is a shell builtin
$ N=Ana; echo "oi $N"; echo 'oi $N'     # aspas duplas expandem a variável; simples não
oi Ana
oi $N
PS> $env:MINHA = 'valor'          # vale para esta sessão e para os filhos
PS> (Get-Command git).Source
C:\Program Files\Git\cmd\git.exe
PS> [Environment]::SetEnvironmentVariable('TG_X','1','Process')   # escopo Process: só nesta sessão

No PowerShell a variável tem três escopos: Process (a sessão atual), User e Machine (Microsoft Learn, about_Environment_Variables). Eu rodei o escopo Process e conferi que um powershell filho enxerga $env:MINHA.

Não testado aquiGravar uma variável permanente. No PowerShell seria [Environment]::SetEnvironmentVariable('NOME','valor','User'); no bash, colocar o export no arquivo de perfil, como o ~/.bashrc (a IBM, tutorial 105.1, trata disso). Não rodei nenhum dos dois: o primeiro mexe no registro do seu usuário e eu não quis alterar o computador por causa de um teste.
Erro comumAchar que o valor dura para sempre. export X=1 e $env:X = '1' valem só enquanto aquela janela existir. Fechou o terminal, perdeu. Outro erro clássico: colocar segredo (senha, chave de API) em variável e depois imprimir ou salvar o ambiente. Variáveis ajudam a não deixar segredo no código, mas continuam sendo texto que quem acessa a sessão consegue ver.

3Scripts: comandos guardados em um arquivo

Repeti os mesmos cinco comandos pela terceira vez no mesmo dia. Dá para escrever uma vez só?

Intuição. Um script é uma receita: os comandos que você digitaria, na ordem, num arquivo. O shell lê o arquivo e executa linha por linha. A vantagem é repetir sem errar e poder usar decisões (if) e repetições (for).

Definição. A primeira linha de um script bash costuma ser o shebang (#!/bin/bash), que diz qual shell executa. Cada comando termina com um código de saída: 0 é sucesso, qualquer outro número é falha. O código do último comando fica na variável $?. Para rodar pelo caminho, o arquivo precisa de permissão de execução.

Base: tutorial 105.2 da IBM (scripts), mais os testes que fiz.

#!/bin/bash
# saudacao.sh  (os trechos sublinhados explicam)
nome="${1:-mundo}"            # $1 ; se vier vazio, usa "mundo"
for i in 1 2 3; do           # repete 3 vezes
  echo "$i: oi, $nome"
done
if [ "$nome" = "erro" ]; then exit 1; fi    # exit 1
exit 0
Exemplo resolvido: rodando e lendo o código de saída
./saudacao.sh Ana imprime 3 linhas (1: oi, Ana, 2: oi, Ana, 3: oi, Ana) e o echo $? logo depois mostra 0.
bash saudacao.sh erro imprime as mesmas 3 linhas, mas termina com exit 1: o $? vale 1.
saudacao.sh sem ./ falha com command not found e o $? vale 127: a pasta atual não está no PATH, então o shell não procurou ali.
$ ./saudacao.sh Ana
1: oi, Ana
2: oi, Ana
3: oi, Ana
$ echo $?
0
$ bash saudacao.sh erro > /dev/null; echo $?
1
$ saudacao.sh
bash: saudacao.sh: command not found
$ echo $?
127
PS> .\saud.ps1 Ana        # o equivalente em PowerShell: .\ na frente também é obrigatório
PS> powershell -NoProfile -File .\saud.ps1 erro; $LASTEXITCODE
1

O script do PowerShell que usei (saud.ps1) é este. Repare na chave em ${i}:

param($nome = "mundo")                         # param
foreach ($i in 1..3) { "${i}: oi, $nome" }     # ${i}
if ($nome -eq "erro") { exit 1 }
exit 0
Erro comumTrês armadilhas reais. (1) Esquecer o ./: o script não está no PATH (código 127, acima). (2) Escrever "$i: oi" no PowerShell. Rodei assim e deu Referência de variável inválida. ':' não era seguido de um caractere de nome de variável válido: o PowerShell leu $i: como se fosse uma unidade (como C:). O conserto é "${i}: oi" ou "$($i): oi". (3) Confiar no chmod +x do Git Bash: no Windows ele não é a fonte da verdade (veja o aviso da seção 1); rodar com bash saudacao.sh sempre funciona.
Não testado aquiA política de execução do PowerShell (Set-ExecutionPolicy), que pode bloquear scripts .ps1 em outros computadores. No ambiente em que testei ela estava em Bypass, então não vi o bloqueio. Se você receber um erro de 'execução de scripts desabilitada', procure a documentação da Microsoft antes de mudar a política: ela é uma configuração de segurança.
Complemento do complemento: if, for e case (IBM 105.2)

A IBM apresenta as estruturas de controle do shell: if ... then ... fi para decidir, for ... do ... done e while para repetir, case para várias opções, e a substituição de comando ($(comando), que usa a saída de um comando como valor). Usei if e for no script acima e rodei; while, case e $(...) li, mas não testei.

4Fechamento do capítulo

Cola da prova

  • Permissão = dono, grupo e outros × r (4), w (2), x (1). 755 = rwxr-xr-x; 644 = rw-r--r--; 600 = rw-------.
  • Evite chmod 777. No Git Bash do Windows o chmod e o bit x não se comportam como no Linux.
  • Variável de ambiente: o filho só vê o que foi exportado. PowerShell: $env:NOME. Dura só a sessão (Process).
  • PATH é a lista de pastas onde o shell procura o programa. Fora do PATH, use caminho: ./script.sh ou .\script.ps1.
  • Script: shebang, comandos, exit. Código 0 = sucesso, outro = falha, em $?. Comando não achado = 127.
  • PowerShell: "${i}: texto" (com chaves), senão $i: vira unidade.

Teste rápido

Pergunta 1

Qual é a notação simbólica de chmod 640?

6 = 4+2 = rw- (dono); 4 = r-- (grupo); 0 = --- (outros). Dá rw-r-----.
Pergunta 2

Você roda X=um (sem export) e depois um programa filho tenta ler $X. O que ele vê?

Sem export, a variável é só do shell. Depois do export X, o filho enxerga um.
Pergunta 3

meu_script.sh está na pasta atual, mas digitar só o nome dá command not found (código 127). Por quê?

O shell só procura nas pastas do PATH. Com ./ você dá o caminho e ele não precisa procurar.
