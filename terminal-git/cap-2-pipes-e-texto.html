1Três canais: entrada, saída e erro

Mandei o resultado de um comando para um arquivo, e a mensagem de erro apareceu na tela mesmo assim. Por quê?

Intuição. Todo comando tem três tubulações. Por uma entra o que ele lê (a entrada, normalmente o teclado). Por outra sai o resultado (a saída). Por uma terceira sai o aviso de que algo deu errado (o erro). Saída e erro caem na mesma tela, e por isso parecem uma coisa só, mas são canais separados.

Definição. Os canais têm número: 0 é a entrada padrão (stdin), 1 é a saída padrão (stdout) e 2 é o erro padrão (stderr). O redirecionamento manda um canal para um arquivo: > manda a saída e sobrescreve; >> manda a saída e acrescenta; 2> manda só o erro; 2>&1 junta o erro na saída.

Exemplo resolvido: sobrescrever, acrescentar e separar o erro
echo um > a.txt cria o arquivo com um. Depois echo dois > a.txt apaga o conteúdo e deixa só dois.
echo tres >> a.txt acrescenta. O cat a.txt mostra 2 linhas: dois e tres.
ls nao_existe > out.txt: o out.txt fica com 0 bytes e a mensagem de erro aparece na tela. O erro não foi pelo canal 1.
ls nao_existe 2> erros.txt manda o erro para o arquivo. E ls nao_existe > out.txt 2>&1 manda os dois para o mesmo lugar. Em todos os casos o código de saída do ls foi 2.
$ echo um > a.txt
$ echo dois > a.txt        # sobrescreveu: o "um" sumiu
$ echo tres >> a.txt       # >> acrescenta ao final
$ cat a.txt
dois
tres
$ ls nao_existe > out.txt  # o erro NÃO vai para o arquivo
ls: cannot access 'nao_existe': No such file or directory
$ ls nao_existe 2> erros.txt          # só o erro vai para o arquivo
$ ls nao_existe > out.txt 2>&1        # saída e erro juntos no arquivo
PS> Get-ChildItem nao_existe 2> erros_ps.txt   # no PowerShell, 2> funciona igual

No PowerShell os mesmos operadores existem (>, >>, 2>, 2>&1). Duas diferenças que vi: o erro é um objeto (a mensagem sai no idioma do Windows, aqui em português) e a codificação do arquivo criado com > muda entre versões do PowerShell. No 5.1 que usei, o arquivo saiu em UTF-16 LE (os bytes começam com 255 254 e cada letra vem seguida de um byte 0), e não em UTF-8. Isso tem consequência prática: o Git não lê um .gitignore gravado assim (o teste está no capítulo 5). Para arquivos de configuração, grave com Set-Content -Encoding ascii (ou utf8), ou crie o arquivo pelo Git Bash, e confira o resultado.

Erro comumUsar > querendo acrescentar. Ele apaga o arquivo antes, sem avisar. Se o arquivo importa, use >> ou mande para um nome novo. E lembre que o erro não acompanha o >: precisa do 2>&1, e depois do >. A ordem importa: rodei ls nao_existe 2>&1 > out.txt e o erro continuou na tela (o out.txt ficou vazio); o certo é ls nao_existe > out.txt 2>&1. O simulador desta apostila faz igual.

Com o pipe.

2Pipe: uma linha de montagem

Contar quantas linhas de erro existem em um log: preciso achar as linhas, salvar num arquivo e contar o arquivo? Tem jeito mais curto?

Intuição. Uma linha de montagem: cada estação recebe a peça da estação anterior, faz a sua parte e passa adiante. Cada comando é uma estação pequena que faz uma coisa só, e você monta a linha que precisa.

Definição. O pipe (|) liga a saída de um comando na entrada do próximo, sem arquivo intermediário. Só o canal 1 passa: o erro continua indo para a tela. No PowerShell o pipe também existe, mas leva objetos e não texto.

Exemplo resolvido: contando erros com três estações
cat log.txt | grep ERRO | wc -l. O log.txt tem 6 linhas.
Estação 1 (cat): entrega as 6 linhas. Estação 2 (grep ERRO): deixa passar só as que têm a palavra, 3 linhas (10:03, 10:07 e 10:12).
Estação 3 (wc -l): conta as linhas que chegaram e responde 3. Sem arquivo intermediário.
$ cat log.txt | grep ERRO | wc -l      # 6 linhas -> 3 linhas -> o número 3
3
PS> Get-Content log.txt | Select-String ERRO | Measure-Object   # no PowerShell, Count = 3
PS> Get-ChildItem -File | Sort-Object Length -Descending | Select-Object -First 2 Name,Length
Name       Length
----       ------
log.txt       125
vendas.csv     78

Repare no último exemplo: o PowerShell ordenou pela propriedade Length (um número), sem tratar nada como texto. Essa é a diferença de fundo: no bash você interpreta colunas de texto; no PowerShell você pede propriedades de objetos. (Fonte para o pipeline de objetos: Microsoft Learn, about_Pipelines.)

As ferramentas de texto.

3grep, sort, uniq, cut, sed e awk

Já sei montar a linha de montagem. Quais são as estações que mais uso?

Intuição. Texto de computador (log, CSV, saída de comando) é uma pilha de linhas. Estas ferramentas filtram linhas (grep), ordenam, contam repetidas, recortam colunas e fazem trocas e contas simples. Juntas, respondem perguntas sem abrir o arquivo.

FerramentaPara quêEquivalente no PowerShell
grep ERRO log.txtsó as linhas com o padrão (-i ignora maiúsculas, -c conta, -n numera, -v inverte)Select-String -Pattern ERRO log.txt (cuidado: ignora maiúsculas e minúsculas por padrão, como o grep -i; para diferenciar, acrescente -CaseSensitive. Num teste com ERRO e erro no arquivo, deu 2 sem a opção e 1 com ela)
sort, sort -rnordena; -r inverte; -n compara como númeroSort-Object
uniq -cjunta linhas vizinhas iguais e contaGroup-Object
cut -d, -f1recorta uma coluna (-d separador, -f campo)Import-Csv e a propriedade
sed 's/ERRO/ERRO!/'troca texto em cada linha-replace 'ERRO','ERRO!'
awk -F, '{...}'separa campos e faz conta, filtro e somaImport-Csv + Measure-Object

Definição. grep procura um padrão e imprime as linhas que casam. sed é um editor de fluxo: o uso mais comum é a troca s/antigo/novo/. awk divide cada linha em campos ($1, $2...) e executa uma ação. Aqui só o básico; cada um é uma linguagem inteira.

Exemplo resolvido: qual erro é o mais comum, e quanto vendi
grep ERRO log.txt | cut -d' ' -f3- | sort | uniq -c | sort -rn. O grep deixa as 3 linhas de erro; o cut pega do campo 3 em diante (disco cheio, timeout, timeout).
O sort agrupa as iguais lado a lado; o uniq -c conta: 2 timeout e 1 disco cheio; o sort -rn põe o maior primeiro. Resposta: timeout, com 2 ocorrências.
Vendas: vendas.csv tem 5 vendas (fora o cabeçalho). O awk multiplica quantidade por preço e soma: 10×2 + 3×15 + 25×1 + 5×2 + 2×15 = 20 + 45 + 25 + 10 + 30 = 130.
No PowerShell: Import-Csv vendas.csv | ForEach-Object { [int]$_.qtd * [int]$_.preco } | Measure-Object -Sum também dá 130.
$ grep ERRO log.txt | cut -d' ' -f3- | sort | uniq -c | sort -rn
      2 timeout
      1 disco cheio
$ awk -F, 'NR>1 {s+=$2*$3} END {print s}' vendas.csv   # NR>1  s+=$2*$3
130
$ sed 's/ERRO/ERRO!/' log.txt | head -3   # troca só no que passa na tela; o arquivo não muda
10:01 INFO login ana
10:03 ERRO! disco cheio
10:05 INFO login bia
PS> (Select-String -Pattern ERRO log.txt).Count
3
PS> Import-Csv vendas.csv | ForEach-Object { [int]$_.qtd * [int]$_.preco } | Measure-Object -Sum | Select-Object -ExpandProperty Sum
130
Erro comumDois tropeços que eu mesmo vi rodando. (1) Usar uniq -c sem sort antes. O uniq só junta linhas vizinhas: com as linhas b, a, b ele conta 1 b, 1 a, 1 b; com sort antes, sai 1 a e 2 b. (2) Aspas duplas no programa do awk. Em awk -F, "NR>1 {s+=$2*$3} END {print s}" o bash troca $2 e $3 por vazio antes do awk ver e o resultado é awk: cmd. line:1: NR>1 {s+=*} END {print s} com syntax error. Use aspas simples: elas não deixam o bash mexer no texto.

Nota sobre as fontes: o artigo da IBM sobre manipulação de texto (2012) descreve grep, sed, awk, sort, cut e uniq; as flags usadas aqui eu conferi rodando. No simulador da demo, awk e sed só aceitam as formas simples mostradas, nada de programa completo.

4Fechamento do capítulo

Cola da prova

  • Três canais: 0 entrada, 1 saída, 2 erro. Saída e erro caem na mesma tela, mas são separados.
  • > sobrescreve; >> acrescenta; 2> só o erro; 2>&1 junta o erro na saída.
  • Pipe (|) liga a saída de um comando na entrada do próximo. O erro não passa sem 2>&1.
  • bash: pipe de texto. PowerShell: pipe de objetos (Where-Object, Sort-Object, Select-Object).
  • grep filtra, sort ordena, uniq -c conta vizinhas (precisa de sort antes), cut recorta, sed troca, awk faz conta por campo.
  • Programa do awk e do sed vai entre aspas simples.

Teste rápido

Pergunta 1

Você roda echo novo > notas.txt em um arquivo que já tinha 10 linhas. O que sobra?

O > troca o conteúdo inteiro. Para manter as 10 linhas e acrescentar, o certo seria >>.
Pergunta 2

ls nao_existe | grep nao mostra a mensagem de erro na tela e o grep recebe 0 linhas. Por quê?

O erro é o canal 2 e o pipe só carrega o canal 1. Com 2>&1 antes do pipe o erro vira parte da saída.
Pergunta 3

Por que uniq -c costuma vir depois de sort?

Sem ordenar, b a b vira três contagens de 1. Ordenado (a b b), vira 1 a e 2 b.
