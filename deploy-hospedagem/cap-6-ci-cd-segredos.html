1CI/CD e DevOps: deploy a cada push

Publicar à mão funciona uma vez. E na vigésima, com três pessoas mexendo no mesmo site?

Intuição. É uma esteira de fábrica. Cada vez que alguém envia código, uma máquina roda a mesma lista de tarefas: baixar, instalar, testar, montar. Se um teste quebrar, a esteira para antes de publicar algo quebrado.

Definição. Integração contínua (CI): enviar código com frequência e rodar build e testes a cada envio. Entrega contínua: o código fica sempre pronto para subir, mas uma pessoa aprova. Implantação contínua: sobe para produção automaticamente, sem aprovação. DevOps é o conjunto de práticas e cultura que une desenvolvimento e operação, e inclui infraestrutura como código e monitoramento. (IBM.)

Exemplo resolvido: lendo a esteira simulada
A esteira tem 5 etapas: baixar o código, instalar dependências, rodar os testes, gerar o build e publicar.
Com os testes passando, no modo só CI, as 4 primeiras passam e a etapa 5 "não roda": o resultado é o aviso de que está tudo certo.
No modo entrega contínua, a etapa 5 fica aguardando até alguém aprovar. No modo implantação contínua, ela roda sozinha, e falha se o segredo de deploy não estiver cadastrado.
Se os testes falham, as etapas 4 e 5 ficam "não rodou" e o site no ar continua sendo a versão anterior. É esse o valor da esteira.

Um exemplo de arquivo de workflow do GitHub Actions com essas 5 etapas. Eu conferi que o YAML é válido (um parser leu 1 job e 5 passos), mas não rodei no GitHub:

# .github/workflows/publicar.yml   (EXEMPLO, nao rodou no GitHub)
name: publicar
on:
  push:
    branches: [main]
jobs:
  build-e-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # confira a versao atual da action
      - name: Instalar dependencias
        run: npm ci
      - name: Rodar os testes
        run: npm test
      - name: Gerar o build
        run: npm run build
      - name: Publicar
        run: ./deploy.sh dist              # seu script de deploy
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}   # veio do cofre do GitHub, nunca do repositorio
Não testado aquiEsse workflow é um exemplo genérico. O deploy.sh não existe, os comandos npm supõem um projeto Node e a versão da action pode estar desatualizada. A documentação do GitHub diz que o segredo é criado em Settings, na parte de segurança, em Secrets and variables e depois Actions (lida em 06/11/2026); não vi a tela.
Erro comumFazer a esteira publicar mesmo com o teste falhando (por exemplo, deixando o deploy numa etapa que não depende do teste). O sentido da CI é barrar. Na demo, derrube os testes no modo de implantação contínua e veja que nada vai ao ar.

Em variáveis de ambiente e segredos.

2Variáveis de ambiente e segredos

Meu programa precisa de uma senha de banco, uma chave de API. Onde eu escrevo isso?

Intuição. No código, nunca. Código vai para o repositório, o repositório pode ser público e o histórico guarda tudo. O valor sensível mora fora do código, em um lugar que o programa consulta na hora de rodar: a variável de ambiente.

Definição. Variável de ambiente é um par nome/valor que o sistema entrega ao programa quando ele começa. O mesmo código roda em lugares diferentes (seu computador, a esteira, a produção) com valores diferentes, sem mudar uma linha. Segredo é um valor sensível (senha, token, chave). Boas práticas de gestão de segredos, segundo a IBM: cofre central, rotação (trocar de tempos em tempos), mínimo privilégio e registro de acesso. A IBM não trata de variáveis de ambiente como tema próprio; o uso aparece no tutorial do Code Engine.

Exemplo resolvido: a mesma variável, nos dois shells
Programa de teste: um script Node de uma linha que mostra a variável PORTA.
No Git Bash: PORTA=8080 node -e '...' define a variável só para aquele comando. Resultado: porta: 8080 | outra: undefined. Uma variável que não foi definida (OUTRA) aparece como undefined, e não dá erro.
No PowerShell: $env:PORTA = "8080" define na sessão; Remove-Item Env:PORTA tira. Rodei o mesmo script antes e depois: porta: 8080 e porta: undefined.
$ PORTA=8080 node -e 'console.log("porta:", process.env.PORTA, "| outra:", process.env.OUTRA)'
porta: 8080 | outra: undefined
PS> "console.log('porta:', process.env.PORTA)" | Set-Content -Encoding ascii t.js   # um arquivo de teste
PS> $env:PORTA = "8080"; node t.js
porta: 8080
PS> Remove-Item Env:PORTA; node t.js
porta: undefined

Rodado em 06/11/2026, em pasta temporária. No PowerShell, node -e com aspas é chato de escrever, por isso usei um arquivo. As variáveis aqui valem só para a sessão; gravar variável permanente no Windows não foi testado.

Em plataformas e em esteiras, a variável é cadastrada no painel ou no cofre de segredos do serviço (no GitHub Actions, a sintaxe ${{ secrets.NOME }} do exemplo acima). Conteúdo de segredo pode aparecer em log se você mandar imprimir: não imprima.

Erro comumColocar a chave "só para testar" direto no código e prometer tirar depois. O histórico do Git guarda mesmo que você apague no commit seguinte (a seção 4 mostra isso rodando). Se o repositório for público, qualquer um lê. Se um dia a chave real entrar no código, trate como vazada.

Com o .gitignore.

3.env, .gitignore e a armadilha do PowerShell

Tenho um arquivo local com as variáveis. Como garanto que o Git nunca o envie?

Intuição. O .gitignore é a lista de "não levar" do Git. Entra o que é segredo (.env), o que é gerado (node_modules/, dist/) e o que é só seu. O que vai para o repositório é um modelo sem valores, o .env.example, para quem clonar saber quais variáveis precisa criar.

Definição. .env é, por convenção, um arquivo de texto com linhas NOME=valor que alguns programas leem no início. O .gitignore usa padrões: .env* casa com .env e .env.local, e uma linha !.env.example reabre uma exceção. O comando git check-ignore -v arquivo diz qual regra decidiu, mesmo que o arquivo nem exista. (Git, documentação do gitignore.)

Exemplo resolvido: testar as regras sem criar o arquivo de segredo
Num repositório temporário, escrevi um .gitignore com .env*, !.env.example e node_modules/. Não criei nenhum arquivo .env: o check-ignore responde pelo caminho.
.env e .env.local casam com a regra da linha 1: ignorados. .env.example casa com a linha 2, que começa com !: não é ignorado, vai para o repositório.
Um erro típico: usar só .env no .gitignore. Com ele, .env é ignorado, mas .env.local não (testei: o git check-ignore não achou regra e saiu com código 1).
$ printf '.env*\n!.env.example\nnode_modules/\n' > .gitignore
$ git check-ignore -v .env
.gitignore:1:.env*	.env
$ git check-ignore -v .env.local
.gitignore:1:.env*	.env.local
$ git check-ignore -v .env.example
.gitignore:2:!.env.example	.env.example         # o "!" mostra que a regra libera este arquivo
$ printf '.env\n' > .gitignore ; git check-ignore -v .env.local ; echo "codigo: $?"
codigo: 1                                            # .env.local NAO foi ignorado

Rodado em 06/11/2026. Note que o check-ignore sai com código 0 mesmo quando a regra é uma exceção com !; leia o texto da saída, não só o código.

A armadilha do PowerShell. Num PowerShell 5.1 limpo (powershell.exe -NoProfile), o operador > grava o arquivo em UTF-16 (bytes iniciais 255,254). O Git espera texto simples, e o .gitignore deixa de funcionar. Eu rodei dos dois jeitos num repositório temporário, com uma pasta node_modules de verdade:

PS> "node_modules/" > .gitignore
PS> [IO.File]::ReadAllBytes(".gitignore")[0..7] | ForEach-Object { '{0:X2}' -f $_ }    # primeiros bytes
FF FE 6E 00 6F 00 64 00                      # FF FE = marca de UTF-16; cada letra ocupa 2 bytes
PS> git status --short
?? .gitignore
?? index.html
?? node_modules/                            # o Git NAO entendeu a regra: a pasta apareceu

PS> "node_modules/" | Set-Content -Encoding ascii .gitignore
PS> git status --short
?? .gitignore
?? index.html                               # agora node_modules/ sumiu: foi ignorada

Rodado em 06/11/2026 com powershell.exe -NoProfile (5.1) e Git 2.56. Testei quatro jeitos numa pasta temporária com node_modules de verdade: > gravou UTF-16 e o Git não ignorou a pasta; Set-Content -Encoding ascii funcionou; Set-Content -Encoding utf8 e Out-File -Encoding utf8 gravaram UTF-8 com BOM (bytes 239,187,191) e neste Git também funcionou. Eu não provei por que o > se comporta diferente em outras máquinas (perfil, versão do PowerShell), então não afirmo a causa: o resultado pode variar, e a regra segura é gravar com Set-Content -Encoding ascii, que foi o jeito testado e não depende de BOM. No Git Bash o > não tem esse problema.

Erro comumCriar o .gitignore depois de já ter feito commit do arquivo. O .gitignore só vale para arquivos que o Git ainda não rastreia. Quem já foi commitado continua no histórico (próxima seção).

4Se o segredo foi commitado

Commitei uma chave sem querer. Apago o arquivo e tudo certo?

Intuição. Não. É como mandar uma carta e perceber o erro: tirar a carta da sua mesa não a tira da caixa do correio. O Git guarda o histórico, e quem clonou antes, ou um robô que varre repositórios públicos, já pode ter copiado.

Definição. git rm --cached arquivo tira o arquivo do rastreamento atual, mas o commit antigo continua no histórico, e o conteúdo dele continua legível. Limpar o histórico (com ferramentas como git filter-repo ou BFG) reduz o risco, mas não desfaz o que já foi copiado. Por isso, o passo obrigatório é revogar e trocar a credencial: no serviço que emitiu a chave, invalide a antiga e crie outra. A IBM recomenda rotação e mínimo privilégio como práticas de segredos.

Exemplo resolvido: o segredo ainda está no histórico, rodado
Num repositório temporário, criei um arquivo com um valor falso (CHAVE_FALSA_123) e fiz o commit "sem querer".
Depois pus o nome do arquivo no .gitignore, rodei git rm --cached e fiz um segundo commit. O git status ficou limpo: parece resolvido.
Mas o git log --all --oneline -S CHAVE_FALSA_123 listou 2 commits que mexeram nessa string, e o git show HEAD~1:segredo.txt imprimiu a chave. O valor segue legível no commit anterior.
$ echo "CHAVE_FALSA_123" > segredo.txt ; git add . ; git commit -qm "sem querer"
$ echo "segredo.txt" > .gitignore ; git rm -q --cached segredo.txt ; git add .gitignore ; git commit -qm "tira do rastreio"
$ git status --short                    # vazio: parece que acabou
$ git log --all --oneline -S CHAVE_FALSA_123
262811c tira do rastreio
5d93383 sem querer
$ git show HEAD~1:segredo.txt
CHAVE_FALSA_123                         # continua ali, no commit anterior

Rodado em 06/11/2026, com valor inventado. Os hashes mudam a cada pessoa.

OrdemO que fazer se vazou
1Revogar e trocar a credencial no serviço de origem. É o passo que realmente fecha a porta.
2Guardar a nova em variável de ambiente ou cofre, nunca no código.
3Pôr o arquivo no .gitignore e remover do rastreamento (git rm --cached).
4Se quiser, limpar o histórico (git filter-repo ou BFG) e avisar quem clonou.
5Olhar o log de acesso do serviço para ver se alguém usou a chave.
Não testado aquiA limpeza de histórico (git filter-repo, BFG) e git push --force não foram testados aqui. São operações que reescrevem o histórico compartilhado; faça com cuidado e combine com a equipe antes.
Erro comumAchar que o passo 3 resolve. Ele só impede um novo vazamento. Quem tem acesso ao histórico antigo continua vendo a chave. Sem o passo 1, a chave segue valendo.

5Fechamento do capítulo

Cola da prova

  • CI: build e testes a cada envio. Entrega contínua: pronto para subir, com aprovação. Implantação contínua: sobe sozinho.
  • Teste falhou: a esteira barra o deploy; o site no ar continua na versão anterior.
  • Segredo não vai no código. Mora em variável de ambiente ou cofre (no GitHub Actions: secrets).
  • .env no .gitignore; no repositório vai o .env.example sem valores. O padrão .env* cobre .env.local e .env sozinho, não.
  • PowerShell 5.1: o > pode gravar UTF-16 e quebrar o .gitignore. Use Set-Content -Encoding ascii (testado); utf8 grava BOM, que funcionou no meu Git mas não é a opção segura.
  • git rm --cached não tira do histórico. O passo obrigatório é revogar e trocar a credencial.

Teste rápido

Pergunta 1

Na demo, no modo implantação contínua, os testes falham. O que acontece com o site no ar?

A esteira para na etapa dos testes. As etapas de build e de publicar não rodam.
Pergunta 2

Você commitou uma chave de API e logo fez git rm --cached num commit seguinte. O que ainda precisa ser feito, obrigatoriamente?

O histórico guarda o conteúdo antigo. A chave precisa ser invalidada no serviço que a emitiu.
Pergunta 3

O .gitignore tem só a linha .env. O que acontece com um arquivo .env.local?

Na execução que fiz, o git check-ignore não achou regra para .env.local. O padrão .env* cobre os dois.
Pergunta 4

Num PowerShell 5.1 limpo, "node_modules/" > .gitignore deixou a pasta aparecer no git status. Por quê?

A solução é gravar com Set-Content -Encoding ascii e conferir de novo com git status.
