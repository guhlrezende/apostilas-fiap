1Antes de publicar: a pasta e o teste local

Tenho três caminhos pela frente. O que é igual em todos eles?

Intuição. Publicar um site estático é entregar uma pasta. Antes de escolher o caminho, a pasta tem de estar certa: o servidor procura um arquivo de entrada e segue os caminhos que você escreveu.

Definição. Pré-requisitos: um index.html na raiz da pasta publicada, e o CSS, o JS e as imagens com caminhos relativos (estilo.css, não /estilo.css). Servidores Linux tratam Sobre.html e sobre.html como arquivos diferentes. Se o projeto tem etapa de build, o que se publica é a pasta gerada (dist, build ou public), não a do código-fonte.

Exemplo resolvido: conferir antes, no computador
Entre na pasta do site e rode python -m http.server 8765 --bind 127.0.0.1. Abra http://127.0.0.1:8765 no navegador. Se abrir direitinho assim, os caminhos funcionam num servidor de verdade.
Conferi com o curl: pedir / deu 200; pedir um nome que não existia deu 404, como no capítulo 1.
O mesmo vale no PowerShell: python -m http.server 8765 --bind 127.0.0.1 é um comando do Python, igual nos dois shells.
$ python -m http.server 8765 --bind 127.0.0.1     # na pasta do site; Ctrl+C encerra
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8765/
200
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8765/nada
404

Rodado em 06/11/2026, num servidor local. Maiúsculas e minúsculas no nome do arquivo (Index.html contra index.html) dependem do sistema: segundo a minha pesquisa de apoio, num servidor Linux são arquivos diferentes. Não testei num Linux.

Erro comumCaminho absoluto que só funciona na raiz do domínio. Um erro comum: um /estilo.css funciona quando o site mora em meusite.example/, mas quebra quando mora em usuario.github.io/projeto/ (subpasta). Use caminho relativo, e abra o site publicado para conferir o CSS carregando.

2Caminho A: GitHub Pages

Já uso Git e GitHub. Dá para o site sair do repositório?

Intuição. O GitHub Pages lê uma pasta de uma branch do seu repositório e publica o conteúdo como site. Atualizar é dar git push.

Definição. Segundo a documentação do GitHub (lida em 06/11/2026): em Settings do repositório existe a seção Pages, onde se escolhe publicar a partir de uma branch e de uma pasta (por exemplo, /docs da main). O arquivo de entrada (index.html) precisa estar no topo da pasta escolhida. Mudanças podem levar até 10 minutos para aparecer. Para donos de conta no plano Free, o repositório precisa ser público. Quando se publica a partir de uma branch, o GitHub Pages usa o Jekyll por padrão para montar o site; a documentação diz que um arquivo vazio chamado .nojekyll na raiz da fonte de publicação desliga isso (confirmado na leitura de 06/11/2026).

Exemplo resolvido: o Git de ponta a ponta, rodado em um remoto de mentira
Não posso empurrar para um GitHub de verdade (isso seria publicar algo). Então criei um repositório "remoto" numa pasta local (git init --bare) e repeti os comandos que você usaria: git init, add, commit, branch -M main, remote add origin e push -u origin main.
A saída confirmou: [new branch] main -> main e branch 'main' set up to track 'origin/main'. O git status -sb ficou em ## main...origin/main, sem diferença entre local e remoto.
Contra o GitHub de verdade, a única diferença é a URL do origin, que fica https://github.com/SEU_USUARIO/SEU_REPO.git (e o login).
$ git init -q -b main            # o -b main escolhe o nome da branch inicial
$ git add .
$ git commit -qm "Primeira versao do site"
$ git branch -M main
$ git remote add origin ../remoto.git     # no GitHub: https://github.com/SEU_USUARIO/SEU_REPO.git
$ git push -u origin main
To ../remoto.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git remote -v
origin	../remoto.git (fetch)
origin	../remoto.git (push)
$ git status -sb
## main...origin/main

Rodado em 06/11/2026, num remoto local. Usei só um texto de teste e nenhuma conta do GitHub.

Não testado aquiO push para o GitHub, ativar o Pages em Settings e abrir o endereço gerado não foram feitos. Também não descrevo botões ou telas do painel: a documentação diz onde fica a opção, mas não lista os rótulos exatos do menu, e eu não vi a tela. Siga a documentação oficial atual.
Erro comumEsperar a mudança aparecer na hora. A documentação fala em até 10 minutos, e o navegador ainda pode mostrar a versão guardada. Teste em aba anônima antes de achar que o push falhou. E lembre-se de que o conteúdo é público: tire do repositório o que não pode ser visto (veja o capítulo 6).

3Caminho B: plataforma de deploy (Cloudflare Pages, Netlify ou Vercel)

Quero uma plataforma feita para publicar sites. O que elas têm em comum?

Intuição. Você entrega a pasta (arrastando, enviando por comando ou conectando o repositório) e a plataforma devolve um endereço. As três fazem o trabalho de servidor por você: é PaaS (capítulo 4) especializado em sites.

Definição. O que cada documentação oficial diz (lidas em 06/11/2026, exceto a da Vercel, lida na pesquisa de apoio do mesmo dia):

PlataformaFormas de enviar o site, segundo a documentação
Cloudflare Pagesarrastar a pasta no painel (Direct Upload) ou usar a linha de comando do wrangler
Netlifyarrastar a pasta, conectar um repositório Git (cada push publica de novo) ou usar a CLI; a página lida não lista os comandos da CLI
VercelGit (a cada push), CLI, arrastar a pasta ou API

Para o Cloudflare Pages, a documentação (Direct Upload) traz o wrangler pages deploy e o --branch para preview, que conferi na leitura de 06/11/2026; o login e o project create vêm da pesquisa de apoio do mesmo dia. Os passos de linha de comando (NOME_DA_PASTA é a pasta com o site pronto). O mesmo funciona no Git Bash e no PowerShell:

$ npx wrangler login                          # abre o navegador para você entrar na conta
$ npx wrangler pages project create           # pergunta o nome do projeto e a branch de produção
$ npx wrangler pages deploy NOME_DA_PASTA     # envia a pasta e publica
$ npx wrangler pages deploy NOME_DA_PASTA --branch=teste   # publica uma versão de teste (preview)

4Caminho C: um VPS com nginx, SSH e scp ou rsync

Quero entender o que a plataforma faz por baixo. Como eu mesmo ponho um site no ar numa máquina minha?

Intuição. É montar a loja inteira: alugar o espaço (o VPS), pôr o balcão (o servidor web, o nginx), arrumar a mercadoria (os arquivos) e colocar a placa na rua (o DNS). Tudo é seu: o bom e os problemas.

Definição. O nginx é um servidor web: ele escuta a porta 80, olha o endereço pedido e entrega arquivos de uma pasta (root). Cada site é descrito num bloco server, com blocos location para os caminhos. Depois de mudar a configuração é preciso recarregar (nginx -s reload); se a configuração tiver erro, o nginx mantém a antiga funcionando. (nginx.org.) Para chegar à máquina usa-se o SSH (porta 22), e para levar arquivos, scp ou rsync.

Não testado aquiTudo desta seção é exemplo e não foi rodado. Eu não tenho um VPS, o nginx e o rsync não estão instalados aqui e não consegui contratar nada. Os comandos seguem a documentação do nginx e o conhecimento geral de Ubuntu; os valores em maiúsculas (IP_DO_SERVIDOR, USUARIO) são lugares para você trocar.
Exemplo resolvido: a sequência, em ordem
Contratar um VPS com Ubuntu, anotar o IP e cadastrar sua chave SSH pública (veja a apostila de Terminal e Git, capítulo sobre SSH). Preço: confira com o provedor.
Conectar: ssh USUARIO@IP_DO_SERVIDOR. Instalar o servidor: sudo apt update e sudo apt install nginx.
Criar a pasta de destino no servidor (mkdir -p) e levar os arquivos do seu computador com scp (cópia simples) ou rsync (copia só o que mudou), sem esquecer os arquivos que começam com ponto.
Configurar o nginx (exemplo abaixo), ativar o site (link em sites-enabled), testar a configuração, recarregar e apontar o DNS (um registro A, capítulo 2) para o IP do VPS.
Liberar as portas 22, 80 e 443 no firewall e ativar HTTPS (capítulo 3).
# EXEMPLO, nao testado (nao ha VPS aqui). No seu computador (Git Bash ou PowerShell, os dois tem scp/ssh):
# 1) cria a pasta de destino no servidor (o scp nao cria a pasta pai)
$ ssh USUARIO@IP_DO_SERVIDOR "mkdir -p /home/USUARIO/meu-site"
# 2) copia a pasta inteira; o "/." no fim leva tambem os arquivos que comecam com ponto (.nojekyll, .htaccess)
$ scp -r ./meu-site/. USUARIO@IP_DO_SERVIDOR:/home/USUARIO/meu-site/
# alternativa que copia so o que mudou (precisa de rsync nos dois lados; o -n so simula):
$ rsync -avzn --delete ./meu-site/ USUARIO@IP_DO_SERVIDOR:/home/USUARIO/meu-site/
# No servidor, depois do ssh. /var/www e do root: por isso copiamos para a home e usamos sudo
$ sudo mkdir -p /var/www/meusite
$ sudo cp -r /home/USUARIO/meu-site/. /var/www/meusite/
# ativa o site no nginx (Ubuntu/Debian: o nginx so carrega o que esta em sites-enabled)
$ sudo ln -s /etc/nginx/sites-available/meusite /etc/nginx/sites-enabled/meusite
$ sudo rm /etc/nginx/sites-enabled/default     # tira o site padrao do ar (so o link; o arquivo original fica)
$ sudo nginx -t                    # testa a configuracao (comando conhecido; a pagina lida do nginx nao o cita)
$ sudo systemctl reload nginx      # ou: nginx -s reload, como na documentacao

Duas notas sobre esse bloco, ambas não testadas aqui. (1) Permissão: a pasta /var/www pertence ao root, então um scp ou rsync direto para /var/www/meusite com o seu usuário comum dá permission denied. Os jeitos usuais são: copiar para a sua home e mover com sudo (como acima), ou dar a pasta ao seu usuário uma vez (sudo chown -R USUARIO: /var/www/meusite) e aí copiar direto, ou ainda rsync --rsync-path="sudo rsync" (exige sudo sem senha). (2) Ativar o site: em Ubuntu e Debian, o arquivo em sites-available só vale depois do link simbólico em sites-enabled. Sem ele, o nginx -t passa (a configuração antiga está certa) e você continua vendo a página padrão do nginx. Mesmo com o link, o site default costuma atender qualquer nome que não bata com algum server_name (inclusive o acesso pelo IP): por isso removi o link dele, ou então marque o seu bloco com listen 80 default_server;. Em outras distribuições a organização das pastas muda: veja a documentação da sua.

O arquivo de configuração do site (por exemplo, /etc/nginx/sites-available/meusite). Esta é a configuração de exemplo, no formato do guia do nginx:

# EXEMPLO de configuracao, nao testado
server {
    listen 80;
    server_name seudominio.example;     # troque pelo seu dominio
    root /var/www/meusite;              # a pasta com index.html
    index index.html;

    location / {
        try_files $uri $uri/ =404;      # arquivo, depois pasta, senao 404
    }
}

Erro comumQuatro tropeços de VPS. (1) Mudar a configuração e não recarregar: nada muda até o reload. (2) Porta bloqueada: o nginx roda, mas o firewall não libera 80/443. (3) Permissão negada: o seu usuário não escreve em /var/www (é do root), e o usuário do nginx precisa conseguir ler os arquivos. (4) Esquecer o link em sites-enabled: aparece a página padrão do nginx. E o cuidado de ouro: o --delete do rsync apaga no destino o que não existe na origem. Rode antes com -n (simulação), sempre.

5Fechamento do capítulo

Cola da prova

  • Antes de tudo: index.html na raiz, caminhos relativos e teste local com python -m http.server.
  • Se há build, publique a pasta gerada (dist, build, public).
  • GitHub Pages: publica uma branch/pasta do repositório; mudanças podem levar até 10 minutos; plano Free exige repositório público.
  • Plataformas (Cloudflare, Netlify, Vercel): você entrega a pasta ou conecta o Git; a plataforma serve.
  • VPS: você cuida de ssh, nginx, firewall, DNS e HTTPS. Configuração só vale depois do reload.
  • rsync --delete apaga no destino: simule antes com -n.

Teste rápido

Pergunta 1

Seu site abre no seu computador, mas depois de publicado o CSS não carrega. Qual a causa mais provável?

Caminho absoluto só funciona quando o site está na raiz do domínio. E em Linux, Estilo.css e estilo.css são arquivos diferentes.
Pergunta 2

Você editou o arquivo de configuração do nginx e nada mudou no site. O que falta?

O nginx só aplica a nova configuração depois do reload. Se a configuração tiver erro, ele mantém a antiga.
Pergunta 3

Por que simular o rsync com -n antes de rodar com --delete?

Rodar direto pode apagar arquivos do servidor que você queria manter. A simulação mostra tudo antes.
