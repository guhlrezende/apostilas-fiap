1Cliente e servidor

Digito um endereço, aperto Enter e a página aparece. Quem fez o quê nesse meio tempo?

Intuição. É um pedido em balcão. Você (o cliente, quase sempre o navegador) chega e pede uma coisa. Quem atende (o servidor, um computador que fica ligado esperando) entrega o que foi pedido ou diz que não tem. Quem começa a conversa é sempre o cliente: o servidor não toca a campainha sozinho.

Definição. Cliente é o programa que faz o pedido. Servidor é o programa (e, por extensão, a máquina) que fica esperando pedidos e responde. Entre os dois podem existir intermediários, como proxies e caches. A conversa segue um combinado chamado HTTP. (Fora da IBM: a descrição de cliente-servidor e de HTTP vem do MDN. As páginas da IBM que tentei ler sobre isso devolveram só o índice geral.)

Exemplo resolvido: o menor servidor possível, na minha máquina
Criei uma pasta temporária com um único arquivo index.html e rodei python -m http.server 8765 --bind 127.0.0.1. Isso liga um servidor web que só aceita pedidos do próprio computador (o 127.0.0.1).
Em outro terminal, o curl fez o papel de cliente: curl -si http://127.0.0.1:8765/. A resposta veio com a primeira linha HTTP/1.0 200 OK, alguns cabeçalhos e depois o conteúdo do arquivo (45 bytes).
Com o servidor desligado, o mesmo pedido falhou: o cliente não tinha ninguém para atender. Quem pede e ninguém responde é o erro mais básico da web.
$ python -m http.server 8765 --bind 127.0.0.1     # num terminal: liga o servidor
$ curl -si http://127.0.0.1:8765/ | head -8        # em outro: o cliente pede
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.13.5
Date: Fri, 06 Nov 2026 17:42:28 GMT
Content-type: text/html
Content-Length: 45
Last-Modified: Fri, 06 Nov 2026 17:42:25 GMT

<!doctype html><title>oi</title><h1>ola</h1>
$ curl -sS http://127.0.0.1:8765/                   # com o servidor desligado
curl: (7) Failed to connect to 127.0.0.1:8765 after 0 ms: Could not connect to server

Rodado de verdade em 06/11/2026, num Windows 11 com Git Bash. A data e o tamanho são os da execução; a versão do Python depende da sua máquina.

Erro comumAchar que o site "está no ar" porque abre no seu computador. Quando você abre index.html com duplo clique, o navegador lê o arquivo direto do disco (endereço file://): não existe servidor nem HTTP nessa conversa. Para o mundo ver, uma máquina precisa estar ligada, com um servidor rodando, e alcançável pela internet. É disso que o resto da apostila trata.

Com o HTTP: método, caminho, cabeçalhos e código de status.

2HTTP: a conversa em pedido e resposta

O servidor sabe que a minha página inicial é o index.html. Como ele sabe o que eu pedi, e como me diz se deu certo?

Intuição. É um formulário de pedido com campos fixos. Na frente vai o que você quer fazer (pegar, enviar, apagar) e onde (o caminho). Atrás vão informações extras (os cabeçalhos). A resposta volta no mesmo formato, com um número na frente que resume o resultado: o código de status.

Definição. A requisição tem uma linha inicial (MÉTODO caminho HTTP/versão), cabeçalhos e, às vezes, um corpo. A resposta tem uma linha inicial (HTTP/versão código texto), cabeçalhos e, quase sempre, um corpo. O método diz a intenção: GET pede um recurso, HEAD pede só os cabeçalhos, POST envia dados, PUT substitui, DELETE apaga, OPTIONS pergunta o que é permitido. (Fora da IBM, MDN.)

Exemplo resolvido: lendo uma resposta real
Pedi os cabeçalhos de um site público de teste: curl -sI https://example.com. A primeira linha veio HTTP/1.1 200 OK: família 2xx, deu certo.
O cabeçalho Content-Type: text/html; charset=utf-8 diz o tipo do corpo. O curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download} bytes" deu 200 text/html; charset=utf-8 577 bytes: a página inteira tem 577 bytes.
Um caminho que não existe, /nao-existe-xyz, devolveu 404. E http://iana.org (sem o www e sem cifra) devolveu 301 com destino https://www.iana.org/: o servidor mandou ir para outro endereço.
No PowerShell 5.1, Invoke-WebRequest -UseBasicParsing mostra os mesmos fatos em propriedades: StatusCode 200 e StatusDescription OK.
$ curl -sI https://example.com
HTTP/1.1 200 OK
Date: Fri, 06 Nov 2026 17:40:11 GMT
Content-Type: text/html; charset=utf-8
Server: cloudflare
Accept-Ranges: bytes
$ curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download} bytes\n" https://example.com
200 text/html; charset=utf-8 577 bytes
$ curl -s -o /dev/null -w "%{http_code}\n" https://example.com/nao-existe-xyz
404
$ curl -s -o /dev/null -w "%{http_code} -> %{redirect_url}\n" http://iana.org
301 -> https://www.iana.org/
PS> $r = Invoke-WebRequest -Uri https://example.com -UseBasicParsing
PS> $r.StatusCode; $r.StatusDescription
200
OK

Atenção ao shell: os comandos curl -sI, -o /dev/null e head são para o Git Bash (ou para o curl.exe). No PowerShell 5.1, curl é apelido de Invoke-WebRequest e essas opções dão erro; por isso o exemplo em PowerShell usa Invoke-WebRequest direto.

Erro comumDois tropeços que aprendi comparando. (1) Confundir 404 com 500. No meu servidor local, pedir uma rota que não existe dá 404 (erro de quem pediu); já um bug no código do servidor dá 500 (erro de quem mantém). Quando o site "quebra" depois de um deploy, 500 aponta para o seu código e 404 costuma apontar para caminho ou nome de arquivo. (2) POST em página estática. O servidor simples do Python respondeu 501 a um POST na raiz, porque ele só sabe entregar arquivos. Outros servidores respondem 405. O recado é o mesmo: a rota existe, mas não aceita esse método.

3IP e portas: o endereço e a porta de entrada

O pedido sai do meu computador. Para onde ele vai, e como o servidor sabe que é um pedido de site e não outra coisa?

Intuição. A IBM usa a comparação de um hotel: o endereço IP é o prédio, a porta é o quarto. O IP leva a mensagem até a máquina certa; a porta leva até o programa certo dentro dela. Uma máquina pode ter um servidor web, um acesso remoto e um banco de dados, cada um em seu quarto.

Definição. O IP identifica um dispositivo numa rede (existem os de versão 4, como 203.0.113.10, e os de versão 6, bem mais longos). A porta é um número de 0 a 65535 que escolhe o serviço. Os números mais famosos são convenção: 80 para HTTP, 443 para HTTPS e 22 para SSH. (IBM, rede; as portas padrão são convenção de uso, sem página da IBM lida.)

Exemplo resolvido: testando se uma porta responde
O Test-NetConnection example.com -Port 443 tenta abrir uma conexão com a porta 443 do servidor. Veio TcpTestSucceeded : True: tem um serviço ouvindo.
Em seguida testei 127.0.0.1 na porta 8765 com o servidor Python desligado: TcpTestSucceeded : False. Ninguém ouvindo, ninguém atende.
É o mesmo fato do erro curl: (7) que vimos: IP certo, porta sem programa.
PS> Test-NetConnection example.com -Port 443 | Format-List ComputerName,RemotePort,TcpTestSucceeded
ComputerName     : example.com
RemotePort       : 443
TcpTestSucceeded : True
PS> Test-NetConnection 127.0.0.1 -Port 8765 | Format-List ComputerName,RemotePort,TcpTestSucceeded
ComputerName     : 127.0.0.1
RemotePort       : 8765
TcpTestSucceeded : False

O Test-NetConnection é do PowerShell no Windows. No Git Bash, o curl dá a mesma informação de outro jeito. Rodado em 06/11/2026.

Erro comumEsquecer que a porta também precisa estar liberada no caminho. Num servidor de verdade, um firewall pode bloquear a 80 ou a 443 e o site "some" mesmo com o nginx rodando. Uma causa comum de site que some é o firewall não liberar a 22 (SSH), a 80 e a 443. Num servidor remoto isso é não testado aqui.

4Fechamento do capítulo

Cola da prova

  • Cliente pede, servidor responde. Quem começa é sempre o cliente.
  • HTTP é o combinado da conversa: requisição (método, caminho, cabeçalhos, corpo) e resposta (código, cabeçalhos, corpo).
  • Métodos: GET pega, HEAD só cabeçalhos, POST envia, PUT troca, DELETE apaga.
  • Status: 2xx deu certo, 3xx vá para outro lugar, 4xx o pedido está errado, 5xx o servidor falhou.
  • IP escolhe a máquina; porta escolhe o serviço. Padrões: 80 HTTP, 443 HTTPS, 22 SSH.
  • Abrir o arquivo por duplo clique (file://) não é publicar: falta um servidor alcançável.

Teste rápido

Pergunta 1

Seu site devolve 404 depois do deploy. Quem, em geral, deve procurar o erro?

A família 4xx indica pedido que não deu certo (caminho inexistente, por exemplo). Erro de código do servidor é 5xx, como o 500.
Pergunta 2

O que o cabeçalho Location numa resposta 301 faz?

301 significa que o recurso mudou. O navegador lê o Location e faz um novo pedido ali. Vimos http://iana.org devolver 301 para https://www.iana.org/.
Pergunta 3

O servidor está ligado, mas o Test-NetConnection à porta 8765 diz False. A causa mais provável?

Porta fechada ou bloqueada. O IP leva até a máquina, mas é a porta que leva ao programa.
