1Monitorar: saber que caiu antes do visitante

O site subiu. Como descubro que ele caiu, sem ficar atualizando a página?

Intuição. É o painel do carro. Você não abre o motor toda hora, mas quer uma luz que acenda quando algo vai mal. Monitorar é isso: medir o que você já sabe que importa e avisar quando sai do normal. Observabilidade é ir além e entender o porquê a partir do que o sistema emite.

Definição. Segundo a IBM, monitoramento acompanha métricas conhecidas (por exemplo, se o serviço está no ar, uso de CPU) e avisa de problemas; observabilidade usa métricas, logs e traces para entender a causa. Para um site pequeno, o monitoramento mais útil é o "está respondendo?" com o código de status e o tempo de resposta.

Exemplo resolvido: um verificador de site em uma linha
Com o curl, pedi três vezes o mesmo site público, com 1 segundo de pausa, e imprimi o código e o tempo total.
Resultado: três linhas 200, com tempos entre 0,059 s e 0,069 s. Se uma linha trouxesse 5xx, ou 000 (sem conexão), o alarme seria disparado.
No PowerShell, o Measure-Command { Invoke-WebRequest ... } deu a mesma informação: 200 em 147 ms numa medição (uma medição só).
$ for i in 1 2 3; do curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com; sleep 1; done
200 0.069051s
200 0.061540s
200 0.059067s
PS> $t = Measure-Command { $r = Invoke-WebRequest -Uri https://example.com -UseBasicParsing }
PS> "{0} em {1:N0} ms" -f $r.StatusCode, $t.TotalMilliseconds
200 em 147 ms

Rodado em 06/11/2026. Os tempos dependem da sua rede; o que importa é o formato da checagem. Serviços de monitoramento fazem exatamente isso de tempos em tempos e avisam por mensagem; não testei nenhum deles nem sei o plano gratuito de cada um.

Erro comumMonitorar só a página inicial. O site pode abrir na raiz e falhar numa rota importante (o formulário de contato, por exemplo). Inclua pelo menos uma página "profunda" na checagem, e confira o conteúdo quando for crítico, não só o código 200.

2Ler um log de acesso

Tem erro 404 e 500 aparecendo. Onde vejo quem pediu o quê?

Intuição. O servidor anota cada pedido numa linha, como o caderno de visitas de uma portaria: quem veio, quando, o que pediu e o que respondeu. É a primeira coisa a abrir quando algo está estranho.

Definição. O log de acesso do nginx e de servidores parecidos tem, em cada linha, o IP do cliente, a data, a requisição, o código de status e o tamanho da resposta. Com as ferramentas de texto da apostila de Terminal e Git (grep, awk, sort, uniq) dá para resumir. O log de erros é separado e guarda o que o servidor ou a aplicação reclamou.

Exemplo resolvido: resumindo um log de mentira
Escrevi um arquivo com 7 linhas no formato de log de acesso, só para treinar (IPs de exemplo, nada de servidor real).
Contando os códigos de status (nono campo de cada linha): 3 respostas 200, 3 respostas 404 e 1 resposta 500.
Os caminhos que deram 404 foram /Sobre.html (maiúscula trocada: o arquivo se chama sobre.html), /wp-login.php e /.env. Os dois últimos são o tipo de tentativa automática de procurar páginas e arquivos sensíveis: o 404 foi o servidor negando que existe, e é por isso que o .env nunca pode ficar numa pasta publicada.
O único 500 foi um POST /contato: o formulário tem um bug no servidor. Esse é o que se investiga primeiro no log de erros.
$ awk '{print $9}' acesso.log | sort | uniq -c | sort -rn      # conta os codigos de status
      3 404
      3 200
      1 500
$ grep -c ' 404 ' acesso.log                                   # quantos 404
3
$ awk '$9==404 {print $7}' acesso.log                          # quais caminhos deram 404
/Sobre.html
/wp-login.php
/.env
$ grep ' 500 ' acesso.log
203.0.113.5 - - [06/Nov/2026:12:02:10 +0000] "POST /contato HTTP/1.1" 500 0 "-" "Mozilla/5.0"

Rodado em 06/11/2026, num arquivo temporário que escrevi à mão com IPs de exemplo. Em servidor de verdade o caminho do arquivo varia por sistema e por configuração; num Ubuntu com nginx costuma ser algo como /var/log/nginx/access.log, mas isso é conhecimento geral e não testado aqui.

Erro comumGastar tempo com cada 404 de robô. Pedidos a /wp-login.php ou /.env num site que não usa isso são ruído de varredura: o importante é o 404 ser mesmo 404 (e não a entrega do arquivo!). O que merece atenção é o 5xx e o 404 de páginas que existem.

3Rollback: voltar ao que funcionava

Subi uma versão quebrada. O site está fora. Qual a saída mais rápida?

Intuição. É o desfazer. Em vez de consertar às pressas com o site caído, você volta para a última versão boa, respira, e conserta com calma. A pergunta que decide é: consigo voltar em um passo?

Definição. Rollback é restabelecer uma versão anterior. Com Git, o jeito seguro é git revert: ele cria um novo commit que desfaz o anterior e mantém o histórico (e funciona com push normal). O git reset --hard seguido de push --force reescreve o histórico compartilhado e é mais arriscado. Plataformas costumam permitir reimplantar uma versão anterior; não testei nenhuma.

Exemplo resolvido: desfazer uma versão quebrada, rodado
Num repositório temporário, o index.html tinha o commit bom. Troquei o conteúdo, commitei como "v2 quebrada" e o log ficou com 2 commits.
git revert --no-edit HEAD criou um terceiro commit chamado Revert "v2 quebrada". O conteúdo do arquivo voltou ao do primeiro commit (confirmei com cat).
O histórico segue inteiro: 3 commits. Se o deploy é automático (capítulo 6), é esse revert que dispara a publicação da versão boa.
$ git log --oneline
c9ec437 v2 quebrada
9545595 Primeira versao do site
$ git revert --no-edit HEAD
[main 81b1098] Revert "v2 quebrada"
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline
81b1098 Revert "v2 quebrada"
c9ec437 v2 quebrada
9545595 Primeira versao do site
$ cat index.html
<!doctype html><title>oi</title><h1>ola</h1>

Rodado em 06/11/2026. Os hashes mudam a cada pessoa.

Não testado aquiReimplantar versão anterior pelo painel de uma plataforma e o git push --force não foram testados. Se o problema foi no banco de dados ou numa variável de ambiente, voltar o código pode não bastar.
Erro comumNão ter para onde voltar. Quem publica copiando arquivos por cima no servidor (scp) perde a versão anterior. Guarde as versões (Git, tags, o histórico da plataforma) e, antes de uma mudança grande, anote qual é a última versão boa.

4Custo e checklist de lançamento

O site está no ar e estável. Falta o quê para eu dizer "lançado"?

Intuição. Lançar é mais que subir: é deixar o site achável, seguro e barato de manter. Um checklist tira da cabeça o que é fácil esquecer.

Definição. Sobre custo: o que cobra varia por modelo. Serverless cobra por execução, VPS costuma cobrar por mês, plataformas têm limites de tráfego e de tamanho. Eu não cito valores, porque preços e planos gratuitos mudam. Antes de contratar: leia a página oficial de preços na data de hoje, veja o que acontece quando o limite acaba (o site para? cobra a mais?), e ponha um alerta de gasto onde o serviço permitir (não testei nenhum).

5Fechamento do capítulo

Cola da prova

  • Monitorar é medir o que você já sabe que importa (está no ar? quanto demora?) e avisar. Observabilidade usa métricas, logs e traces para entender o porquê.
  • Log de acesso: IP, data, requisição, status, tamanho. Resuma com awk '{print $9}' | sort | uniq -c.
  • 5xx é o que se investiga primeiro. Ruído de robô (404 em /wp-login.php, /.env) é comum.
  • Rollback com Git: git revert (novo commit que desfaz) é mais seguro que reescrever o histórico.
  • Custo: não decore valores. Leia a página oficial de preços na data de uso e veja o que acontece quando o limite acaba.
  • Checklist: HTTPS, DNS, certificado, segredos, links, 404, monitoramento, rollback, custo e backup, cada um com um jeito de provar.

Teste rápido

Pergunta 1

Depois de um deploy, o log mostra vários 500 em POST /contato. O que isso aponta?

A família 5xx é erro do lado do servidor. O 404 é que indicaria pedido a algo que não existe.
Pergunta 2

Qual a vantagem do git revert sobre git reset --hard + push --force para voltar uma versão?

O revert preserva a história compartilhada. Reescrever o histórico e forçar o push pode atrapalhar quem trabalha com você.
Pergunta 3

Por que esta apostila não traz preços nem cotas de planos gratuitos?

Preço e limite são os dados que mais envelhecem. O hábito certo é conferir na hora de contratar.
