1Git e GitHub: duas coisas diferentes

Quem guarda o histórico, e quem guarda a cópia na nuvem?

Git

Um sistema de controle de versão, que roda no seu computador. Registra o histórico de mudanças do projeto: permite voltar a versões anteriores, comparar alterações e trabalhar em paralelo sem perder trabalho.

GitHub

Uma plataforma que hospeda repositórios Git na nuvem. É o intermediário entre o código local e uma cópia remota na internet: backup, colaboração e compartilhamento.

Um repositório é a pasta do projeto com o histórico. No GitHub ele pode ser público (qualquer pessoa vê o código, mesmo sem conta; ótimo para portfólio, material de estudo e open source) ou privado (só você e quem você convidar).

2O caminho de uma mudança

Editar não é salvar no histórico. Salvar no histórico não é enviar para a nuvem.

Um commit é um "ponto de salvamento": uma fotografia do estado dos arquivos naquele momento, com uma mensagem dizendo o que mudou. Até o commit existir, o Git só percebe que algo mudou. O fluxo básico:

  1. Alterar arquivos no projeto.
  2. git add: escolher o que vai entrar no próximo commit (a staging, a "mesa de preparação").
  3. git commit -m "mensagem": tirar a foto.
  4. git push: enviar os commits para o GitHub.

Experimente cada passo e observe onde a mudança está depois de cada botão:

git add .                                  # prepara todas as mudanças
git commit -m "corrige o cálculo do desconto"
git push                                   # envia para o GitHub
add . ou arquivo específico?git add . prepara tudo o que mudou. Para ser seletivo, git add arquivo.py prepara só aquele. A seletividade serve para que cada commit conte uma história só (uma correção, uma funcionalidade), o que facilita entender e desfazer depois.

Uma lista curta que resolve 90% das situações.

Complemento: branches

Uma branch (ramo) é uma linha paralela de commits. Serve para desenvolver algo novo sem mexer na versão estável (a main): você cria um ramo, trabalha nele e, quando estiver pronto, junta (merge) de volta. É o jeito de várias pessoas trabalharem ao mesmo tempo sem pisar umas nas outras. Comandos: git branch, git switch -c nome-do-ramo, git merge nome-do-ramo.

Complemento: boas práticas que evitam dor de cabeça

  • Mensagens que contam o porquê, não "mudanças" ou "arrumei": "corrige desconto para mais de 10 unidades".
  • Nunca commite segredos (senhas, chaves de API, arquivos .env). Em repositório público, qualquer um vê. Se um segredo vazar, revogue-o imediatamente (apagar o commit depois não basta, porque ele fica no histórico).
  • Use um arquivo .gitignore para dizer ao Git o que não versionar (arquivos temporários, .env, pastas de dependências).
  • Faça commits pequenos e frequentes. E git pull antes de começar a trabalhar, se mais gente mexe no projeto.
Ligação com o resto do cursoUm repositório público bem cuidado funciona como portfólio: cada projeto das disciplinas (um notebook de ML, um projeto de ESP32, um site) pode virar um repositório com um bom README. É assim que esta apostila foi publicada.

4Fechamento do capítulo

Cola da prova

  • Git controla versões (no seu computador). GitHub hospeda repositórios na nuvem.
  • Repositório público (todos veem) ou privado (só convidados).
  • Fluxo: editar → git add (staging) → git commit -m (histórico local) → git push (GitHub).
  • git status mostra onde cada mudança está. git pull traz o que você não tem.
  • Branch: linha paralela de trabalho. Merge: junta de volta.
  • Nunca commite segredos. .gitignore lista o que não versionar.

Teste rápido

Pergunta 1

Depois de git commit, as mudanças já estão no GitHub?

O commit registra no histórico local. É o push que envia para o repositório remoto.
Pergunta 2

Qual a função do git add?

O add leva as mudanças para a staging. Só o que está lá entra no commit.
Pergunta 3

Você commitou uma senha num repositório público. O que fazer primeiro?

O histórico guarda o commit antigo, e a exposição pode já ter ocorrido (inclusive por robôs). O primeiro passo é invalidar o segredo.
