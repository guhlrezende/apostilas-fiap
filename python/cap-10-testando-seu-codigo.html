1Um script de assert não é um teste

Quase todo mundo começa conferindo com um arquivo cheio de assert. Funciona, até um dia deixar de funcionar.

Vamos testar esta função de um arquivo loja.py (ela devolve o preço depois de um desconto em porcentagem):

# loja.py
def desconto(preco, percentual):
    """Devolve o preço depois de aplicar o desconto em porcentagem."""
    if percentual < 0 or percentual > 100:
        raise ValueError("percentual fora de 0 a 100")
    return round(preco * (1 - percentual / 100), 2)

A primeira tentativa de conferir costuma ser um arquivo solto:

# verifica.py
import loja

assert loja.desconto(50.0, 10) == 45.0
assert loja.desconto(50.0, 0) == 50.0
print("tudo certo")

Rodando python verifica.py, aparece tudo certo. O problema é o que esse arquivo não faz:

  • Para no primeiro erro. Se o primeiro assert falha, o programa termina com AssertionError e você não sabe se os outros passam.
  • Roda quando é importado. Tudo no topo do arquivo executa no import, e o print aparece mesmo sem ninguém pedir.
  • Não é descoberto por nenhuma ferramenta. Um runner de testes procura testes, e aqui não há nenhum para ele contar.

Para ver isso na prática, mande o unittest carregar esse arquivo (testado):

$ python -m unittest verifica
tudo certo

----------------------------------------------------------------------
Ran 0 tests in 0.000s

NO TESTS RAN

O tudo certo apareceu porque o arquivo foi executado ao ser importado, e mesmo assim o resultado é 0 testes rodados (o comando termina com código de saída 5, que ferramentas de automação leem como falha). Passar sem testar nada é pior que falhar: dá confiança sem motivo.

Erro comumAchar que "o script rodou sem erro" significa "está testado". Um teste de verdade precisa ser achado, contado e relatado individualmente por uma ferramenta, e precisa continuar rodando mesmo que o vizinho falhe.
Para onde vamos agora
Se o script solto não serve, qual é a forma que serve?

O Python já traz um módulo pronto para isso: o unittest.

2unittest: uma classe, métodos test_ e assertEqual

Cada comportamento que você quer garantir vira um método pequeno, com nome que explica o que ele garante.

Intuição. Um teste é uma pergunta com resposta conhecida: "se eu pedir 10% de desconto em 50, deve dar 45". Você escreve a pergunta uma vez e o computador refaz sempre que você mandar.

Definição. No unittest você cria uma classe que herda de unittest.TestCase. Cada método cujo nome começa com test é um teste. Dentro dele, self.assertEqual(obtido, esperado) compara os dois valores; se forem diferentes, o teste falha e mostra os dois. Para conferir que uma exceção sai, use with self.assertRaises(ValueError):.

# test_loja.py
import unittest
import loja

class TestDesconto(unittest.TestCase):
    def test_dez_por_cento(self):
        self.assertEqual(loja.desconto(50.0, 10), 45.0)

    def test_sem_desconto(self):
        self.assertEqual(loja.desconto(50.0, 0), 50.0)

    def test_percentual_invalido(self):
        with self.assertRaises(ValueError):      # o teste passa SE a exceção acontecer
            loja.desconto(50.0, 150)

if __name__ == "__main__":
    unittest.main()

Para rodar, python -m unittest na pasta (ele acha os arquivos test*.py sozinho), ou python test_loja.py por causa do bloco final. Com o código certo, a saída é:

$ python -m unittest -v
test_dez_por_cento (test_loja.TestDesconto.test_dez_por_cento) ... ok
test_percentual_invalido (test_loja.TestDesconto.test_percentual_invalido) ... ok
test_sem_desconto (test_loja.TestDesconto.test_sem_desconto) ... ok

----------------------------------------------------------------------
Ran 3 tests in 0.001s

OK
Exemplo resolvido: o que cada teste conta
desconto(50.0, 10): 50.0 * (1 - 10/100) = 50.0 * 0.9 = 45.0. O esperado no teste é 45.0, então passa.
desconto(50.0, 0): 50.0 * (1 - 0) = 50.0. Passa.
desconto(50.0, 150): 150 é maior que 100, a função levanta ValueError. O assertRaises espera exatamente isso, então passa.

Agora o proveito de ter isso escrito. Troque a versão do código na demo e rode os testes: cada defeito deixa uma marca diferente.

Repare em dois tipos de problema, que o resumo final conta separado:

  • Falha (F, FAIL): o teste rodou e o assert não passou. O valor obtido é diferente do esperado.
  • Erro (E, ERROR): aconteceu uma exceção que o teste não esperava, como um ValueError estourando dentro do código.
Erro comumDar ao método um nome sem o prefixo test (por exemplo verifica_zero). O unittest ignora esse método sem avisar: no meu teste, o método com nome errado tinha uma conta propositalmente errada, e mesmo assim a saída foi Ran 1 test ... OK. Se a contagem de testes não bate com o que você escreveu, confira os nomes.
CuidadoOs testes só protegem o que eles perguntam. Na demo, o defeito 2 só aparece porque existe um teste que pede um percentual inválido. Para cada função, escreva ao menos um caso normal, um limite (como o 0) e um caso de erro.
Outra ferramenta: pytest

O pytest é uma biblioteca de terceiros (instala com pip) que dispensa a classe: o teste é uma função test_... com um assert simples, e ele mostra os valores quando falha. É muito usado, mas o unittest vem com o Python, sem instalar nada, e é o que este capítulo usa. Fonte: documentação oficial do pytest.

Para onde vamos agora
E se a função não devolve nada, mas lê com input() e escreve com print()?

Os testes acima só chamam funções que recebem parâmetros e devolvem um valor. Programas de verdade conversam com a pessoa.

3Testando função que usa input e print

Um teste não pode ficar parado esperando alguém digitar, e o que foi impresso precisa de um jeito de ser conferido.

Esta função repete a pergunta até receber um inteiro maior que zero (o padrão "pedir de novo" do capítulo 9):

# loja.py (continuação)
def pedir_quantidade():
    """Pergunta até receber um inteiro maior que zero."""
    while True:
        texto = input("Quantas unidades? ")
        try:
            n = int(texto)
        except ValueError:
            print("Digite um número inteiro.")
            continue
        if n > 0:
            return n
        print("Precisa ser maior que zero.")

Duas peças da biblioteca padrão resolvem. A primeira é o unittest.mock.patch, que troca um nome por outro só durante o teste e restaura o original no fim. A segunda é o io.StringIO, um "arquivo" que vive na memória: se ele ocupar o lugar do sys.stdout, tudo que o print escreve cai nele, e o método getvalue() devolve o texto.

import io
import unittest
from unittest.mock import patch
import loja

class TestPedirQuantidade(unittest.TestCase):
    def test_aceita_valor_valido(self):
        with patch("builtins.input", return_value="3"):      # input() devolve "3" sem esperar ninguém
            self.assertEqual(loja.pedir_quantidade(), 3)

    def test_pede_de_novo_apos_erro(self):
        # side_effect com lista: cada chamada de input() devolve o próximo item
        with patch("builtins.input", side_effect=["abc", "0", "4"]):
            with patch("sys.stdout", new_callable=io.StringIO) as saida:   # captura o print
                resultado = loja.pedir_quantidade()
        self.assertEqual(resultado, 4)
        self.assertIn("Digite um número inteiro.", saida.getvalue())
        self.assertIn("maior que zero", saida.getvalue())
Exemplo resolvido: as três respostas simuladas
1ª chamada de input() devolve "abc": o int falha, imprime "Digite um número inteiro." e volta ao início do laço.
2ª devolve "0": é inteiro, mas não é maior que zero, então imprime "Precisa ser maior que zero." e repete.
3ª devolve "4": serve, e a função devolve 4. O teste confere o 4 e as duas mensagens que apareceram no caminho. Rodando com o código certo, passou: Ran 5 tests com os 5 testes deste capítulo, OK.

Este teste é o do caminho de erro seguido de acerto, e vale pedir sempre: errar e depois acertar. Um erro típico é a função aceitar a primeira tentativa certa e quebrar na errada (ou pedir só uma vez). Na demo, o defeito 3 retira o try/except e só esse teste percebe.

Onde o patch ageA documentação do unittest.mock orienta trocar o nome no lugar onde ele é usado. Aqui o input é uma função embutida do Python, por isso "builtins.input". Para trocar uma função sua que outro módulo importou, o alvo é o módulo que a usa.
Erro comumDeixar um input() ou um main() solto no topo do arquivo. Importar o arquivo no teste dispararia a pergunta e travaria tudo esperando teclado. Por isso o programa fica em main() dentro do if __name__ == "__main__": (capítulo 9): o import loja só define as funções, e nada é perguntado (testado).

Quantos testes escrever, e quando rodar?

Fechamos com os hábitos que fazem os testes valerem o trabalho.

4Hábitos que fazem o teste valer a pena

Um teste ruim dá medo de mexer no código. Um teste bom dá coragem.

  • Um teste, um comportamento. O nome diz o que se garante (test_percentual_invalido), e quando falha você já sabe onde olhar.
  • Rode depois de cada mudança. O valor está em descobrir o defeito minutos depois de criá-lo, e não na véspera da entrega.
  • Teste os limites e os erros, e não só o caso do meio: o zero, o vazio, o valor inválido, o "errou e depois acertou".
  • Não toque nos seus dados de verdade. Se a função grava arquivo, o teste usa uma pasta temporária (capítulo 9), e não o arquivo que você usa.
  • Quando um defeito aparece, escreva primeiro o teste que o pega e só então corrija. Ele passa a impedir que o defeito volte.

5Fechamento do capítulo

Cola da prova

  • Script solto de assert roda no import, para no primeiro erro e não é contado. python -m unittest verifica mostrou 0 testes.
  • unittest: classe que herda de TestCase, métodos que começam com test, self.assertEqual(obtido, esperado), assertRaises para exceção. Rodar: python -m unittest.
  • Falha (F): o assert não passou. Erro (E): exceção inesperada.
  • Método sem o prefixo test é ignorado sem aviso.
  • patch("builtins.input", side_effect=[...]) simula as digitações; patch("sys.stdout", new_callable=io.StringIO) captura o que o print escreveu (getvalue()).
  • Teste sempre o caminho de erro seguido de acerto, e deixe o programa dentro de main() com if __name__ == "__main__":.

Teste rápido

Pergunta 1

Um arquivo só com assert no topo roda sem erro. Por que isso não basta como teste?

O assert funciona em qualquer lugar. O problema é que o arquivo não é descoberto, contado nem relatado teste a teste, e o primeiro erro esconde os demais.
Pergunta 2

Você escreveu o método def verifica_zero(self): numa classe TestCase. O que o unittest faz com ele?

Só métodos que começam com test são testes. Se a contagem de "Ran N tests" estiver menor do que o esperado, confira os nomes.
Pergunta 3

Como testar uma função que chama input() três vezes, sem ninguém digitar?

O patch troca o input só durante o teste, e o side_effect com lista entrega as respostas em ordem.
