1Dado não é informação

Antes de guardar qualquer coisa, qual é a coisa?

Dados são fatos ou valores brutos, registros que podem ser gravados e têm algum significado inerente: nomes, telefones, endereços. Veja um exemplo do material: "o aluno A tirou 10 na prova de Matemática em 03/04/2025". Cada pedaço (aluno, nota, disciplina, data) é um dado.

A informação nasce quando você organiza e interpreta esses dados para responder uma pergunta: "qual foi a média da turma em Matemática?" A mesma tabela de dados gera informações diferentes conforme a pergunta. Por isso um banco de dados precisa guardar o dado de um jeito que permita perguntar muitas coisas depois.

Exemplo: do dado à informação
Dados: João, 10, Matemática · Maria, 9, Português · Ana, 8, Matemática.
Pergunta: qual a nota média em Matemática?
Informação: (10 + 8) ÷ 2 = 9. Os dados sozinhos não diziam isso. Foi a pergunta que os transformou.

Onde guardar esses dados para poder perguntar muita coisa, para muita gente, sem bagunça?

Em um banco de dados. E quem cuida dele para você é o SGBD.

2Banco de dados e SGBD

Uma pasta de planilhas já é um banco de dados?

Segundo Elmasri e Navathe (a bibliografia da disciplina), um banco de dados é uma coleção de dados relacionados. O slide completa: uma coleção organizada de informações tratadas como uma unidade, para coletar, armazenar e recuperar informações para uso por aplicativos. Um detalhe curioso: um banco de dados pode ser mantido manualmente. Um fichário de papel é um banco de dados. O que mudou foi o jeito de operar.

Quem opera é o SGBD: o software que permite definir, construir, manipular e compartilhar bancos de dados. Você não mexe nos arquivos do disco. Você pede ao SGBD, normalmente em SQL, e ele cuida do resto.

Por que não bastam arquivos soltos?

Num sistema "tradicional", cada programa guarda seus próprios arquivos, e os mesmos dados acabam copiados em vários lugares. O SGBD existe para resolver cinco problemas:

RequisitoO problema que resolve
Controle de redundânciaO mesmo dado em locais diferentes ocupa espaço e se contradiz.
ConsistênciaTodo usuário enxerga os mesmos valores.
Compartilhamento e concorrênciaDuas pessoas não podem alterar o mesmo dado ao mesmo tempo e corromper o resultado.
SegurançaAutenticação (quem é você) e autorização (o que você pode fazer).
Backup e recuperaçãoUm registro (log) de todas as transações permite restaurar depois de uma falha.

Há ainda vantagens extras: busca mais rápida por índices (estruturas em árvore, as B-tree, que você vê no Capítulo 8), persistência, ferramentas de backup, vários usuários e regras (constraints), como "só pode existir um número de matrícula por aluno".

3O modelo relacional, de Codd

Como organizar dados para que o computador não precise "seguir ponteiros"?

Na década de 1960 os bancos eram hierárquicos (IBM). Em 1970, Edgar "Ted" Codd, também da IBM, propôs outro caminho: guardar tudo em tabelas, sem ponteiros, ligadas só pelos valores dos dados. É o modelo relacional, e é o que esta disciplina usa. Depois vieram os bancos orientados a objetos (anos 1980), a web (1990) e, a partir dos anos 2000, o NoSQL e o Big Data.

Três ideias sustentam o modelo:

  • Tabelas (conjuntos de linhas). Cada linha é um registro; cada coluna, um atributo.
  • Sem ponteiros: duas tabelas se ligam porque uma guarda o valor que identifica uma linha da outra.
  • Chaves: a chave primária (PK) identifica unicamente cada linha da própria tabela; a chave estrangeira (FK) guarda a PK de outra tabela e cria a ligação.

Os SGBDs relacionais mais usados: MySQL, PostgreSQL, Oracle, SQL Server, SQLite, MariaDB e DB2. O MySQL e o MariaDB falam praticamente o mesmo SQL, porque o MariaDB nasceu em 2009 como um fork do MySQL, feito pelo mesmo criador logo depois da compra do MySQL pela Oracle.

LembraRepare nas duas palavras que vão voltar em todo capítulo: PK (identifica a linha) e FK (aponta para a PK de outra tabela). Quem entende as duas já domina a base de qualquer modelagem.

4Normalização: cada informação em um lugar só

Se o mesmo dado aparece em várias linhas, o que acontece quando ele muda?

O próprio Codd formalizou regras para eliminar redundância e inconsistência: as formas normais. A ideia: cada informação fica guardada em um único lugar. Sem isso aparecem três problemas, as anomalias:

Inserção

Não dá para cadastrar um cliente sem inventar um pedido.

Atualização

O dado repetido em várias linhas exige mudar todas as cópias. Esquecer uma gera contradição.

Exclusão

Apagar o único pedido de alguém apaga, sem querer, os dados do cliente.

Veja a anomalia de atualização acontecer. A tabela pedido_flat repete o nome e a cidade da Júlia em cada pedido dela. Mude a cidade em uma linha só e depois olhe os clientes distintos:

UPDATE pedido_flat SET cliente_cidade = 'Campinas' WHERE idPedido = 1;
SELECT DISTINCT cliente_nome, cliente_cidade FROM pedido_flat;

A Júlia agora mora em duas cidades ao mesmo tempo. Foi isso que a redundância causou. A versão normalizada separa o cliente (uma linha só) dos pedidos. Repita o mesmo ajuste nela e veja o resultado:

UPDATE cliente_n SET cidade = 'Campinas' WHERE cliente_id = 10;
SELECT p.idPedido, c.nome, c.cidade, p.produto
FROM pedido_n p JOIN cliente_n c ON c.cliente_id = p.cliente_id;

As formas normais, em ordem de rigor

FormaExigeO que eliminaExemplo de violação
1FNvalores atômicos (indivisíveis)grupos repetitivoscolunas telefone1, telefone2, telefone3, ou uma célula com "python, sql, aws"
2FN1FN e nada depende de parte da chavedependências parciaiscom PK composta (pedido, produto), o nome do produto depende só do produto
3FN2FN e nada depende de outro atributo não-chavedependências transitivascliente_nome e cliente_cidade dentro de Pedido: dependem do cliente, não do pedido
BCNFtodo determinante é uma superchavecasos raros de chaves candidatas sobrepostasversão mais rígida da 3FN
CuidadoNormalizar demais fragmenta o banco e custa JOINs (Capítulo 6). Por isso muitos sistemas de produção param na 3FN, e às vezes desnormalizam de propósito por performance. É um trade-off, não um erro.
Sua vez: exercício do slide"Uma empresa quer guardar produtos, clientes e fornecedores. Quantas tabelas? Que relacionamentos?" Resposta de partida: 3 entidades, logo 3 tabelas. Produto e fornecedor costumam ser N:1 (cada produto tem um fornecedor), e cliente e produto se ligam por meio de pedidos, que viram uma 4ª tabela (e uma tabela de itens, para o N:N). 5Fechamento do capítulo

Cola da prova

  • Dado é o fato bruto; informação é o dado interpretado para responder uma pergunta.
  • SGBD define, constrói, manipula e compartilha bancos. Resolve redundância, consistência, concorrência, segurança e backup.
  • Relacional (Codd, 1970): tabelas sem ponteiros, ligadas por chaves. PK identifica a linha; FK aponta para a PK de outra tabela.
  • Normalização: cada informação em um só lugar. Anomalias de inserção, atualização e exclusão.
  • 1FN atômico · 2FN sem dependência parcial · 3FN sem dependência transitiva · BCNF determinante é superchave.
  • Na prática, a 3FN é o ponto de equilíbrio. Desnormalizar é uma escolha consciente.

Teste rápido

Pergunta 1

Uma coluna habilidades guarda 'python, sql, aws' numa única célula. Qual forma normal ela viola?

A 1FN exige valores indivisíveis. O ideal seria uma tabela de habilidades ligada ao funcionário. (No Capítulo 4 você vê por que filtrar essa coluna com LIKE é impreciso.)
Pergunta 2

A cidade de um cliente aparece repetida em todos os pedidos dele. Que problema isso causa?

É a redundância clássica. Basta esquecer uma cópia para o cliente 'morar' em duas cidades, como você viu no exemplo.
Pergunta 3

A diferença entre PK e FK é:

Toda tabela tem uma PK. A FK é a ponte que cria o relacionamento e permite ao SGBD impedir ligações para linhas que não existem.
