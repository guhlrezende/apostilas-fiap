1Índices: a diferença entre achar e procurar

Por que o slide dizia que o SGBD é bom em buscas rápidas?

Sem índice, para achar o funcionário "Ana" o banco lê a tabela inteira, linha por linha (full scan). Com um índice (normalmente uma B-tree, uma árvore balanceada ordenada pela coluna), ele desce a árvore em poucos passos, como achar uma palavra num dicionário aberto no meio. O custo da busca passa de proporcional ao tamanho da tabela para proporcional ao logaritmo dele.

Peça ao banco para mostrar o plano de execução (EXPLAIN) antes e depois de criar um índice:

EXPLAIN QUERY PLAN SELECT * FROM Funcionario WHERE nome = 'Ana';
CREATE INDEX idx_func_nome ON Funcionario(nome);
EXPLAIN QUERY PLAN SELECT * FROM Funcionario WHERE nome = 'Ana';
EXPLAIN QUERY PLAN SELECT * FROM Funcionario WHERE nome LIKE '%na';

Leia os três planos: o primeiro diz SCAN (lê tudo), o segundo diz SEARCH ... USING INDEX (desce a árvore) e o terceiro volta a SCAN, porque LIKE '%na' começa com curinga e o índice, ordenado pelo começo do texto, não ajuda. (No MySQL o comando é EXPLAIN SELECT ..., com uma saída mais detalhada.)

Índices ajudamÍndices custam
leituras com WHERE, JOIN e ORDER BY sobre a coluna indexadaespaço em disco, e cada INSERT, UPDATE e DELETE precisa atualizar o índice (escritas ficam mais lentas)
LembraPK e UNIQUE já criam índice automaticamente. Indexe as colunas que você de fato filtra e junta, e não todas. Colunas com poucos valores distintos (como sexo) ajudam pouco.

2Transações e ACID

Transferir dinheiro são dois UPDATEs. E se o segundo falhar?

Uma transação agrupa comandos que devem acontecer todos ou nenhum. Se algo dá errado no meio, o ROLLBACK desfaz tudo; se está tudo certo, o COMMIT confirma. As propriedades que um SGBD confiável garante se chamam ACID:

Atomicidade

Tudo ou nada.

Consistência

O banco sai de um estado válido para outro estado válido (respeitando as regras).

Isolamento

Transações simultâneas não enxergam o meio uma da outra.

Durabilidade

O que foi confirmado (COMMIT) sobrevive a uma falha.

CREATE TABLE conta (id INTEGER PRIMARY KEY, dono TEXT, saldo REAL);
INSERT INTO conta VALUES (1, 'Ana', 100), (2, 'Bia', 50);

BEGIN;
UPDATE conta SET saldo = saldo - 80 WHERE id = 1;   -- debita a Ana
SELECT dono, saldo FROM conta;                       -- no meio da transação
ROLLBACK;                                            -- desiste: desfaz tudo
SELECT dono, saldo FROM conta;                       -- como se nada tivesse acontecido

Dentro da transação a Ana ficou com 20; depois do ROLLBACK voltou a ter 100. Num sistema real, o segundo passo (creditar a Bia) viria antes do COMMIT, e uma falha entre os dois jamais deixaria o dinheiro "sumido".

3Subconsultas, CTE e funções de janela

Quando uma consulta precisa da resposta de outra.

Uma subconsulta é um SELECT dentro de outro. Quais alocações têm mais horas que a média geral? A média precisa ser calculada antes:

SELECT idFuncionario, idProjeto, horas
FROM ProjetoFuncionario
WHERE horas > (SELECT AVG(horas) FROM ProjetoFuncionario);

Quando a consulta fica longa, uma CTE (WITH) dá nome a cada etapa e deixa o código legível. Quem soma mais de 10 horas no total?

WITH total AS (
  SELECT idFuncionario, SUM(horas) AS h
  FROM ProjetoFuncionario
  GROUP BY idFuncionario
)
SELECT f.nome, t.h
FROM total t JOIN Funcionario f ON f.idFuncionario = t.idFuncionario
WHERE t.h > 10;

E as funções de janela (RANK() OVER (...)) calculam sobre um conjunto de linhas sem colapsá-las como o GROUP BY faz. Disponíveis no MySQL 8 e no SQLite moderno:

SELECT f.nome, pf.horas,
       RANK() OVER (ORDER BY pf.horas DESC) AS posicao
FROM ProjetoFuncionario pf
JOIN Funcionario f ON f.idFuncionario = pf.idFuncionario
ORDER BY posicao, f.nome;

4Injeção de SQL: o ataque que mais derruba sistemas

O erro de montar SQL com texto que veio do usuário.

Se o programa monta a consulta colando o que o usuário digitou dentro do texto SQL, o usuário pode digitar pedaços de SQL. Brinque com a tela de busca abaixo: ela roda de verdade sobre a base alpha. Primeiro com um nome normal, depois com os botões de ataque. Por fim, marque "consulta parametrizada".

A defesa é nunca concatenar. Em vez disso, use consultas parametrizadas (prepared statements): o SQL é fixo, com um marcador (?), e o valor viaja à parte, sempre tratado como dado, nunca como código. É assim em qualquer linguagem. Também vale dar ao usuário do banco da aplicação o mínimo de permissões (se ele não pode fazer DROP, o ataque do botão três falha de qualquer jeito). Esse ataque aparece no catálogo de ameaças da apostila de Cibersegurança.

5E o NoSQL? Quando usar

O slide de panorama citava documentos, chave-valor, grafos e colunas. O que cada um resolve?

TipoIdeiaBom paraExemplos
Documentoregistros em JSON, com estrutura flexívelcatálogos, conteúdo, dados que mudam de formatoMongoDB
Chave-valorum dicionário gigante: chave aponta para um valorcache, sessão de usuário, filas simplesRedis

Grafonós e arestas como cidadãos de primeira classeredes sociais, recomendação, caminhosNeo4j

A escolha é um trade-off: bancos NoSQL costumam trocar parte das garantias de consistência e dos JOINs por escala horizontal e flexibilidade. Para a maioria dos sistemas de negócio (cadastros, pedidos, finanças), o relacional continua sendo a escolha segura. E muitos sistemas usam os dois: o relacional como fonte da verdade e o NoSQL (como o Redis) para acelerar.

6Fechamento da apostila

Cola da prova

  • Índice (B-tree) acelera leituras e atrasa escritas. LIKE '%x' não usa índice. Confira com EXPLAIN.
  • Transação: tudo ou nada (COMMIT/ROLLBACK). ACID: atomicidade, consistência, isolamento, durabilidade.
  • Subconsulta, CTE (WITH) e funções de janela organizam consultas complexas.
  • Injeção de SQL: nunca concatene entrada do usuário. Use consultas parametrizadas e permissões mínimas.
  • NoSQL é trade-off (flexibilidade e escala x garantias). O relacional segue sendo o padrão para dados de negócio.

Teste rápido

Pergunta 1

Por que a consulta WHERE nome LIKE '%na' não se beneficia de um índice em nome?

O índice B-tree ordena pelo início do valor. Com o curinga na frente, o banco não sabe por onde começar e lê tudo.
Pergunta 2

A melhor defesa contra injeção de SQL é:

Filtros de caracteres falham. Parametrizar separa definitivamente o código (SQL) do dado (o que o usuário digitou).
Pergunta 3

Numa transferência bancária, o que a atomicidade garante?

Atomicidade é 'tudo ou nada'. Foi o que o ROLLBACK mostrou.
