2View: a consulta com nome

Escreveu o JOIN uma vez? Chame de novo pelo nome.

Uma view é uma consulta salva. Ela não guarda dados (a consulta roda de novo a cada uso), esconde o JOIN e pode mostrar só algumas colunas, o que ajuda em relatórios e em controle de acesso.

CREATE VIEW ViewProjetosEmAndamento AS
  SELECT P.nome AS nomeProjeto, F.nome, PF.horas
  FROM ProjetoFuncionario PF
  LEFT JOIN Projeto P ON PF.idProjeto = P.idProjeto
  LEFT JOIN Funcionario F ON PF.idFuncionario = F.idFuncionario
  ORDER BY P.nome, F.nome;

SELECT * FROM ViewProjetosEmAndamento;
Erro comumConfiar no nome. A ViewProjetosEmAndamento do slide não filtra "em andamento": ela traz as 21 alocações, sem nenhum WHERE. O nome é só um nome. Quem lê o código, e não o rótulo, não se engana.

3Function: devolve um valor

Por que toda função do MySQL começa com um tal de DELIMITER?

O cliente do MySQL entende ; como "fim do comando". Mas dentro de BEGIN ... END há vários ;, e o cliente cortaria no primeiro. Por isso se troca o delimitador (// ou $$), cria-se o objeto e se volta para ;. Percorra o código:

Uma segunda função do slide lê uma tabela e usa variável. Ela soma as horas de um funcionário (o Carlos, id 2, está em dois projetos e dá 11):

CREATE FUNCTION fn_total_horas_funcionario(p_idFuncionario INT)
RETURNS INT DETERMINISTIC
BEGIN
    DECLARE v_total INT DEFAULT 0;
    SELECT SUM(horas) INTO v_total
    FROM ProjetoFuncionario WHERE idFuncionario = p_idFuncionario;
    RETURN v_total;
END
Complemento, conferido rodandoPara um funcionário sem projeto (a Vanessa, por exemplo), essa função devolve NULL, e não 0: o SUM de nenhuma linha é NULL e sobrescreve o DEFAULT 0 da variável. Para devolver 0, use COALESCE(SUM(horas), 0). Além disso, o slide marca a função como DETERMINISTIC, mas ela lê uma tabela, e o resultado muda quando os dados mudam. O MySQL aceitou assim no teste; marcar como READS SQL DATA seria mais fiel.

5Trigger: o banco reage sozinho

"Quem excluiu o registro XYZ?" Só dá para responder se alguém anotou na hora.

Uma trigger (gatilho) fica ligada a uma tabela e a um evento (INSERT, UPDATE ou DELETE), em um momento (BEFORE ou AFTER), e roda uma vez por linha afetada (FOR EACH ROW). Usos do slide: validar dados e auditar. Dentro dela, OLD é a linha antes da mudança (existe em UPDATE e DELETE) e NEW é a linha depois (existe em INSERT e UPDATE).

Agora rode você, no SQLite. A sintaxe muda um pouco (o corpo fica entre BEGIN e END, e no lugar de NOW() e CURRENT_USER() uso date('now') e um texto):

CREATE TABLE FuncionarioAuditoria (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  habilidades VARCHAR(100) NOT NULL,
  usuario VARCHAR(50) NOT NULL,
  data DATE,
  acao VARCHAR(50)
);
CREATE TRIGGER trg_antes_atualizar_funcionario
BEFORE UPDATE ON Funcionario
FOR EACH ROW
BEGIN
  INSERT INTO FuncionarioAuditoria (habilidades, usuario, data)
  VALUES (OLD.habilidades, 'estudante', date('now'));
END;

UPDATE Funcionario SET habilidades = habilidades || ', python' WHERE idFuncionario = 1;
SELECT * FROM FuncionarioAuditoria;

A tabela de auditoria guardou MySQL, SQL (o valor antigo), e a Funcionario agora tem MySQL, SQL, python. Detalhe do código do slide: essa trigger não tem condição, então dispara em qualquer UPDATE de funcionario, mesmo que ele não mude as habilidades.

Exercício 3 do slide: auditar só mudança de nome de projeto (a solução é complemento)

A solução usa uma condição para disparar só quando o nome muda (no MySQL, IF OLD.nome <> NEW.nome dentro de BEGIN...END; no SQLite, WHEN no cabeçalho). Mude o nome do projeto 1 e depois só a descrição do 2, e veja que só a primeira mudança é registrada:

CREATE TABLE ProjetoAuditoria (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  nome_antigo TEXT, nome_novo TEXT, usuario TEXT, data DATE
);
CREATE TRIGGER trg_projeto_nome
BEFORE UPDATE ON Projeto
FOR EACH ROW WHEN OLD.nome <> NEW.nome
BEGIN
  INSERT INTO ProjetoAuditoria (nome_antigo, nome_novo, usuario, data)
  VALUES (OLD.nome, NEW.nome, 'estudante', date('now'));
END;

UPDATE Projeto SET nome = 'Omega 2' WHERE idProjeto = 1;
UPDATE Projeto SET descricao = 'novo texto' WHERE idProjeto = 2;
SELECT * FROM ProjetoAuditoria;
Complemento: BEFORE ou AFTER?BEFORE roda antes de gravar, então serve para validar ou ajustar o dado que vai entrar (e até impedir a operação). AFTER roda depois de gravar, e serve para reagir ao que já aconteceu (auditoria, atualizar totais). Triggers também escondem lógica: quem lê só o UPDATE não vê o que ela faz, e muitas triggers encadeadas dificultam o diagnóstico.

6Fechamento do capítulo

Cola da prova

  • View: consulta salva, usada como tabela. Não guarda dados.
  • Function: devolve um valor (RETURN) e se usa dentro de um SELECT.
  • Procedure: comandos guardados, chamada com CALL, sem RETURN.
  • Trigger: dispara sozinha num INSERT, UPDATE ou DELETE. OLD é o valor antes; NEW, o depois.
  • DELIMITER troca o fim de comando para que os ; do corpo não cortem a criação.
  • O nome de um objeto não garante o que ele faz: leia o código.
