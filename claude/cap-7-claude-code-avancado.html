Skills.

2Skills

Como ensinar um fluxo uma vez e chamar com uma palavra?

Uma skill é uma pasta com um SKILL.md. A description fica sempre visível para o Claude, e é por ela que ele decide carregar a skill sozinho; o corpo só entra no contexto quando a skill é usada. Você também chama direto com /nome. Pastas: ~/.claude/skills/ (suas, em todos os projetos) ou .claude/skills/ (do projeto, no Git).

---
description: Resume as mudanças ainda não commitadas e aponta riscos. Use quando eu perguntar o que mudou ou pedir mensagem de commit.
---

## Mudanças atuais

!`git diff HEAD`

## Instruções

Resuma as mudanças acima em dois ou três tópicos e depois liste riscos, como tratamento de erro faltando ou valor fixo no código. Se o diff estiver vazio, diga que não há mudanças pendentes.

A linha !`git diff HEAD` roda o comando e injeta a saída no texto da skill antes de o Claude ler. Outros campos úteis do frontmatter: disable-model-invocation: true (só você chama; bom para fluxos com efeito colateral, como deploy) e $ARGUMENTS no corpo, que recebe o que vier depois de /nome. Os antigos comandos em .claude/commands/ continuam funcionando, mas a documentação recomenda skills para coisas novas.

Para isso, subagentes.

3Subagentes

Como fazer uma investigação enorme sem encher a sua sessão?

Um subagente roda numa janela de contexto própria, com system prompt, ferramentas e permissões próprios. Ele trabalha e devolve só o resultado. Serve para preservar contexto, restringir ferramentas (um revisor que só lê) e usar um modelo mais barato em tarefa simples.

---
name: revisor
description: Revisa código recém-alterado procurando bugs, segredos expostos e falta de teste. Use depois de implementar algo.
tools: Read, Glob, Grep
model: sonnet
---

Você é um revisor de código. Leia só o que mudou e aponte, com arquivo e linha:
1. bugs prováveis;
2. chaves, senhas ou dados pessoais no código;
3. comportamento novo sem teste.
Não reescreva o código. Não comente estilo, só o que afeta correção ou segurança.

Campos obrigatórios: name e description. tools limita o que ele pode fazer (aqui, só ler e buscar); sem esse campo, ele herda tudo. Use pedindo: "use o subagente revisor nas mudanças de hoje".

Hooks.

4Hooks

Como garantir que algo aconteça sempre, ou nunca?

Hooks são comandos de shell que o Claude Code roda em pontos fixos do ciclo: SessionStart, UserPromptSubmit, PreToolUse (antes de uma ferramenta; pode bloquear), PostToolUse (depois de dar certo), Notification, Stop, entre outros. O evento chega como JSON no stdin do seu script. Sair com código 2 bloqueia a ação, e o que você escreve no stderr vira o motivo que o Claude lê.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protege-arquivos.sh"
          }
        ]
      }
    ]
  }
}

#!/bin/bash
# Hook PreToolUse: bloqueia edição de arquivos sensíveis (adaptado da documentação oficial).
# O Claude Code manda um JSON no stdin; sair com código 2 bloqueia a ação,
# e o que for escrito no stderr vira o motivo que o Claude lê.

ENTRADA=$(cat)
ARQUIVO=$(echo "$ENTRADA" | jq -r '.tool_input.file_path // empty')
ARQUIVO="${ARQUIVO//\\//}"   # normaliza barras do Windows

PROTEGIDOS=(".env" "package-lock.json" ".git/")

for padrao in "${PROTEGIDOS[@]}"; do
  if [[ "$ARQUIVO" == *"$padrao"* ]]; then
    echo "Bloqueado: $ARQUIVO bate com o padrão protegido '$padrao'" >&2
    exit 2
  fi
done

exit 0
Exemplo resolvido: o hook rodado de verdade
Entrada {"tool_input":{"file_path":"/p/.env"}}: saiu com código 2 e a mensagem "Bloqueado: /p/.env bate com o padrão protegido '.env'".
Entrada {"tool_input":{"file_path":"/p/app.py"}}: saiu com código 0, então a edição segue o fluxo normal de permissão.
DicaO script precisa de permissão de execução (chmod +x) e usa jq para ler o JSON. /hooks mostra os hooks configurados.

MCP e plugins.

5MCP, plugins e o modo não interativo

Como dar ao Claude Code acesso ao Notion, e como rodá-lo de dentro de um script?

# servidor remoto (HTTP, o recomendado)
claude mcp add --transport http notion https://mcp.notion.com/mcp

# servidor local (stdio): tudo depois de -- é o comando do servidor
claude mcp add --env AIRTABLE_API_KEY=SUA_CHAVE --transport stdio airtable -- npx -y airtable-mcp-server

# compartilhar com o time: grava em .mcp.json na raiz do projeto
claude mcp add --transport http meu-servidor --scope project https://exemplo.com/mcp

claude mcp list      # lista e mostra a saúde dos servidores

Escopos: local (padrão, só você, neste projeto), project (no .mcp.json, versionado) e user (você, em todos os projetos). No .mcp.json, use ${VARIAVEL} para a chave não ir para o Git. Dentro da sessão, /mcp mostra o status e faz o login OAuth.

Plugins empacotam skills, subagentes, hooks e servidores MCP numa instalação só; /plugin abre o catálogo. Modo não interativo: claude -p "explique o que este projeto faz" roda uma vez e imprime a resposta; com --output-format json, a saída vem em JSON para outro programa ler. É assim que se usa o Claude Code em scripts e CI.

SegurançaServidor MCP, plugin e hook rodam com o seu acesso. Instale só de fontes confiáveis e leia o que um hook faz antes de ativar.

Teste rápido

Pergunta 1

O que o Claude lê o tempo todo para decidir se usa uma skill?

A description fica sempre no contexto; o corpo só carrega quando a skill é usada.
Pergunta 2

Um hook PreToolUse termina com exit 2. O que acontece?

Saída 2 em PreToolUse nega a chamada da ferramenta. Saída 0 não decide nada e segue o fluxo normal.
Pergunta 3

Você quer que o time inteiro tenha o mesmo servidor MCP ao clonar o repositório. Use:

O escopo project grava no .mcp.json da raiz, que vai para o Git.
Pergunta 4

Por que dar tools: Read, Glob, Grep ao subagente revisor?

Restringir ferramentas é uma das razões para usar subagentes: um revisor não precisa alterar nada.
